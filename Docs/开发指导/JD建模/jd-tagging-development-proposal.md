# JD 标签拆分：开发建议

日期：2026-10-22
适用项目：米哈游「程序&技术」社招 JD BI 展示站
文档性质：需求讨论与开发范围建议，不是实施指令。下文的优先级、数据组织和评估方式可结合现有代码调整，不预设新增框架、服务或数据库表。

## 一、开发目标

为已完成每日采集的岗位 JD 建立一个可重复执行、可追溯、可评估的结构化处理层，将接口事实和正文中的岗位要求整理为稳定的数据维度，供后续岗位筛选、聚合统计和图表展示使用。

期望达到的结果是：同一份JD在同一套规则下得到一致结果；每个提取值能找到原文依据；缺失、歧义和推断能够被明确区分；历史数据能够按指定口径重新分析。

本任务的核心价值不是提取尽可能多的词，也不是自动判断谁适合某岗位，而是提供可信的岗位分析数据基础。

### 本次工作的边界

- 已有每日采集作为上游，通常无需在本任务中重做采集、调度或云部署。
- 主要交付为结构化结果、标签定义与统计口径、质量评估及必要的查询/检查能力。五张图表本身仍可分别安排开发周期。
- 沿用项目以Go为主、Python负责采集的分工；具体实现组织由开发者结合现有工程决定。
- 本任务不改变每个成功采集周期全量保留的既定政策；标签和解析结果不能替代原始JD。
- 首版不以个人匹配评分、岗位难度评分、招聘人数推测或完整技能知识图谱为目标。

## 二、依据与需要先澄清的数据边界

本建议基于可访问的2026-10-19快照（159份JD）及现有采集器字段映射。用户项目已经每日采集，但新的原始响应尚未作为本建议的样本核验。因此，上线前值得对照新采集器的原始响应，确认是否存在过去未保存的结构化字段。

现有数据中，projectName全部为“社会招聘”，不能把它直接理解为游戏项目名称。学历、经验年限、官方发布日期和部门等没有作为独立字段保存在旧快照中，不能据此断言原始接口绝对不存在这些字段。

建议分开考虑三类数据：
1. 基础字段：岗位ID、名称、来源类别、工作地区等事实。
2. 要求与内容标签：技能、经验、学历、业务场景等从文本中提取的内容。
3. 跨期计算指标：新增、移出、提及率和版本变化等程序计算结果。

无需把所有内容都装进同一张通用“标签表”。例如年限有数字和条件，技能有熟练程度和任选关系，适合保留不同的数据形态。

## 三、建议的标签范围与处理层级

### A. 接口直接支持的基础维度

| 维度 | 已知来源 | 建议保留方式与限制 |
|---|---|---|
| 岗位身份 | id | 公司/来源与源ID组合识别岗位，不用标题作身份 |
| 名称 | title | 保留原文；改名仍属于同一岗位 |
| 工作地区 | addressDetailList | 保留多值结构；避免拼接字符串影响统计 |
| 官方岗位大类 | competencyType / competencyTypeId | 官方分类与内部分析分类分开 |
| 工作性质 | jobNature / jobNatureId | 原样保留；旧样本含全职与第三方编制，不额外推断劳动关系 |
| 招聘相关标签 | hireTypeName / projectName / objectName | 根据实测值确认含义，不从字段英文名猜语义 |
| 紧急标记 | hurry | 区分明确false和接口缺失 |
| 原文分区 | description / jobRequire / addition等 | 保留来源字段、原文及适当的展示文本 |

来源提供的结构化字段通常优于正文推断；两者冲突时宜记录冲突，而非静默覆盖。

### B. 建议首批考虑的解析维度

| 维度 | 预期结果 | 处理难点 | 建议优先级 |
|---|---|---|---|
| 技术关键词 | 标准技能、别名、原文、技能族 | 匹配边界、同义词、任选关系、要求属性 | 高 |
| 工作年限 | 数值/区间、总或专项经验、限定词和条件 | 中文数字、多条约束、学历分支、替代经历 | 高 |
| 学历与专业 | 学历范围、专业要求、优先或替代条件 | “硕士2年”等跨维度关联 | 高 |
| 岗位族与细分方向 | 主分类、辅助标签、依据 | 标题跨领域、分类冲突、覆盖不全 | 高 |
| 生产与交付经验 | 明确要求上线、生产环境、排障等 | 区分岗位职责与候选人已有经验要求 | 高 |
| 项目归属 | 已确认项目、候选名称、类型和证据 | 未知项目、技术团队和游戏名称混杂 | 中 |
| 业务场景 | 广告投放、舆情审核、问数、游戏战斗等 | 技术名与业务场景不应混为一类 | 中 |
| 目标平台与硬件 | 操作系统、游戏终端、GPU/网络硬件 | 过去经验平台不一定是该岗位目标平台 | 中 |
| 管理与职责范围 | 团队管理、技术负责人、独立模块交付 | “主导模块”不等于带团队 | 中 |
| 研究与成果 | 论文、竞赛、开源、上线成果 | 需要区分硬性要求和加分项 | 后续 |
| 语言能力 | 英语阅读、口语沟通等 | 能力类型与程度 | 后续 |
| 值班与应急职责 | 明确on-call、值班、故障应急 | 不能进一步推断工时或加班强度 | 后续 |
| 优化目标与指标 | TTFT、P99、成功率、ROAS等 | 指标提及不等于指标要求值 | 后续 |

技术词建议区分语言、框架/引擎、数据库/中间件、基础设施工具、算法/方法等族，底层保留独立技能。Go与Java可以在展示时组合，原始标签不宜合并成“Go/Java”。

岗位族宜允许“待分类”，辅助标签允许多个；主分类互斥有助于矩形树图加总，但不能为了凑齐总数而强制猜测。

## 四、从真实JD看到的关键问题

1. **任选技术关系**：7787写“精通Go / Rust / C++其一”。三项都被提及，但并非每项都必须掌握。建议保留选项组与至少满足一个的关系。
2. **学历影响年限**：9510写“3年以上后端/平台开发经验（硕士2年+）”。取最小值2会丢掉条件，取3也不完整，适合表达为条件分支。
3. **经验可替代**：1327允许游戏从业经历或同等时间的业余/独立游戏开发经历。建议保存可接受经验来源和OR关系，不统一改写成雇佣年限。
4. **生产证据是独立门槛**：9641要求上线过生产级Operator；9624未明确年限但要求生产经验。建议分别记录年限与生产经验，不互相换算。
5. **同一个AI词可能指不同方向**：6373涉及行为树和状态机；9057涉及LLM/Agent评测。宽泛“AI”标签可以保留，但不宜默认归成同一技术方向。
6. **职责与资格不同**：负责建设监控体系，表示入职后工作内容；有监控体系建设经验，表示候选人经历要求。两者可关联，但不应合并计为同一种硬门槛。
7. **来源字段不是要求属性**：jobRequire里也有“优先”；addition也应结合具体文字解释。建议保留来源字段与语义属性两个维度。

这些案例适合作为初期人工审阅样本，而不只是散落在解析器中的特判。

## 五、规则、AI与人工的建议分工

明确字段可直接采用接口值；常见年限句式、技能名称、学历表述等优先用规则与词典解析。规则覆盖不了的条件或项目名称可以形成待复核候选。

AI适合辅助复杂分类、模糊能力归纳和条件关系判断，但不必成为首版依赖。若采用AI，建议与规则结果一样保留原文证据、处理方式、模型/提示版本与复核状态。不能把模型自报置信度当作已验证正确率。

无论使用何种方法，原文未出现的薪资、人数、工时、实际职级、发布原因都不宜猜测。计数、去重、聚合、内容hash和文本diff仍由程序完成。

项目候选可从标题后缀、书名号、正文明确归属表达中发现，再人工确认是否为游戏项目、技术项目或团队。多次出现可以提高复核优先级，不能直接证明其类型。

## 六、建议保留的结果信息

各维度的业务字段可以不同，但宜共享以下追溯信息：
- 对应岗位及JD内容版本。
- 维度、标准化值与原文表述。
- 原文字段与证据位置；若在清洗文本上定位，应说明定位依据。
- 上下文角色：职责、任职要求、补充说明。
- 要求属性：必要、优先/加分、普通提及、无法判定；必要时保留原始限定词。
- 条件组：AND、OR、至少满足几个、学历/经历前提。
- 处理来源：接口、规则、AI或人工。
- 解析器、词典和分类体系版本；候选/确认/待复核状态。

“未提及”“解析失败”“存在歧义”“明确不限”建议分别表示，不能统一写成空字符串或0。

## 七、与拟定图表的关系

| 图表 | 主要数据依赖 | 本任务的作用 |
|---|---|---|
| 岗位变化构成 | 成功采集周期、岗位ID集合、正文版本 | 标签可支持按方向筛选；基础变化计数不依赖语义标签 |
| 年限进度条 | 年限约束、领域、条件与未知状态 | 提供可解释的年限数据；不宜强行压成一个最小数字 |
| 技术岗位版图 | 主岗位族、待分类数量、统计范围 | 提供稳定分类与覆盖率 |
| 岗位方向×技术关键词 | 分类、技能、要求属性、分母 | 支持关键词提及率、证据回溯和限定范围统计 |
| JD修改对照 | 新旧原文版本、字段diff | 标签变化是补充；Git式原文对照不应依赖标签解析成功 |

对于技术“热度”，建议先采用“提及岗位数”和“提及率”等明确名称。每周期同岗位同技能只计一次；每日重复抓到同一岗位不能累加为新增需求。每日截面、周期新增集合和历史唯一岗位是不同统计对象。

多城市、多标签在切片汇总时可能产生重复，图表宜明确计数单位。所有分析只代表当前公司、招聘范围和采集周期，不直接代表行业市场。

## 八、建议的交付结果与评估方向

可考虑形成四类交付：
1. 标签与字段说明：含定义、来源、允许值、未知状态、统计口径及真实例子。
2. 可运行的处理能力：接收现有采集数据，输出版本化结构化结果；实现形式适配已有工程。
3. 质量报告：基于人工审阅样本，列出各维度的正确、漏提、误提与待复核案例。
4. 检查能力：能够从某个标签回到原文，并定位哪些JD没有被可靠解析。初期CLI或导出结果即可，不必立即建设管理后台。

评估可分别观察准确性、覆盖率和可追溯性：
- 已输出结果中有多少正确，而不是只看输出多少标签。
- 原文确有要求的样本中，有多少被完整提取。
- 复杂条件是否保留，未知是否被诚实表达。
- 同一原文和规则能否重复得到一致结果。
- 同一日任务重试是否产生重复标签；规则升级是否留下版本。
- 图表聚合能否回到岗位清单，解释分子、分母与去重依据。

暂不预设缺乏基线支撑的统一“95%准确率”门槛。适合先按维度建立小型人工标注集，覆盖不同岗位族及边界句式，再共同确定验收门槛。抽取器使用的调试样本和最终评估样本宜有所区分。

若历史数据使用新版规则重算，建议明确保存或标注计算口径，避免规则升级被误读为招聘需求突变。

## 九、建议的首轮范围

如果希望先支撑现有图表，建议首轮围绕基础字段、技能及要求关系、年限、学历、主岗位族和明确生产经验展开。项目名称候选、业务场景与平台硬件可作为下一批扩展。

更重要的首轮完成标志是：一批有代表性的JD能被稳定拆分，每条结果有证据，复杂情况不会被错误简化，聚合数字能够复核。标签数量和自动化覆盖率可以随着真实样本逐步增长。

最终实现范围、存储结构、接口形式及是否引入AI，建议由开发者结合现有项目代码、样本评估和成本共同决定。
