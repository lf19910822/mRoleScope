# 技术关键词候选审计（2026-11-13）

状态：远端只读审计报告。本文不表示候选词已经批准、导入或对 Serving 生效；后续应以新的词典版本、全量重算和发布门禁为准。

## 1. 统计口径

- 数据范围：远端 PostgreSQL 当前保存的全部 182 个岗位。
- 版本选择：每个岗位只取 `job_body_content_versions` 中最新创建的正文版本；包含当前仍有效和已确认下线岗位。
- 岗位状态：162 个仍有效，20 个已确认下线。
- 正文范围：只扫描 `description`、`jobRequire`、`addition`，不扫描标题、`jobSummary`、来源标签或投递说明；与当前技术词解析器保持一致。
- 当前正式配置：`technology-mentions-v1` + `technology-keyword-alias-map-v0.3`。
- 当前词典规模：141 个技术身份、159 条已启用规则、9 条条件规则。
- 统计时点：2026-11-13；当前已发布采集批次覆盖 2026-10-22 至 2026-11-13（按上海时间换算）。

## 3. 第一结论：先处理现有条件规则

当前词典中已经存在但尚未进入正式结果的条件规则如下：

| 词面/身份 | 最新正文岗位数 | 其中当前没有任何正式关键词的岗位 | 建议 |
|---|---:|---:|---|
| `Unreal` / `Unreal Engine` | 38 | 4 | 保留 `unreal-engine` 身份，增加上下文规则；不要直接无条件启用裸词。 |
| `Unity` | 24 | 5 | 保留 `unity` 身份，增加游戏引擎上下文规则。 |
| `Shell` | 11 | 0 | 条件规则可以保留，暂不带来岗位级覆盖增量。 |
| `verl` / `VeRL` / `VERL` | 8 | 0 | 只在后训练/强化学习训练语境中命中。 |

此外，正文中出现了 `UE` 31 个岗位、`UE4` 11 个岗位、`UE5` 6 个岗位、完整短语 `Unreal Engine` 13 个岗位。`UE4`/`UE5` 不应简单作为无版本别名丢失代际信息；可以复用 `game-engine` 分类，但应保留版本信息或建立同分类下的独立技术身份。

如果只把 `Unreal`/`Unity` 的上下文规则正确接入，预计可以覆盖当前 19 个零关键词岗位中的 7 个，将岗位级覆盖从 `163/182` 提高到约 `170/182`（93.4%），且不需要新增分类。

## 5. 低优先级或暂不纳入

### 5.1 平台和厂商词

`Linux`（25）、`Windows`（11）、`Android`（7）、`PlayStation`（6）、`Xbox`（2）、`PS5`（2）出现频率不低，但更接近运行平台/目标平台，而非当前技术关键词主维度。若继续复用已有 `platform` 分类，可以单独登记；但它们不会显著解决“技术关键词未命中”的问题，建议放在 v0.4 的第二批。

`NVIDIA`（12）是厂商/生态名，不应作为 CUDA、GPU、DCGM 或 NVSwitch 的别名。`Arista`、`Cisco`、`Juniper` 也暂不登记裸厂商名；应等待明确的设备系统、协议或产品词面。

### 5.2 普通词、论文会议和业务概念

`Engine`、`Gameplay`、`Cache`、`Gateway`、`Pipeline`、`Operator`、`Token`、`Reward`、`Model` 等普通英文词不能直接作为技术关键词。`ICML`、`NeurIPS`、`EMNLP`、`ICLR`、`ASPLOS`、`NSDI`、`OSDI`、`SIGCOMM`、`SOSP` 等论文会议名也不应进入技术关键词主统计。

`AIGC`、`Agentic`、`Post-training`、`Reasoning` 等更接近方向或方法概念，是否进入 `ai-method-or-mechanism` 应单独决定，不能因为频次较高就直接当作软件技术。

### 5.3 `Superlumina`

`Superlumina` 只在 1 个最新正文中出现，语境与 `Unreal Insights` 并列为采样/性能分析工具。当前不建议直接把它作为正式别名写入词典：

1. 需要先在 CVM 原文中确认它是公开产品名、内部工具名还是拼写错误。
2. 外部公开产品的正式拼写是 `Superluminal`，定位为 CPU 性能分析工具；这与样本语境相符，但不能据此自动把 `Superlumina` 纠正为 `Superluminal`。
3. 若确认是公开工具，应登记 `Superluminal`；若确认是内部工具，则保留来源原词并标记为受控候选。

本次不把外部检索结果直接作为词典证据；如要纳入，仍需在 CVM 中回看原文并由项目负责人确认规范名称。

## 7. 实施注意事项

1. v0.4 应是新的不可变词典版本，不修改 v0.3 规则、结果或发布记录。
2. 当前 matcher 对 `conditional` 规则不会产出正式提及；要安全启用 `Unreal`、`Unity`、`UE`、`Triton` 等词，必须先定义可测试的上下文规则，不能只把状态改成 `enabled`。
3. 不要把 `UE4`/`UE5`、`RoCE`/`RoCEv2`、`Megatron`/`Megatron-LM`、`Triton`/`Triton Inference Server`、`Kubernetes`/`kubelet` 合并成无损别名。
4. 新规则仍需逐条批准、全量重算最新及历史正文、验证证据坐标，再切换 Serving 发布指针。
5. 本报告只统计候选，不改变当前技术关键词结果；下一步应先创建对应 OpenSpec change，再实现词典和上下文规则。

## 8. 讨论记录（2026-11-17，第 1 轮）

### 8.1 已确认：Unreal 采用版本独立身份方案 A

项目负责人确认 Unreal 采用“版本作为独立技术身份”的方案，而不是把所有版本压成一个 `Unreal Engine` 身份。

目标语义如下：

```text
正文命中 Unreal / UE
  -> Unreal Engine

正文命中 UE4
  -> Unreal Engine
  -> Unreal Engine 4

正文命中 UE5
  -> Unreal Engine
  -> Unreal Engine 5
```

因此，`UE4`、`UE5` 命中时必须同时产生基础技术身份与版本技术身份。不能仅通过把 `UE`、`UE4`、`UE5` 注册为互相重叠的普通 alias 实现，因为当前 matcher 会对重叠结果执行最长非重叠选择，较短的 `UE` 会被丢弃。v0.4 需要显式表达“版本身份继承基础身份”的关系，或实现等价的确定性展开规则，并为父子命中分别保留证据。

### 8.2 已确认：发布切换与历史重算口径

新词典应作为不可变的 `technology-keyword-alias-map-v0.4` 发布；v0.3 在 v0.4 成功发布前继续作为 Serving 当前版本，避免候选分析期间前端出现空结果。

v0.4 完成全量历史正文重算、证据校验和发布门禁后，必须原子地完成以下动作：

1. Serving 发布指针切换到 v0.4；
2. v0.3 分析配置标记为 `superseded`，旧词典进入弃用状态；
3. 前端、岗位筛选、技术关键词选项和趋势统计只读取 v0.4 结果；
4. v0.3 的历史结果不删除，继续作为不可变审计和回溯材料。

“立刻弃用旧词典”解释为 v0.4 成功发布时立即停止旧版本对产品的影响，而不是在 v0.4 尚未完成时提前清空当前结果。

### 8.3 仍待确定

- `UE5.4` 是单独展示为 `Unreal Engine 5.4`，还是只归入 `Unreal Engine 5`，同时把 `UE5.4` 保留为证据词面。
- `React`/`react` 的前端身份与 `ReAct` 的 agent 范式身份需要采用精确大小写规则，还是为小写 `react` 增加前端语境条件；不能继续使用全局大小写不敏感规则。
- 审计报告第一批高置信度候选是否全部纳入 v0.4，或先只纳入项目负责人明确点名的 Unreal、Unity、React/ReAct 四类修正。

## 9. 讨论记录（2026-11-17，第 2 轮）

本轮将项目负责人对上一轮方案的“同意”解释为：接受上一轮提出的三项推荐口径，并据此继续冻结 v0.4 的匹配语义与首期范围。

### 9.1 已确认：版本、大小写与首期范围

1. `UE5.4` 不单独生成可展示的 `Unreal Engine 5.4` 技术身份。它归入 `Unreal Engine 5`，同时保留原始命中词面 `UE5.4` 作为证据。
2. `React`、`react` 与 `ReAct` 使用精确大小写规则，不再使用全局 `strings.EqualFold`：
   - `React`、`react` -> `React` 前端框架；
   - `ReAct` -> `ReAct` agent 范式；
   - 其他大小写变体不自动推断为上述技术。
3. v0.4 首期纳入用户明确点名的四类修正，并同步纳入审计报告第一批高置信度候选；第二批需要上下文判定或人工复核的候选继续保持候选/条件状态，不因 v0.4 自动启用。

### 9.2 已确认：Unreal 与 Unity 的身份展开

v0.4 不把重叠 alias 当作父子身份继承，而是要求匹配结果显式展开：

| 原文命中 | 正式技术身份 | 证据词面 |
| --- | --- | --- |
| `Unreal` / `unreal` | `Unreal Engine` | 保留原词面 |
| `UE` | `Unreal Engine` | `UE` |
| `UE4` | `Unreal Engine`、`Unreal Engine 4` | `UE4` |
| `UE5` | `Unreal Engine`、`Unreal Engine 5` | `UE5` |
| `UE5.4` | `Unreal Engine`、`Unreal Engine 5` | `UE5.4` |
| `Unity` / `unity` | `Unity` | 保留原词面 |
| `Unity 3D` / `Unity3D` | `Unity` | 保留完整原词面 |

其中：

- `UE4`、`UE5`、`UE5.4` 命中时，基础 `Unreal Engine` 不能丢失；
- `Unity 3D` 是 `Unity` 的别名，不额外创造一个与 `Unity` 并列的技术身份；
- 版本身份与基础身份都必须能够追溯到同一段原文证据，不能用没有证据坐标的后处理补标签；
- 只展示正式技术身份，原始词面用于证据、详情高亮和审计，不作为额外筛选项。

### 9.3 已确认：大小写与语境的边界

精确大小写只能解决 `React` 与 `ReAct` 的直接冲突，不能替代歧义词语境判断。因此 v0.4 仍需为以下规则定义可测试的上下文条件：

- 裸 `UE` 需要游戏引擎语境；`UE4`、`UE5`、`UE5.4` 具备明确版本语义，可直接按 Unreal 版本规则处理；
- `Unreal`、`Unity`、`unity` 需要避免把普通英语或非技术语境直接记为技术命中；
- 小写 `react` 按用户确认归入 React，但需要保留“普通英语动词不应误命中”的语境约束；
- `ReAct` 只接受精确词面或经明确登记的组合词，不得因大小写不敏感规则被归入 React。

因此，v0.4 的设计不能只增加 alias，还需要将“词面匹配”和“身份展开/语境确认”拆成可审计的确定性步骤，并为每一步补充正例、反例和重叠命中测试。

### 9.4 已确认：发布与旧版本切换

沿用上一轮发布口径：

1. v0.4 分析完成前，v0.3 继续作为 Serving 当前版本；
2. v0.4 对全部历史 JD 正文版本重算，并完成证据坐标与正式身份校验；
3. 通过发布门禁后原子切换 Serving 发布指针，v0.3 标记为 `superseded`；
4. 前端、岗位筛选、技术选项和趋势统计只读取 v0.4；
5. v0.3 结果保留用于审计与回溯，不删除、不混入当前展示。

## 10. 讨论记录（2026-11-17，第 3 轮）

### 10.1 现有实现对 v0.4 的实际约束

本轮代码核对确认，当前 `DictionaryRule` 只持久化 alias、大小写模式、边界模式和重叠优先级；分析配置的规则集指纹也只覆盖这些匹配字段。证据写入时还要求“证据所引用的规则”和“产生该技术身份的规则”是同一条规则。

因此以下做法均不可接受：

- 在 matcher 外部临时判断 `UE5 -> Unreal Engine`，但不写入词典/配置快照；

- 只保存一条 `UE5` 证据，却把它伪装成两个没有独立规则 provenance 的技术身份。

否则同一份历史正文在不同代码版本或不同运行节点上可能得到不同结果，也无法由现有证据校验链复演。

### 10.2 推荐的确定性处理流水线

```text
正文字段
  -> 词面候选
  -> 标识符边界
  -> 语境门槛
  -> 重叠区间选择
  -> 父子身份展开
  -> 每个正式身份分别保存证据
```

推荐把“词面命中”和“身份展开”明确拆开：

1. 词面规则负责回答“原文是否命中了哪一个登记词面”；
2. 语境规则负责回答“这个词面在当前正文片段中是否确实表示目标技术”；
3. 身份展开规则负责回答“一个已确认词面需要产生哪些正式技术身份”；
4. 每个正式身份都保留同一原文区间，但有自己的可追溯规则关系；
5. v0.4 的配置快照必须包含语境规则和身份展开关系的稳定指纹。

- `UE4`、`UE5`、`UE5.4`；
- `Unreal Engine`；
- `Unity 3D`、`Unity3D`；
- 精确大小写的 `React`；
- 精确大小写的 `ReAct`。

- 裸 `UE`；
- `Unreal`、`unreal`；
- `Unity`、`unity`；
- 小写 `react`。

| 原文示例 | 预期结果 |
| --- | --- |
| `熟悉 UE5、C++ 和蓝图开发` | `Unreal Engine`、`Unreal Engine 5` |
| `熟悉 UE、Unity、C++，负责游戏客户端开发` | `Unreal Engine`、`Unity`、`C++` |
| `推动团队 unity` | 不命中 `Unity` |
| `熟悉 Unity 开发和 3D 游戏引擎` | 命中 `Unity` |
| `熟悉 React 和 TypeScript` | 命中 `React` 前端框架 |
| `系统会 react to user input` | 不因普通英文动词自动命中 `React` |
| `了解 ReAct agent 范式` | 只命中 `ReAct`，不命中 `React` |

对于条件规则，建议只在**同一正文字段中的同一标点分隔片段**内判断，并设置最大 Unicode 长度上限；不扫描整份 JD 作为上下文，也不跨越段落寻找“远处证据”。

## 12. 讨论记录（2026-11-17，第 5 轮）

项目负责人表示上一轮“强分隔符集合 + 96 个 Unicode code point 局部窗口”的问题不够直观。本轮改用生活化比喻解释，不改变上一轮提出的方案。

### 12.1 为什么需要“语境”

有些词既可能是技术名，也可能是普通语言。系统不能只看到文字就直接打标签。

例如：

- `熟悉 UE5、C++ 和蓝图开发`：这里的 `UE5` 明确是 Unreal Engine 5；
- `熟悉 UE、Unity、C++，负责游戏客户端开发`：这里的 `UE` 和 `Unity` 也明显是游戏引擎；
- `推动团队 unity`：这里的 `unity` 更像“团队团结”，不应该算 Unity 引擎；
- `系统会 react to user input`：这里的 `react` 是普通英文动词，不应该算 React 前端框架。

所以，系统要像人一样多看附近几个词：附近有“游戏、引擎、C++、蓝图”等词，才批准歧义词成为技术命中。

### 12.2 什么是“强分隔符”

可以把一段 JD 想象成一条走廊，把句号、分号、问号、感叹号想象成墙：墙两边通常是不同的语义房间。

```text
熟悉 UE、Unity、C++，负责游戏客户端开发；熟悉后端服务。
<---------------- 游戏语境房间 ---------------->|<-- 后端房间 -->
```

首期把下面这些符号当作“墙”：

- 中文：`。`、`！`、`？`、`；`
- 英文：`.`、`!`、`?`、`;`

逗号、顿号、斜杠暂时不当作墙，因为技术清单经常用它们连接同一组内容：

```text
UE、Unity、C++，负责游戏客户端开发
```

这里 `UE`、`Unity`、`C++` 和“游戏客户端开发”应该留在同一个语境里。

### 12.3 什么是“96 个 Unicode code point 窗口”

可以把它想象成：系统拿着手电筒照亮命中词附近的一小段文字，而不是照亮整份 JD。

```text
很远的无关内容 ... |  [最多约 96 个字符的局部范围]  | ... 很远的内容
                                      ^
                                    UE
```

例如：

```text
前文很长很长……团队文化强调 unity。后文才出现游戏引擎、C++、蓝图开发。
```

如果 `unity` 和“游戏引擎、C++、蓝图开发”距离太远，系统不会把后文借过来替它解释。这样可以避免一份 JD 里某处出现游戏技术，就把其他地方的普通英文 `unity` 误判成 Unity 引擎。

`96` 不是要求用户记住的产品概念，而是工程上的安全上限：

- 太小：`UE、Unity、C++，负责游戏客户端开发` 可能看不到完整语境；
- 太大：容易把同一份 JD 其他句子的词借过来，误判普通词；
- `96`：覆盖一条通常的技能要求，同时限制语境影响范围。

### 12.4 这次实际要确认什么

问题可以简化成一句话：

> 对 `UE`、`Unity`、小写 `react` 这类容易有普通含义的词，我们是否只参考它们附近的一小段文字，不参考整份 JD？

我的建议是接受这个方案。它类似人工审核时的原则：看同一句话和附近内容，不因为整篇 JD 其他地方出现过游戏或前端词，就强行解释当前这个普通词。

### 13.1 修正原则：直接技术词优先，不要求陪跑词

技术词典的基本任务是识别 JD 正文明确写出的技术名称，而不是要求 JD 使用固定句式。以下内容都应该能够命中 `Unity`：

```text
熟悉 Unity
有 Unity 开发经验
Unity 客户端程序
```

即使这些句子附近没有 `C#`、`游戏` 或 `3D`，也不应因为缺少陪跑词而漏选。

因此，本轮建议把规则从：

```text
命中 Unity + 附近存在技术语境 -> 记录 Unity
```

调整为：

```text
命中已登记的明确技术词面 -> 默认记录技术身份
只有遇到明确、可复演的普通语言反例 -> 抑制该次命中
```

这相当于把“语境”从入场券改成安全护栏：没有陪跑词不再阻止命中，只有出现明确反例时才阻止误判。

### 13.2 对四类词面的建议处理

| 词面 | 默认处理 | 说明 |
| --- | --- | --- |
| `Unreal`、`unreal` | 直接命中 | 在 JD 技术正文中作为引擎名的概率高；不要求附近再出现“游戏” |
| `UE` | 直接命中，但保留明确排除模式 | 不因缺少 `C++` 或“蓝图”而漏选；若明确属于 `User Experience` / `用户体验` 语境，才抑制 |
| `UE4`、`UE5`、`UE5.4` | 直接命中并展开父子身份 | 版本词面本身已经是强技术证据 |
| `Unity`、`unity`、`Unity 3D`、`Unity3D` | 直接命中 | 不要求附近出现其他技术词；只对明确普通英语短语做排除 |
| `React`、`react` | 精确词面直接命中，`ReAct` 独立 | 只排除明确的普通动词短语，例如 `react to`；不能用“附近没有前端词”作为漏选理由 |
| `ReAct` | 精确大小写直接命中 | 不因附近出现 `React` 或前端词而合并 |

### 13.3 “96 个字符窗口”的新定位

在这个修正方案中，`96` 个 Unicode code point 不再是“必须在范围内找到正向技术词”的范围，而只用于检查明确的反例。

例如：

- `熟悉 Unity`：直接命中，不需要寻找附近技术词；
- `负责 Unity 游戏开发`：直接命中；
- `推动团队 unity`：如果命中明确的普通英语排除模式，则抑制；
- `系统会 react to user input`：识别为普通动词短语，抑制小写 `react`；
- `熟悉 React`：直接命中，不需要额外出现 `前端` 或 `TypeScript`。

这样既保留了单独技术词的召回能力，也没有完全放弃对明显普通语言的防误判能力。

### 13.4 本轮结论性质

本轮确认了一个重要产品取舍：对于 JD 技术词典，**明确技术词面的漏选比少量可解释的普通词误选更难接受**。因此建议 v0.4 采用“默认直接命中，明确反例抑制”的策略，废止“必须存在正向语境词才命中”的严格门槛。

该修正仍需在 OpenSpec 设计中补齐：排除模式的固定词表、边界、优先级、审计证据和测试正反例；不能让实现者自由发挥普通语言判断。

### 15.2 现有 OpenSpec 对新变更的影响

现有变更已经提供了可复用基础，但不能直接当作 v0.4 实施计划：

- `implement-jd-technology-mentions` 建立了正文版本、证据坐标、规则快照、全量重算和发布门禁；
- `add-go-golang-technology-dictionary` 展示了不可变 successor dictionary 和 v0.2 -> v0.3 原子切换；
- `fix-serving-technology-publication-projection` 明确了 Serving 只能读取 active publication pointer；
- 但当前发布入口和部分发布门禁仍以 `v0.3`、`V03ApprovedRuleKeys`、`ReleaseV03Upgrade` 为固定名称。

因此 v0.4 不应简单复制一套“v0.4 专用硬编码流程”，而应在新的 OpenSpec 设计中明确：
