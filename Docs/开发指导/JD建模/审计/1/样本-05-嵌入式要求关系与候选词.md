# 样本 05：嵌入式候选词与 C/C++、Python 要求关系

## 1. 问题简介与失败环节

P1、P2 的历史任务均以 `policy_rejected` 结束，旧账本没有保存首个细分阶段。P3 是一份 1,257 Token 的完整 JSON；其失败被离线诊断定位为 `candidate_mention` 持久化环节：模型列出 14 个候选词，而旧路径不能把这些候选写入已发布词典的候选队列。

本样本不只是在测试候选词边界。P3 还将分别引用两条独立要求的 C/C++ 和 Python 放进一个 `at_least/1` 组，即“二者任选其一”。正文是否真的表达任选关系，是直接影响筛选展示的语义问题；不能因为当前失败点恰好是候选词，就忽略该技术关系。

P1 的领域键没有逐字使用“嵌入式开发”；P2 有 `base_year` 却没有 item；P3 修复了前两项形式问题，但仍把两条分别陈述的技术要求合并成一个任选组。候选列表则同时包含操作系统、接口、总线、外设、传感器、物理量与控制对象，粒度并不一致。

## 4. 提示词相关片段

> V3：`configured` 时同时给出至少一项 `items`；总体年限用 `scope_type=base`、`scope_key=overall`。

> V2/V3：领域 `scope_key` 必须逐字复制自引用片段的原文，不得翻译或归一化。

> 技术关系规则：清晰并列的 A、B、C 为 `min_satisfied=3`；只有“任一/之一/至少一种/或”才为 1。逻辑不明确时不要生成可用逻辑组，使用 `uncertain` 与 `required_review`。

> 熟练度规则：精通=P4，熟悉=P2；词典外技术放 `candidate_mentions`，且必须 `required_review`。

P3 的熟练度映射与提示词匹配；但是两条独立片段之间没有“或”或“任选”字样，仍被模型合成 `min_satisfied=1`。提示词没有专门说明“来自不同条目的多个正向要求不得自动合并成任选组”，这是可考虑的提示词边界，但是否需要改由 FAN 裁决。
