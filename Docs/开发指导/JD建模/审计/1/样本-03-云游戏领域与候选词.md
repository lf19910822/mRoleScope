# 样本 03：云游戏领域年限与泛化候选词

## 1. 问题简介与失败环节

本正文版本的 P1、P2 账本均为 `policy_rejected`，但旧路径没有持久化首个细分失败阶段。P3 是 733 Token 的完整、可解析回复；结构和引用通过后，在已发布词典下的 `candidate_mention` 持久化阶段被历史路径拒绝。

P3 的失败并不抹掉其已经给出的学历（未配置）和经验结论；离线回放已证明，将冻结词典候选转为需人工审计的 `uncertain` 事实后，持久化可完成。模型答案本身仍有两个独立的语义问题需要判断：它把“或”连接的三个方向分别列为领域经验项，且把产品、工作方式和泛称都放入候选词。

## 2. JD 相关证据片段

> `[jobRequire:s03]` 在云计算、后台开发或音视频/流媒体等方向具备3年以上系统性实践经验

> `[addition:s02]` 有云游戏、游戏平台或流媒体相关产品的一线研发或技术决策经验

> `[description:s02]` 负责云游戏核心技术方向的架构设计与落地

> `[description:s07]` 结合算力供给、传输链路、平台工程等多个维度

> `[addition:s04]` 实际将LLM/Agent工具融入日常工作流

> `[addition:s05]` 能用AI手段提升个人或团队的研发与决策效率

P1 所有领域键都是英文化/归一化改写，和它们引用的中文片段不逐字相同；P2 不含满足严格映射要求的 item。P3 改为原文领域与总体项，但没有在结构里表达“云计算、后台开发**或**音视频/流媒体”是任选关系，而是并列给出三项领域经验。候选词中有一部分来自职责或加分描述，P3 对这些项给出 `unspecified`，但仍列入候选集合。

## 4. 提示词相关片段

> V2/V3：领域 `scope_key` 必须逐字复制自且只出现于一个引用片段的原文；不得翻译、归一化、加下划线或编造领域名。

> V3：单个字段不确定不影响其他字段；无法可靠表示的条件应使用 `uncertain` 与 `required_review`，不得补造范围或证据。

> 技术关系规则：只在逻辑明确时建立 `at_least` 组；“任一/之一/至少一种/或”为 1，关系不明确时不要建立可用逻辑组。

> 词典外技术放 `candidate_mentions`，且候选词必须 `required_review`。

经验项没有与技术要求组同样的“任选关系”结构。提示词要求模型抽取领域经验，却没有规定面对“领域 A、B 或 C”时应只保留总体经验、以 `uncertain` 降级，还是可以分别记录三个领域项；这正是本样本应由业务裁决的建模边界。
