# 样本 04：生成式模型术语、Python/PyTorch 关系与熟练度

## 1. 问题简介与失败环节

P1、P2 的旧任务均以 `policy_rejected` 结束，历史账本未保存细分失败阶段。P3 返回了 872 Token 的完整 JSON，且学历、技术组的引用均可解析；其历史失败被离线诊断定位为 `candidate_mention` 持久化阶段：模型给出的候选词无法按旧路径写入已发布的词典候选队列。

因此本样本同时暴露两类问题：

1. 工作流问题：候选词是局部、需复核的信息，不应使可独立验证的“硕士及以上”或 Python/PyTorch 结论整体不可展示。
2. 模型质量问题：同一句“熟悉 Python 与 PyTorch”，P1/P2/P3 对必要数量和熟练度的输出并不一致。

P3 对“与”使用 `min_satisfied=2`，但没有把原文“熟悉”映射为 `P2`。P1 的 `P3` 与提示词规定的“熟悉=P2”不一致；P2/P3 的 `null` 是保守遗漏还是质量问题，需要业务判断。候选词同时包含模型类别、媒体对象、数据/动作概念和可能的工具/领域名，不能因为它们均被模型列出就认定为同一层级的技术。

## 4. 提示词相关片段

> 熟练度规则：了解=P1、**熟悉=P2**、熟练/熟练掌握/能独立使用=P3、精通/专家级/深入掌握=P4；未明确则 `null`。

> 关系规则：清晰并列的 A、B、C 使用 `at_least`，`min_satisfied` 为明确数量；“任一/之一/至少一种/或”为 1。

> 词典外技术放 `candidate_mentions`，不得伪造 `technology_key` 或让候选词成为有效 options；词典外候选必须 `required_review`。

提示词已经能约束“熟悉”的枚举和“与”的并列关系，却没有规定候选词应是可治理的技术实体而非媒体对象、泛化模型类别或研究主题。P2 对 `at_least=1` 的输出也显示仅有该规则文字不足以保证模型执行一致。
