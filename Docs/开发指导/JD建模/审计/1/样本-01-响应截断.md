## 4. 提示词相关片段

三版都要求“输出必须是……单一 JSON 对象”，且“不得输出 Markdown、代码块、自然语言说明”。这正是 P3 JSON 语法门的直接契约。

与本样本有关的版本差异：

> V1 经验规则：非具体领域只能使用原文明确的固定领域名。

> V2 经验规则：`scope_type=domain` 时，`scope_key` 必须逐字复制自且只出现于一个引用片段的原文。

> V3 经验规则：`configured` 时同时给出 `items`（至少一项），每项有 `evidence_span_ids`；总体年限使用 `scope_type=base`、`scope_key=overall`。

V2 没有要求 `configured` 的经验必须含 `items`，而校验器 V1 要求 `base_year` 与可验证 item 的最大年限一致；P2 的“有 base_year、无 items”正处在这个提示词/校验器断层上。V3 已把这项要求写进提示词，但 P3 在写完部分 item 前耗尽了预算。

## 6. 对 P3 截断的补充核查（2026-10-26）

对已保存的这**一份** P3 原始回复做了离线结构检查；没有重跑模型，也没有展示或复制回复正文。结果如下：

- 请求构造层已开启结构化输出：`response_format.type=json_schema`、`json_schema.name=ai-jd-result-v1`、`strict=true`；同时显式发送 `enable_thinking=false`、`temperature=0` 和 `max_tokens=2500`。该结论来自 P3 所用不可变客户端版本及其请求构造测试。
- 保存的 `message.content` 没有 Markdown 围栏、`<think>`、`reasoning`、`思考过程`、`推理过程` 或 `analysis:` 标记；字符串外也没有 JSON 语法字符以外的字节。因此，**没有证据表明模型把自然语言推演、Markdown 或其他字段外文本写进了这份回复内容。**
- 9,065 字节中有 8,813 字节为空白（97.2%）。807 个物理行中只有前 13 行非空，之后是连续 794 行空白；最后一个非空字符仍为逗号。JSON 因而保持在“对象/数组尚未闭合”的中间状态。
- 账本的 `output_tokens=2500` 正好等于请求上限。这与“模型先生成了一个未完成的结构化 JSON 前缀，随后持续生成 JSON 语法允许的空白，最终耗尽输出预算”一致。客户端未保存 provider 的 `finish_reason`，所以不能把停止原因表述为某个 provider 专属结束码。

### 这对契约的含义

`strict=true` 确实随请求发送，但它不能在请求被 `max_tokens` 中断时替模型补上尚未生成的 `]`/`}`；而 JSON 语法允许对象内部出现任意数量的空白。因此“单一 JSON、不得 Markdown/说明”的现有提示词足以禁止解释文本，却**没有明确要求紧凑 JSON、禁止空行/缩进，或要求在预算内优先闭合对象**。本例说明仅提高到 5,000 Token 不能单独构成防线：它增加完成机会，却也可能让同类空白继续消耗更大的预算。

建议把已裁决的 5,000 Token 与下一版提示词/契约一并落实：明确要求输出紧凑 JSON（第一个字符 `{`、完成时最后一个字符 `}`；不得缩进、换行、空行或字段间空白），并在客户端保存脱敏的 `finish_reason`/是否达到输出上限。后者可把未来的“长度截断”与其他无效 JSON 明确区分；两项都不应放宽 JSON 完整性校验。
