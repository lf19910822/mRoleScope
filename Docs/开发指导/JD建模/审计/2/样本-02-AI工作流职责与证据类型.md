# 样本 02：AI 工作流 JD 将职责、span 与技术证据混为一谈

## 1. 问题简介与失败环节

该 Plus 回复在证据契约校验处以 `invalid_evidence_reference` 安全失败；受控审计结论为 `evidence_contract_mismatch`。重建输入中只有一个 verified 命中：`RAG`，其 `mention_evidence_id` 是一个 UUID，来源为 `description:s04`。

模型一方面为 RAG 选项同时给出了该 UUID **和** `description:s04`；后者是 span ID，不是 mention evidence ID。另一方面，它为 LLM Agent 编排、数据处理 Pipeline、API 集成等不在 verified 列表内的术语创建了正式 option，并同样将普通 span 作为技术证据。

这份 JD 还暴露角色边界：RAG、LLM Agent 编排和 Pipeline 出现在工作职责中，不能仅因技术词被命中就自动成为候选人的资格要求。

## 2. JD 相关证据片段

> `[description:s04]` 包括 LLM Agent 编排、RAG 架构设计、数据处理 Pipeline 与 API 集成方案

> `[jobRequire:s01]` 5-10 年工作经验

> `[jobRequire:s04]` 有 AI 改造既有业务场景的实践经验

> `[jobRequire:s09]` 熟悉 Agent 平台架构设计

> `[jobRequire:s10]` 包括记忆系统、上下文管理、编排规划及 Agent 评测体系构建

前一段是“设计什么”的职责；后两段才是候选人资格文本。当前 verified 列表中的 RAG 却只来自职责片段。

## 3. Plus 的保存结论（未人工修正）


| 字段                        | 模型结论                                                     | 证据问题                           |
| ------------------------- | -------------------------------------------------------- | ------------------------------ |
| 总体经验                      | `base_year=5`，引用 5-10 年工作经验                              | 总体下限可独立审阅；本次失败不等于该项为假。         |
| RAG option                | `qualification/required`，并附一个有效 UUID 与 `description:s04` | 后一个 ID 类型错误；且证据来自职责，不足以推出资格要求。 |

| 词典外候选                     | 从 `description` 中列出 AI-Native、Agent 编排规范、Prompt 工程方案等    | 与审计/1 已定的“职责不收集候选词”边界冲突。       |




## 4. 提示词相关片段

> `role=qualification` 才是候选人要求；`role=responsibility` 是入职后工作内容；只有 qualification 参与候选人要求组。

> 词典外候选只收集候选人 qualification 中 necessity=required 或 preferred 的陌生术语；职责不得输出为候选。

> 技术 option 必须引用对应 `mention_evidence_id`；关系不明确时使用 `uncertain` 与 `required_review`。
