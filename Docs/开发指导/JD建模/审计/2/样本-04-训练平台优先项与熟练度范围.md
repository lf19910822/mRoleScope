# 样本 04：训练平台 JD 的“优先”翻转与熟练度修饰范围

## 1. 问题简介与完成环节

该 Plus 结果完成并持久化，但受控复核确认了一个 `major_error/necessity_reversal`，以及若干熟练度过度推断的 `minor_error/other`。

最明确的问题来自调度系统句：模型对应的 requirement group 被持久化为 `qualification/required/at_least/1`，而原文把具体系统经验说成“优先”。模型还把“熟悉调度器原理”扩展成 Volcano、Kueue 等具体系统的 P2。

这不是“模型完全不能识别技术”的问题：同一结果中，5 年总体经验、本科学历、Kubernetes 的高熟练度、Docker/containerd/Helm/Prometheus/Grafana 的 P2、以及 Go 或 Python 的 `at_least/1` 都存在可接受的局部结论。

## 2. JD 相关证据片段

> `[jobRequire:s01]` 本科及以上学历，计算机、软件工程等相关专业，5 年以上后端/基础设施研发经验

> `[jobRequire:s02]` 深入理解 Kubernetes 原理与生态，具备 Operator/Controller/CRD 开发经验，熟悉 client-go

> `[jobRequire:s03]` 熟悉云原生技术栈：容器化(Docker/containerd)、服务网格、Helm、Prometheus/Grafana 监控体系

> `[jobRequire:s05]` 了解分布式训练框架原理……有 PyTorch Distributed、Megatron-LM、DeepSpeed 等框架对接经验者优先

> `[jobRequire:s06]` 熟悉调度器原理，有 Volcano、Kueue、Slurm 等批处理调度系统使用或二次开发经验者优先

> `[jobRequire:s07]` 熟练使用 Go 或 Python 进行系统级开发

## 4. 提示词相关片段

> “优先”、“加分”、“更佳”等明确可选条件为 `preferred`。

> 只按明确熟练度词映射；未明确则 `null`；年限、必要性和常识不得补全。

> 同一明确资格片段内清晰并列的 A、B、C 才按明示关系建组；不同片段中的硬性资格不得合并成任选。
