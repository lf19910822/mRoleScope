# 样本 01：爬虫 JD 在空 verified 列表中伪造正式技术选项

## 1. 问题简介与失败环节

这份 Plus 回复是合法 JSON，但在语义持久化之前的证据契约校验以 `invalid_evidence_reference` 安全失败。受控终端审计结论为 `evidence_contract_mismatch`。

关键运行事实：重建输入的 `verified_technology_mentions=[]`。模型却仍输出了一个 `qualification/required/at_least/1` 技术组，其中包含 Chromium、Web 引擎、网页渲染、JS 执行、DOM/BOM 等正式 `technology_key`；各项的 `mention_evidence_ids` 填写为 `jobRequire:s01` 一类的**片段 ID**，而不是输入中不存在的 `mention_evidence_id`。

因此失败不是 API、预算或 JSON 格式问题，而是“正式技术选项必须严格来自确定性词典命中”的输入/输出契约没有被模型遵守。该失败发生在技术项落库前，不能把模型声称的技术组当作可展示事实。

## 2. JD 相关证据片段

> `[jobRequire:s01]` 具备成熟的 Chromium 浏览器内核二次开发、内核定制、内核性能优化实战经验

> `[jobRequire:s02]` 深入理解 Web 引擎完整工作原理

> `[jobRequire:s03]` 精通网页渲染流程、JS 执行机制、浏览器网络请求架构、DOM/BOM 底层逻辑

> `[jobRequire:s04]` 熟悉浏览器内核源码调试与问题攻坚

> `[jobRequire:s06]` 深入掌握全网主流风控机制

这些是候选人资格要求，而非职责文本；但当前确定性词典并未为该正文提供任何 verified 命中。

## 3. Plus 的保存结论（未人工修正）


| 字段                              | 模型结论                                                           | 能否通过当前契约                           |
| ------------------------------- | -------------------------------------------------------------- | ---------------------------------- |
| `technology_requirement_groups` | 一个 `qualification/required/at_least/1` 组，列出 Chromium、Web 引擎等多项 | 否；options 不在空的 verified 列表中。       |
| `mention_evidence_ids`          | 对各 option 使用 `jobRequire:sNN`                                  | 否；这是 `span_id`，不是技术命中 evidence ID。 |
| `candidate_mentions`            | 输出 3 个 Chromium/内核相关候选                                         | 候选的词义可单独审阅，但不能使上面的正式技术组选项合法。       |
| 经验与学历                           | 回复中未给出可通过当前失败门的可持久化结果                                          | 不应因为技术项失败而推断其为“不满足”。               |




## 4. 提示词相关片段

> options 只能使用 `verified_technology_mentions` 中已有的 `technology_key`；词典外技术放 `candidate_mentions`，绝不伪造 `technology_key`。

> 只引用 INPUT 中存在的 `span_id` 和 `mention_evidence_id`；技术选项还必须引用对应的 `mention_evidence_id`。

这里并非提示词没有表达规则，而是模型没有遵守“空 verified 列表意味着不得产生正式 option”的直接后果。
