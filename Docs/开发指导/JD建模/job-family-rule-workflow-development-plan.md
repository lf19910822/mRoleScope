# JD岗位族建模：传统工作流开发计划

日期：2026-10-28 目标项目：程序&技术社招JD BI 性质：开发计划与词典建议稿，尚未修改生产代码、数据或正式规则。本文已记录当前已裁决的标题匹配、计数与主岗位族口径；仍须通过 OpenSpec 与 TDD 才能进入实现。

## 1. 开发目标与范围

为当前只有“程序&技术类”官方大类的JD补充可解释的分析岗位族，支持后续“岗位族×技术关键词”热力图、岗位结构图和筛选。

首期仅对官方顶层分类为“程序&技术类”的岗位执行岗位族建模。未来同步范围若包含其他官方大类，则其岗位标记为 `out_of_scope`，不产生主岗位族，且不计入技术岗位的 `unclassified` 词典覆盖率。官方顶层分类缺失或无法识别时为 `scope_unknown`，同样不从标题猜测范围归属、不产生主岗位族，且不计入任何岗位族覆盖率，待源数据修复后再处理。

首期采用固定流程、人工维护词典、确定性匹配与人工复核，不调用AI分类，不使用Embedding、向量相似度、模型置信度或动态Agent。原始官方类别保持不变，新增分析岗位族不能冒充公司部门或官方细分类别。

每份 JD 都计算各岗位族的命中次数，并且最多产生一个正式主岗位族。命中次数最大的岗位族即为主岗位族；若最高次数并列，取标题中最后结束的有效命中所属岗位族；若结束位置仍相同，才取内部 `family_key` 按字典序最靠前者。

有效标题没有命中时为 `unclassified`；标题为空、仅空白或无法按既定规则规范化时为 `invalid_title`。后者是源数据质量问题，不计入词典的 `unclassified` 覆盖率，待标题修复后重算。不设辅助方向标签、人工猜测的“其他”或冲突状态；多岗位族命中本身保留为可审计计数，不改变唯一主岗位族。

首期分类输入仅为岗位标题历史中的规范标题字段及人工维护的项目词典，避免扩大正文处理范围。不得拼接项目名、地点、职级等元数据；标题缺失时也不得用JD正文、岗位描述或AI输出兜底。三块正文仍服务现有技术、年限、学历处理。人工复核只决定新增或调整下一版词典规则，不能为单个标题写入主岗位族覆盖值；正文辅助规则如确有价值，再作为独立版本增加。

本任务完成岗位族数据能力即可，不同时承诺实现热力图、修改既有AI分析或重构采集系统。

## 2. 事实依据与初期工作量

公开接口的competencyTypeId=1、competencyType=程序&技术类仅支持大类，分类接口也未提供客户端、后端、算法等内部细分。

2026-10-28本次只读列表探测返回171个唯一岗位。仅在内存中扫描标题，输出聚合，不保存本次标题、岗位ID或JD正文。观察到的词面命中包括：客户端51、构建7、引擎开发9、渲染6、服务器开发6、后端4、网关6、算法15、研究员13、平台12、运维14、SRE5、安全8、测试2、爬虫2、外包管理1等。

这些数量可重叠，不是分类结果，不可相加为171；例如“客户端工具开发（构建方向）”同时包含客户端和构建。AI命中31、Agent命中6、LLM命中10也不能直接转换成算法岗位数。

现有数据事实报告中的当前开放可见期和来源列表可以不同；本任务覆盖率应采用系统既定的当前开放总体，并以正式远端聚合为准，不能把本次探测列表数替换为当前开放数。

## 3. 推荐主岗位族

当前 V3 采用 15 类稳定岗位族，另设 `unclassified` 状态。内部 ID 稳定，展示名可修改。分类数量不是硬性目标，如评估后某类无区分价值可合并并记录词典版本。


| `family_key`（仅用于完全相同位置的最终兜底） | 展示名称 | 覆盖工作对象 |
| --- | --- | --- |
| `ai_algorithm` | AI 算法 | 明确以模型训练、后训练、评测、模型研究或推荐算法改进模型能力为工作主体 |
| `ai_application` | AI 应用 | 明确把模型、Agent 或生成能力交付给业务、生产或用户可用功能 |
| `algorithm_research` | 算法与研究 | 未具备 AI 模型复合信号的泛算法、生成算法与研究工作 |
| `backend` | 后端 | 后端、后台、服务端、服务器、全栈及相应应用开发 |
| `client` | 游戏客户端 | 客户端系统、玩法、战斗、关卡、3C、联机客户端 |
| `data_engineering` | 数据工程 | 数仓、ETL、数据平台的数据开发、爬虫数据采集 |
| `engineering_management` | 研发管理与外包协作 | 明确以外包管理、交付或研发管理为工作主体 |
| `engine_systems` | 游戏引擎 | 游戏引擎、渲染、图形 API、浏览器内核、底层运行时 |
| `frontend` | 前端 | Web 或应用界面的前端开发；不与游戏客户端混同 |
| `hardware_embedded` | 硬件与嵌入式 | 硬件结构、嵌入式软件、电子/结构设计 |
| `operations_sre` | 运维 | SRE、运维开发、NOC、虚拟化运维与基础网络运维 |
| `platform_infra` | 平台与 AI 基础设施 | 训练/推理平台、资源调度、推理系统、算子与计算基础设施 |
| `security` | 安全研发 | 客户端安全、白盒安全、漏洞、反入侵、攻防团队 |
| `testing_quality` | 测试 | 测试开发、技术美术测试、性能与硬件测试 |
| `toolchain` | 研发工具 | 编辑器、内容工具、构建打包、集成与交付管线 |


“专家、资深、负责人”不单独决定岗位族。算法负责人仍可归算法，安全负责人归安全；是否带团队可作为辅助信息。hardware_embedded体现当前官方大类确实含硬件岗位，不能为了软件BI方便将其丢弃。

## 4. 固定工作流

远端读取当前标题身份与版本 → 受控标题规范化 → 标记项目后缀等非岗位片段 → 词典别名匹配与同族重叠去重 → 按岗位族累计命中数及最后命中位置 → 最高命中数选唯一主岗位族（并列取标题中最后结束的命中；仍相同才按 `family_key`）或 `unclassified` → 保存版本化结果与理由 → 远端质量汇总与人工复核 → 聚合接口供图表使用。

规范化建议限制为：Unicode规范化方案明确固定、统一可接受空白、显式大小写策略。保留原文和定位关系，不随意删除全部括号或所有连字符后的内容。

已知项目名称由项目词典定位后，可在分类扫描视图中屏蔽对应片段，防止“-AI引擎”把全栈岗位误判引擎。仅屏蔽已确认的**完整项目名称**，按规范化后的精确词面定位，不按“第一个连字符之后全部丢弃”；LLM Post-train等名称本身就有连字符。项目词典不得以“引擎”“平台”“客户端”等通用岗位或技术词作为可屏蔽别名：例如确认“AI引擎”为项目名时可屏蔽该完整片段，但不能因此屏蔽“游戏引擎开发”中的“引擎”。

无需新增外部工作流平台，优先复用现有Go pending pipeline、PostgreSQL和词典发布/复算机制。

首次上线时，对全部历史中当时属于“程序&技术类”的岗位执行一次确定性岗位族建模。日常同步只处理新增标题、标题变化的岗位，以及新进入“程序&技术类”范围的岗位；岗位关闭、地点等无关字段变化只更新每日状态，不重新解析。词典、解析器或项目词典发布新版时，依照 6.7 对历史标题全量重算。以上流程均不调用AI，并按逐岗位最大努力原则运行：已成功的结果立即交付；数据质量状态或单个岗位的意外处理失败只影响该岗位并进入独立重试，不阻断其他岗位、日常同步或其他并行工作。

## 5. 收敛匹配词典：别名映射

词典条目应为“别名 → 一个 `family_key`”的简单、版本化映射；同一个完整字面别名不得映射到多个岗位族，不把同义表达重复登记为彼此独立的细分类。若有不同含义，只能登记更具体的复合别名，不能依赖上下文猜测。首期仅按词典逐条列出的明确字面别名匹配，不使用正则、模糊匹配、自动词形扩展或其他泛化规则。下表是首版的收敛边界；列出的词只代表标题命中线索，不声称每个写法已在当前样本出现。首期以映射表和本计划已裁决的匹配、计数边界为准，不额外建立逐别名的样例准入、候选清单或回归测试流程；这些治理规范留待后续词典规模扩大时再设计。

| `family_key` | 首期收敛别名 / 词面候选 |
| --- | --- |
| `algorithm_research` | 算法、模型研究、研究科学家、预训练、后训练、生成算法、模型评测 |
| `backend` | **后端、后台、服务端、服务器、全栈**；游戏服务器、网关、API 网关、AI 网关、推理网关、AI 应用、Agent 开发 |
| `client` | 游戏客户端、客户端、Gameplay、游戏玩法、战斗客户端、关卡客户端、3C、联机客户端 |
| `data_engineering` | 数据开发、大数据、数据工程、数仓、数据仓库、ETL、实时计算、爬虫、数据采集 |
| `engineering_management` | 研发外包、游戏外包、外包管理、外包经理、研发项目管理、技术项目经理、研发交付 |
| `engine_systems` | 游戏引擎、引擎、渲染、图形、图形 API、浏览器内核、运行时 |
| `frontend` | 前端、前端开发、前端工程师 |
| `hardware_embedded` | 嵌入式、固件、单片机、硬件、电子工程、硬件结构、结构工程 |
| `operations_sre` | 运维、SRE、NOC、虚拟化运维、服务器运维、GPU 运维、集群运维、存储运维、网络运维、AIOps |
| `platform_infra` | 训练平台、推理平台、训推平台、模型平台、AI 基础设施、AI 存储、高性能算子、推理系统、训练系统、K8s 调度、Kubernetes 平台、RL Infra |
| `security` | 安全、反入侵、漏洞挖掘、客户端安全、白盒扫描、反作弊、攻防、逆向安全、渗透测试 |
| `testing_quality` | 测试、测试开发、技术美术测试、硬件测试、性能测试、自动化测试、软件测试、质量保障 |
| `toolchain` | 工具开发、客户端工具、构建、编辑器、研发工具、工具链、打包、构建管线、资源制作工具、DCC 插件 |

首版中，`AI`、`平台`、`网络`、`开发`、`工程师`等脱离组合语义后过宽的词不作为单独别名启用。英文别名采用大小写不敏感、ASCII 标识符边界匹配；中文别名只要以连续字面片段出现在标题中即命中，不要求中文分词或独立成词。同一岗位族的重叠别名仍依 6.2 去重。已裁决的 V2 例外及其边界见下节。

### 5.1 已裁决的 V2 词典修订（2026-10-29）

V2 保持 13 个稳定 `family_key` 与既有匹配、掩蔽和主岗位族规则不变，只增加下列审核别名。V1 资产及其历史结果不可变保留；当前解析器切换至 V2 后，以词典版本和摘要变化触发现有 provider-free pending 流程的历史重算。

| `family_key` | V2 新增别名 | 规则边界 |
| --- | --- | --- |
| `algorithm_research` | `Posttrain`、`搜推`、`搜推AI` | `Posttrain` 大小写不敏感且有 ASCII 标识符边界。`搜推AI` 用于保留“搜推AI”标题的算法主岗位族，同时仍保留平台 `AI` 命中。 |
| `backend` | `数据库`、`Agent开发`、`Agent研发` | 后两个别名大小写不敏感且有 ASCII 标识符边界；它们与平台 `agent` 可同时命中，按既定最长/末位置规则仍使明确 Agent 开发或研发为后端主岗位族。 |
| `data_engineering` | `数据处理` | 按审核决定将标题中的数据处理归为数据工程。 |
| `operations_sre` | `网络工程师`、`k8s`、`Kubernetes` | 后两个别名大小写不敏感且有 ASCII 标识符边界。 |
| `platform_infra` | `AI`、`agent`、`大模型`、`推理优化`、`云原生`、`MaaS` | `AI`、`agent`、`MaaS` 大小写不敏感且有 ASCII 标识符边界；其余为连续字面匹配。 |

`AI` 与 `agent` 是 V2 经审计明确批准的平台与 AI 基础设施词，不应再按首版的泛词规则拒绝；但其 ASCII 标识符边界必须保留，因而 `AI` 不得在 `AIOps` 的前缀中产生平台命中。`K8S云原生开发`会同时得到运维 `k8s` 与平台 `云原生` 命中，后者位置更靠后，故主岗位族为 `platform_infra`。`云游戏技术专家`只有行业领域，没有已批准的职能词，V2 继续返回 `unclassified`，不新增“云游戏”岗位族或别名。

### 5.2 已裁决的 V3 词典修订（2026-10-30）

V3 新增两个稳定岗位族 `ai_algorithm`（AI 算法）和 `ai_application`（AI
应用）。它们是可与现有岗位族并行命中的标题事实，而不是互斥部门或展示
标签。当前完整词典、每个启用别名及 ASCII 边界设置以
[`岗位族词典_latest.md`](岗位族词典_latest.md) 为唯一可读维护入口；运行时
资产为 `job_family_dictionary_v3.json`。V1/V2 资产及历史结果保持不可变。

| V2 所有者 | V3 所有者 | 审核通过的迁移别名 |
| --- | --- | --- |
| `algorithm_research` | `ai_algorithm` | `模型研究`、`预训练`、`后训练`、`模型评测`、`Posttrain`、`搜推AI` |
| `backend` | `ai_application` | `AI 应用`、`Agent 开发`、`Agent开发`、`Agent研发` |

V3 另外启用审核通过的 LLM 训练/评测、多模态、虚拟人、推荐算法、AI 全栈、

中英混合已审核拼写分别列出。`LLM Post-train 算法`与
`LLM Posttrain 算法`是已裁决“带空格和不带空格的中英混合写法都列出”的
空格变体，并未扩展语义。

不能把裸 `AI`、`LLM`、`大模型`、`Agent`、`AIGC`、`RAG`、`MCP`、`Prompt`
或`工作流`单独归入新岗位族。`AI`、`agent`和`大模型`仍是
`platform_infra` 的既有宽信号；其余词也不会仅因出现在标题中形成新岗位族。
`大模型平台开发工程师`和`AI Agent引擎系统开发工程师`因此保留平台/系统
边界，`云游戏技术专家`继续是 `unclassified`。首期不新增按岗位族加权或
优先级覆盖：仍按 6.1 的次数、最后结束位置、`family_key` 顺序选唯一主岗位族。

## 6. 计数、主岗位族与边界规则

### 6.1 结果口径

每个标题的版本化结果至少包含：

| 字段 | 规则 |
| --- | --- |
| `family_match_counts` | 每个命中的 `family_key` 与其非负整数命中次数；可包含多个岗位族 |
| `primary_family_key` | 仅当至少一个岗位族有命中时存在；取最高次数，若并列则取标题中最后结束的有效命中；结束位置仍相同才取 `family_key` 字典序第一项 |
| `status` | 官方分类明确为范围外时为 `out_of_scope`；官方分类缺失或无法识别时为 `scope_unknown`；范围内且有主岗位族为 `classified`；范围内有效标题没有任何命中为 `unclassified`；范围内标题为空、仅空白或无法规范化为 `invalid_title` |

例如，某标题得到 `backend: 2`、`operations_sre: 1` 时，主岗位族为 `backend`。标题“服务端运维”得到 `backend: 1`、`operations_sre: 1`；“运维”的有效命中在“服务端”之后结束，因此主岗位族为 `operations_sre`。

只有两个并列岗位族的最后有效命中结束位置也相同，才以 `family_key` 字典序解决该最终平局。并列不是错误，也不产生第二个主岗位族。

### 6.2 命中次数

1. 同一别名在标题中每个彼此不重叠的位置最多计一次；同一岗位族在不同位置命中可以累计。
2. 只有**同一岗位族**的多个别名覆盖相同字符位置时，才只保留最长别名。长度相同的同族别名任选一个即可，因为它们都只贡献该岗位族的 1 次命中。例如“后端开发”不会同时以“后端开发”和“后端”为 `backend` 记成两次。
3. **不同岗位族**即使别名字符位置重叠，也分别计数，不能因词更长而互相压制。例如“客户端安全开发”记录 `client: 1` 与 `security: 1`；它们并列时，取标题中最后结束的有效命中所属岗位族。首期不设能覆盖跨岗位族命中的“专属短语”例外。
4. 项目词典已确认的完整项目名称先按规范化后的精确词面屏蔽，再执行岗位族扫描；屏蔽只作用于该项目名称本身，不删除连字符后的整段标题。通用岗位或技术词不得作为项目别名而被屏蔽。
5. 正式输入仅为规范化标题和已确认项目片段位置；不读取 JD 正文、不以技术词、来源 `projectName`/`objectName`、AI 输出或相似岗位反推岗位族。

### 6.3 版本身份与增量重算

岗位族结果的身份由“规范化标题、岗位族解析器/词典版本、项目词典版本”共同确定。仅在下列任一项变化时重算：

1. 规范化标题变化；
2. 岗位族解析器或岗位族词典版本变化；
3. 用于定位并屏蔽项目名称的项目词典版本变化。

地点、工作性质、来源 `projectName`/`objectName` 等不参与岗位族判断的元数据变化，不触发重算。官方顶层分类变化不改变标题的词典解析身份，但必须更新该岗位在相应日期是否属于本模型范围：变为“程序&技术类”时纳入解析，变为 `out_of_scope` 或 `scope_unknown` 时不产生当前范围内的岗位族结果。这样日常同步仅处理受影响的岗位；项目词典变化仍能使扫描输入发生变化的标题得到统一重算。

### 6.4 岗位生命周期与历史保留

岗位族结果附着于标题身份，而不是当前是否开放。岗位关闭、重新开放以及地点等非标题元数据变化，只改变岗位在相应日期是否可见，不删除或重算既有岗位族结果。若同一岗位后续改标题，旧标题结果保留给该标题有效期间的历史快照；新标题作为新身份按本计划重新解析。

### 6.5 意外处理失败、审计与重试

若某个来源元数据版本建立岗位族观察记录时发生意外失败，该来源版本保留仅引用来源版本、规则版本、固定失败原因和处理时间的审计信息，进入独立待重试队列；它不阻断其他岗位的处理。若岗位已改标题而新标题的解析发生意外失败，旧标题的岗位族结果仅保留给旧标题有效期间的历史快照，不得作为新标题的当前岗位族结果。新标题保留与其标题身份、规则版本、失败原因和处理时间有关的审计信息，进入独立待重试队列；同样不阻断其他岗位。

岗位族审计不重复保存标题文本或JD正文，而是引用既有岗位与标题历史。审计至少记录岗位族词典、解析器和项目词典版本，`family_match_counts`、主岗位族或状态、命中的别名与位置，以及处理时间、失败原因和重试事件；据此可结合标题历史复核任一结果。

人工处理可以修复源标题、发布词典修订或触发重试，但不能为某个标题直接写入主岗位族覆盖值。

### 6.6 词典升级

每一版岗位族解析结果均须保留，供审计和回溯。发布新的岗位族词典、解析器或项目词典版本后，应对全部历史标题统一重算该版本的结果。

图表的统计口径、版本选择和呈现规则不属于本期岗位族建模；后续图表变更必须单独定义其时间、可见性和版本口径。本期只保留可重算、不可变的岗位族事实，且不阻止已经成功的逐岗位结果被保存、交付或用于其他处理。
