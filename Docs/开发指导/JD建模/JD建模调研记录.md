## 1. 调研目标与边界

本调研的目标是为米哈游“程序&技术”社会招聘 JD 建立可重复、可追溯、可评估的结构化分析能力，为后续筛选、聚合统计和图表提供可信数据基础。

本调研不实施代码、数据库迁移、定时器或云端配置变更。形成足够明确的设计后，另行进入 OpenSpec proposal，再决定是否实施。

### 1.1 数据与安全边界（已确认）

- 后续设计和验收以 CVM/COS 中的**当前 164 份真实 JD**为准；此前 159 份旧快照只作讨论参考。
- 真实 JD、原文证据和可还原原文的 Diff 只在 CVM/COS 的受控环境处理。
- 本地开发机和 Git 仓库只使用合成测试数据、规则、词典、字段定义以及不含原文的汇总结果。
- 不将完整 JD、真实片段、原始响应或含正文的日志输出到本地、Git、GitHub Actions 日志或聊天记录。
- 分析结果不能替代私有 COS 中的原始证据归档。

### 1.2 角色与资料定位（已确认）

- 《[JD 标签拆分：开发建议](jd-tagging-development-proposal.md)》由大计划守护者提供，是高价值的总体设计建议，不是可不经核验直接执行的实施指令。
- 大计划守护者掌握项目最终目的与验收标准；当前工程的字段映射、数据库行为和运行限制仍须由开发者核实。
- 遇到语义、范围、验收口径或总体目标存在不确定性时，应整理出具体问题，以尊重的方式请大计划守护者确认。
- 面向大计划守护者的每轮问题应先说明业务影响，再用通俗示例或类比解释选项；技术术语只作为括号中的实现映射，且每轮只请求确认一个决定。

## 2. 已核实的当前工程事实

### 2.1 接口字段探测

2026-10-22 对公开接口做过一次只在内存中进行的探测：请求一条列表项及其对应详情，仅输出字段名与类型，不保存响应、不输出岗位 ID、名称、地点或 JD 正文。

已确认的直接结构化字段包括：

- 稳定来源岗位 ID：`id`；
- 名称：`title`；
- 地点数组：`addressDetailList[]`，当前样本元素包含 `addressId`、`addressDetail`；
- 官方类别：`competencyType`、`competencyTypeId`；
- 工作性质：`jobNature`、`jobNatureId`；
- 招聘类型：`hireType`、`hireTypeName`；
- 项目/来源分组候选：`projectId`、`projectName`、`objectId`、`objectName`；
- 状态/标识：`status`、`hurry`、`hadDelivery`、`channelDetailIds`；
- 标签候选：`tagList`（本次样本为空，尚未确认元素结构）。

文本字段包括 `jobSummary`、`description`、`jobRequire`、`addition`、`deliveryInstructions`。从文本抽取技能、年限、学历和职责关系属于后续解析工作，不能视为来源直接事实。

本次只覆盖一个样本；字段的可选性、`tagList` 非空结构及枚举值语义仍需在受控远端环境用汇总方式验证。

### 2.2 当前同步的存储与版本行为

| 信息 | 当前行为 |
| --- | --- |
| 岗位身份 | `jobs` 以 `(source_company, source_job_id)` 唯一识别岗位。 |
| 原始证据 | 每个成功同步批次的完整列表与详情响应归档至私有 COS，可按运行批次重算。 |
| 数据库原字段 | `jd_versions.raw_fields` 保存每个 JD 内容版本的一份详情 `data` 对象。 |
| 规范化展示内容 | `jd_versions.display_text` 当前保存 `title`、`locations`、`category`、`nature`、`project`、`description`、`requirements`、`additional`。 |
| 当前内容哈希 | 覆盖上述规范化展示内容；内容不变时复用同一 `jd_version`。 |
| 可见历史 | `job_presence_periods` 记录岗位出现、消失和重新出现。 |
| 内容历史 | `job_content_periods` 记录当前内容哈希覆盖字段发生变化的时间段。 |

重要限制：`code`、`competencyTypeId`、`jobNatureId`、`hireType`、`status`、`hurry`、`hadDelivery`、`channelDetailIds`、`objectId`、`objectName`、`tagList`、`jobSummary`、`deliveryInstructions` 等字段目前主要仅存在于 `raw_fields` 或 COS 原始证据中。若只有这些字段发生变化，当前实现不会创建新的 JD 内容版本，也不会更新既有版本的 `raw_fields`。不过，由于每个成功批次均归档至 COS，仍可在远端重算其历史值。

### 2.3 已发现的语义不一致

当前实现中存在以下需要在设计阶段处理的差异：

- `locations` 目前只保存排序、去重后的地点文本，未保留独立地点 ID 作为可筛选的结构化维度；
- `hireTypeName` 与 `jobNature` 被收敛到单个 `nature` 展示字段，不能表达二者各自的变化；
- `projectName` 当前写入 `project` 并纳入内容哈希，但当前实测/历史样本显示它可能只是“社会招聘”这样的招聘标签，不能未经验证解释为游戏项目或业务项目；
- `tagList` 在本次样本为空，尚没有证据支持其结构、稳定性或业务含义；
- `status` 等枚举字段已存在，但其来源语义尚未核验，不能直接驱动业务展示或岗位关闭判断。

## 3. 讨论记录

### Round 1 — 2026-10-22 — 阅读大计划守护者的初始建议

**输入资料**：`jd-tagging-development-proposal.md`。

**大计划守护者的主要建议**：

1. 先将来源直接事实、正文解析标签和跨期计算指标分层；不要把所有内容塞进单一通用标签表。
2. 接口直接字段优先于正文推断；发生冲突时记录冲突，不静默覆盖。
3. 解析结果应关联 JD 内容版本、原文依据、来源字段、上下文角色、要求属性、条件关系、处理来源、规则/词典版本和复核状态。
4. 技能、年限、学历、岗位族与生产经验适合分维度建模；“未提及”“解析失败”“歧义”“明确不限”不可混为同一空值。
5. AI 可以辅助复杂分类，但不应成为首版依赖；模型输出同样要有证据、版本与复核状态。
6. 首轮应先支撑可验证的基础字段与解析能力；图表、个人匹配、薪资/人数/工时推测不属于本期。

**当前工程对照结论**：

- 总体目标与现有同步、SCD2、COS 证据归档和审计模型相容；
- 当前真实基线为 164 份 JD，旧建议引用的 159 份快照不能作为现行数据结论；
- 真实 JD 的质量核查和证据回溯必须在 CVM/COS 内完成，本地不能保存原文；
- 同步当前已覆盖部分基础字段，但尚未将全部应追踪的来源事实独立建模。

**本轮结论**：接受“先确定基础字段版本边界，再做最小解析切片”的总体方向；不进入实施。

### Round 2 — 2026-10-22 — 大计划守护者对实施切分的反馈

**已确认的取舍**：

1. “独立可筛选”与“纳入版本变化判断”是两个独立决定。
2. 公司/来源与岗位 ID 是稳定身份；名称、地点集合、官方类别及编码、工作性质及编码、紧急标记、招聘类型和正文分区应按各自业务含义保存并决定是否追踪变化。
3. `projectName`、`objectName` 等含义未确认的字段先保留为来源事实，暂不解释为业务项目维度。
4. `raw_fields` 可以完整保留，但整个 JSON 的差异不能直接视为岗位业务变化；应区分业务内容、运输/排序噪声与未知字段。
5. 首个交付切片限定为**技术关键词提及提取**：标准技术名、原始写法、来源字段、出现位置、同 JD 去重、多处证据、词典与解析器版本。
6. 首版只称“技术提及”，不称“必需技能”；不解析任选关系，不把三个可选技术误计为三项硬性要求。
7. 年限、学历、任选关系和岗位族不纳入首个切片。
8. 证据、JD 内容版本、分析运行/规则版本、人工复核记录必须分别保存；人工复核不覆写自动结果，也不自动继承到新 JD/规则版本。

**对当前工程的直接影响**：

- 成功批次的 COS 原始归档已经回答了“未纳入 SCD2 的字段能否还原历史”的问题：可以在远端按批次重算；
- 数据库中的 `raw_fields` 不能作为此类字段逐运行历史的唯一依据；
- 在技术提及解析之前，需要先设计并调整基础字段的独立保存与版本边界；
- 不应把当前 `display_text.project` 当作已经确认的游戏项目归属。

**仍为建议、尚未确认的实施细节**：

- 未知字段值变化是否仅记作接口观察，或需要保留可查询的值变化记录；
- 证据定位的坐标规范；
- 哪些文本分区应进入首轮技术词扫描。

### Round 3 — 2026-10-22 — 开发侧建议，等待确认

**建议的实施顺序（未确认）**：

```text
来源字段版本边界
        |
        v
技术词典与版本
        |
        v
JD 内容版本上的技术提及提取
        |
        v
远端证据核查与质量汇总
```

**建议的证据最小引用**：

```text
JD 内容版本
  + 来源字段（例如 description / jobRequire）
  + 规范化文本中的 [start, end) 位置
  + 定位/规范化规则版本
  + 技术词典与解析器版本
```

建议位置采用 Unicode 码点区间 `[start, end)`，而非 UTF-8 字节偏移。理由是中文展示、人工复核和跨语言实现更易一致。定位对象应是远端已保存或可确定重建的规范化文本；不能将清洗文本的位置直接套到原始 HTML。

**待请大计划守护者确认的问题**：

1. `jobSummary` 是否纳入首轮技术词扫描？它目前存在于来源详情 JSON，但不属于当前 `display_text` 的规范化展示正文。纳入会扩大“基础字段版本边界”调整范围；不纳入可先从 `description`、`jobRequire`、`addition` 建立闭环。
2. 对未知来源字段变化，首期应只记录字段结构（字段名与类型）变化，还是也记录值变化但明确不解释为业务变更？前者成本低且更保守；后者有助于日后回溯但会增加存储与噪声处理需求。

### Round 4 — 2026-10-22 — 请求大计划守护者确认：首轮文本范围

**问题**：`jobSummary` 是否纳入首轮技术关键词提及扫描？

**已知事实**：`jobSummary` 存在于来源详情 JSON，但不在当前规范化 `display_text` 中；`description`、`jobRequire`、`addition` 已有稳定的规范化展示字段。无论是否纳入，完整来源证据均已按成功运行批次归档至私有 COS。

**推荐**：首轮仅扫描 `description`、`jobRequire`、`addition`，不扫描 `jobSummary`。这样可先验证“JD 内容版本 → 技术提及 → 远端证据 → 质量汇总”的完整链路，而不扩大当前基础字段版本边界。后续如证实 `jobSummary` 提供独特且有价值的技术信息，可作为可追溯的第二批输入字段加入；既有 COS 归档允许届时重算。

**备选**：首轮同时扫描 `jobSummary`。优点是可能提高提及覆盖率；代价是需要先确定该字段的版本语义、展示/证据定位文本和去重规则，扩大最小切片。

**大计划守护者回复（已确认）**：首轮不扫描 `jobSummary`。该字段可能包含有价值的技术信息，但首轮应先将已经纳入 JD 内容版本的三个字段处理可靠，以便验证证据定位和历史重算链路。

**确认的口径**：

- 首轮指标全称为“**职责、任职要求及补充说明中的技术提及**”。
- 首轮不声称覆盖全部来源文本，也不声称代表所有技术信息。
- 原始 `jobSummary` 继续作为成功运行批次的一部分保留在私有 COS。
- 后续应在远端评估 `jobSummary` 对技术提及的增量覆盖价值；只有确认值得纳入时才扩展输入字段。
- 扩展输入字段时必须升级解析口径/版本，并以新版口径重算历史；不得把口径扩大造成的计数变化误读为技术热度增长。

**受影响范围**：首轮证据定位只需要覆盖 `description`、`jobRequire`、`addition` 三个已经规范化的来源分区。`jobSummary` 不丢失，后续仍可依据 COS 原始证据重新分析。

**状态**：已确认。

### Round 5 — 2026-10-22 — 请求大计划守护者确认：未知字段变化的首期观察策略

**问题**：对于尚未赋予业务语义的来源字段（例如未来出现的新字段、未确认用途的字段），首期应只记录字段结构变化，还是也记录逐值变化？

**推荐**：首期只记录字段结构变化，即字段名、JSON 类型、是否出现、数组元素类型/对象键集合等接口契约信息；不在 PostgreSQL 额外记录未知字段的逐值变化。

**理由**：每个成功批次的完整原始响应已经保留在私有 COS，逐值历史可在远端日后重算。立即把未知字段值变化持久化会重复 COS 证据、增加噪声和存储，却不能在字段语义不明时产生可靠业务解释。结构变化则可以及早发现接口契约漂移，直接保护采集与解析链路。

**备选**：同时记录未知字段的值变化，但明确不解释为业务变更。优点是后续调查更直接；代价是需要定义脱敏、哈希、字段白名单和噪声过滤策略，超出技术提及最小切片。

**大计划守护者回复（已确认）**：首期不仅观察字段结构，也记录远端的聚合取值分布。类型不变但出现新枚举值、空值率突增或来源标签覆盖率显著变化，均可能影响后续处理；这些变化必须与“职责/要求变化”分开记录。

**已确认的字段定位**：

| 字段 | 首期定位与边界 |
| --- | --- |
| `projectId` / `projectName` | 命名为 `source_project_id/name` 的来源招聘项目/分类元数据，不解释为游戏项目；可记录来源元数据变化，但不用于业务项目图表。 |
| `objectId` / `objectName` | 保留来源 ID/名称对及缺失状态；正式业务定义和长期稳定性未证实，不建立组织、团队或招聘主体筛选。 |
| `tagList` | 作为 `source_tags` 保留；来源标签与解析得到的 `extracted_skills` 必须分开。首轮不把来源标签混入技术提及统计。 |
| `status` | 保存原始状态码及其分布；不存在完整官方枚举证据，不得用于岗位关闭/消失判断。 |
| `hadDelivery` | 疑似访问者相关状态；排除出岗位事实、标签及任何内容版本变化判断。 |
| `channelDetailIds` | 作为采集范围和来源渠道证据保存；比较岗位增减时请求范围必须保持不变，不解释编号含义或作为求职筛选条件。 |
| `code` | 保留原值；没有稳定、有效业务编码的证据，不作为主键、去重键或备用身份。 |

**范围控制**：完整原始响应继续归档至 COS。字段的结构和聚合分布变化可形成单独的来源接口/元数据观察记录；逐岗位未知字段值的完整历史仍以 COS 原始证据为准，首期不复制为通用业务变更历史。

**状态**：已确认。

### Round 7 — 2026-10-22 — 请求大计划守护者确认：来源元数据版本与正文内容版本是否分离

**问题**：是否将“来源元数据变化”与“JD 正文内容变化”建模为两类独立版本？

**推荐**：分离为三层身份：

```text
稳定岗位身份
    |
    +-- 来源元数据版本
    |     标题、地点、官方类别/编码、工作性质/编码、紧急标记、
    |     招聘类型、source_project、object、source_tags、状态和渠道证据
    |
    +-- 正文内容版本
    |     description、jobRequire、addition 的规范化文本
    |
    +-- 分析运行/规则版本
          技术提及结果、词典与解析器版本、人工复核
```

每个成功运行中的岗位观察关联当时的来源元数据版本和正文内容版本。来源元数据单独变化时，记录来源元数据变更，但不声称职责/要求改变，也不必重跑正文技术提及解析；正文变化时才产生新的正文内容版本并触发解析。`hadDelivery` 不进入任何版本判断。

**理由**：这与已确认的“观察事实”和“业务解释”分离原则一致，也避免地点、标签或渠道变化被错误呈现为 JD 职责/要求修改，或无意义地重复同一正文的解析结果。

**备选**：沿用单一 JD 内容版本，将所有已追踪的来源字段并入同一个内容哈希。实现表面较少，但会混淆变更语义，并使元数据变化重复触发正文解析。

**大计划守护者回复（已确认）**：同意来源元数据版本、正文内容版本与分析运行/规则版本三层分离。但版本判定必须采用显式字段白名单；不能将必然或经常变化、却没有稳定业务含义的元数据（例如状态码、哈希值等）纳入版本哈希或更新判断，否则会徒增无意义版本。

**确认的版本原则**：

- 不以完整 `raw_fields` JSON、归档摘要、内容哈希、采集时间、排序字段、请求标识或传输字段作为版本比较对象；
- 来源元数据版本只比较经确认的、具有稳定业务价值的字段白名单；
- 正文内容版本只比较首轮规定的正文分区，不因来源元数据变化而重跑技术提及解析；
- 状态码、渠道返回值等未确认或运行态字段可保留为当次观察/聚合分布，但不自动产生岗位版本；
- `hadDelivery` 继续排除出岗位事实、版本和分析判断；
- 所有未纳入比较白名单的原始字段仍由 COS 完整批次归档保留，供远端追溯和未来重算。

**状态**：已确认；具体白名单待下一轮确认。

#### Round 8 补充 — 标题修改的历史表达（已确认）

大计划守护者确认：标题改名归入来源元数据版本，不触发正文技术提及解析。

这不表示标题改名不产生版本或不进入后续 JD 改动历史。相反：

- 同一稳定岗位 ID 的标题发生变化时，必须创建新的**来源元数据版本**；
- 该版本与前一版本的差异可被解释为“标题修改”；
- JD 改动历史图表应同时汇集岗位可见期变化、来源元数据版本变化和正文内容版本变化；

- 后续如需要性能优化，可由相邻版本差异在查询时推导“标题修改”事件，或建立可再生的投影；不要求首期额外维护一张会与版本历史重复的业务事件表。

### Round 9 — 2026-10-22 — 请求大计划守护者确认：来源空值与集合的比较契约


### Round 11 — 2026-10-22 — 请求大计划守护者确认：技术提及证据的坐标契约

**需要确认的业务决定（通俗表述）**：当系统说“这份 JD 提到了某项技术”时，我们是否应像在书页上做书签一样，记录它出现在哪个正文区块、对应哪一版正文、以及“从第几个字到第几个字前”？

**为什么需要它**：同一份 JD 可能在职责和任职要求两处都提到同一技术。我们既要把它算作“该岗位提及过一次”，又要能在远端复核时准确找到两处依据。由于真实正文不能离开 CVM/COS，位置书签比把原文片段复制到本地更安全。

**例子（仅为合成示例，不来自真实 JD）**：若一段文字为“熟悉 Go 和数据库”，系统命中“Go”时，记录“任职要求区块、这版正文、第 4 个字到第 6 个字前”。之后无论谁复核，都能回到同一版远端正文准确找到它；不是只留下一个无法说明出处的“Go”。

**推荐**：以人阅读的“字符位置”保存书签，而不是机器内部的“字节位置”。一个中文字符在人眼中是一个字，但在计算机存储中可能占多个字节；若记录字节位置，换一个工具查看就可能指到错误地方。技术实现采用 Unicode 码点半开区间 `[start, end)`，即“起点包含、终点不包含”。

**同时约定**：

- 书签只允许指向 `description`、`jobRequire`、`addition` 三个首期正文区块；
- 书签指向可在远端确定性重建的同一版规范化文本，不直接套到原始 HTML；
- 保存词典/规则与解析器版本，使日后能解释“当时为什么把这里识别为该技术”；
- 不以命中文字串作为唯一证据；如远端为复核临时展示片段，片段不得回流本地或输出到 CI、聊天和日志；
- 用含中文、英文、标点及相邻词的**合成文本**测试书签边界。

**本问题解锁**：多处命中证据的表结构、幂等写入、远端验收和合成测试。

**大计划守护者回复（已确认）**：确认首轮采用“来源字段 + 规范化文本版本 + Unicode 码点半开区间 `[start, end)`”定位技术提及证据，范围仅限 `description`、`jobRequire`、`addition`。

**确认的定位契约**：

- 每个来源字段各自从 `0` 开始计数；`[start, end)` 包含起点、不包含终点；
- 文本版本必须唯一确定实际用于匹配的文本：至少关联 JD 正文版本、规范化规则版本和该字段规范化文本的哈希，不能只保存规范化算法版本号；
- 先按固定规则规范化空白、换行、HTML 实体等内容，再匹配并生成坐标；坐标生成后，不再修改该版规范化文本；
- Unicode 码点不是等同于屏幕上“可见字符”的简单单位；组合字符和部分 Emoji 可能由多个码点组成。Go 不得直接存正则表达式返回的 UTF-8 字节索引；浏览器展示也不得把码点坐标直接用于 JavaScript 字符串切片；
- 远端验证必须检查 `0 ≤ start < end ≤ 该字段码点数`，并验证该区间实际匹配对应技术词或已登记别名；
- 同一技能在同一岗位正文中出现多次时，证据层保留每一组区间；只在岗位级统计时去重，不能提前丢失其他命中；
- 真实规范化文本、命中片段和复核证据均留在远端；本地、日志与错误堆栈仅可保留必要的标识、坐标、版本、计数和错误类型，不能夹带原文。

### Round 12 — 2026-10-22 — 请求大计划守护者确认：首轮技术词典的“宁少勿错”规则

**需要确认的业务决定（通俗表述）**：首轮是否采用“宁可暂时漏掉不确定的新词，也不把相似但不同的词误当成同一技术”的词典规则？

**为什么需要它**：技术词很容易长得相似。例如“Java”和“JavaScript”不是同一项技术；若系统只要看到“Java”几个字就标记为 Java，会把只提到 JavaScript 的岗位错误计入 Java。反过来，如果一个来源标签或新写法看起来像技术词，但还没有人工确认，直接自动纳入也会制造虚假的统计。

**例子（均为合成示例）**：词典若已明确登记“Golang”是“Go”的别名，则两种写法均可识别为 Go；但“JavaScript”不能因为包含“Java”就同时被记成 Java。一个尚未确认的新来源标签，先进入“待人工确认清单”，不直接产生任何技术提及。

**推荐**：

- 每个可识别技术必须有人工确认的标准名称、允许的原始写法/别名，以及匹配边界规则；
- 首轮只做词典中的精确规则匹配，不做模糊匹配、自动同义词推断或 AI 猜测；
- 英文和符号类词按明确边界规则匹配，避免子串误命中；中文词仅匹配登记的完整词组；
- 出现未登记或无法安全判定的候选时，仅在远端形成脱离正文的候选/错误类型汇总，等待人工决定是否加入下一版词典；

**备选**：允许模糊或包含式匹配，以提高首轮覆盖率。它会明显增加误报，且难以在不暴露原文的前提下解释和复核；不推荐。

**本问题解锁**：词典条目模型、匹配器边界测试、候选词人工确认流程及词典更新后的重算语义。

**项目负责人确认**：同意首轮采用“宁少勿错”的技术词典规则。

**确认的词典边界**：

- 词典条目、别名或边界规则变动时，生成新的词典版本并重算历史正文；分析时需区分“规则覆盖扩大”与真实岗位需求变化。

### Round 13 — 2026-10-22 — 请求大计划守护者确认：首轮技术词的颗粒度

**需要确认的业务决定（通俗表述）**：首轮是否只统计“具体、可明确命名的技术”，暂不把宽泛方向词当作技术提及？

**为什么需要它**：用户看到“某技术被多少岗位提及”时，应该能理解统计的对象。像 Go、某个明确的引擎、某个数据库产品或具体工具，通常指向清晰；而“AI”“后端”“数据库”“云原生”更像方向或大类，可能包含很多完全不同的能力。把两者混在一张技术统计里，会让结果的口径不稳定。

**例子（均为合成示例）**：一句话提到“使用 Go 和 PostgreSQL”，可以分别记为两项具体技术；一句话只写“具备后端开发能力”或“了解数据库”，先不凭空推断它指向哪种语言或数据库。未来若做“AI 岗位”“后端方向”等图表，可另建岗位方向或能力主题模型，不能借用首轮技术提及的数字。

**推荐**：首轮词典只收录具有明确身份和边界的技术实体，例如编程语言、明确命名的框架/引擎、数据库/中间件产品以及基础设施工具；宽泛方向词仅可作为后续候选维度，不能与具体技术混合计数。

**备选**：同时把宽泛方向词纳入技术词典。覆盖看似更高，但会将“技术产品/语言”和“工作方向/能力概念”混为一谈，后续难以解释趋势；不推荐。

**本问题解锁**：首版词典的收录标准、词典分类字段和后续岗位方向模型的边界。

**项目负责人确认**：同意首轮只统计具体、可明确命名的技术。

**确认的技术词颗粒度**：

- 首轮词典仅收录身份和边界清晰的技术实体，例如编程语言、明确命名的框架/引擎、数据库/中间件产品和基础设施工具；
- “AI”“后端”“数据库”“云原生”等宽泛方向、能力概念或技术大类不生成首轮技术提及；
- 宽泛方向词可在远端作为后续岗位方向/能力主题建模的候选，但不能与具体技术共用统计口径；
- 因此首轮“技术提及”统计的每一项都必须能由词典中的具体标准技术名和远端证据说明。

**状态**：已确认。

### Round 14 — 2026-10-22 — 请求大计划守护者确认：首轮的人工复核最小闭环

**需要确认的业务决定（通俗表述）**：首轮是否需要像老师批改答卷一样，对一小批自动识别结果留下“正确、错误或暂不确定”的独立复核记录？

**为什么需要它**：自动识别结果即使有出处，也不等于已经正确。没有复核记录，我们只能知道系统找到了多少词，不能知道它把多少相似词看错，也无法判断下一版词典是否真的变好。与此同时，直接修改或删除机器结果会让我们失去“系统当时是怎样判断的”这一重要事实。

**例子（均为合成示例）**：系统把“Golang”识别为 Go，复核人可以标为“正确”；若系统误把“JavaScript”标为 Java，复核人标为“错误，并注明是边界误判”。机器的原始识别结果仍保留，复核结论作为单独的一张批改记录附在旁边。正文或证据片段始终只在远端查看。

**推荐**：首轮建立最小人工复核闭环，但不建设复核网页或复杂工作流：在远端对抽样结果保存独立的复核结论、错误类型、复核时间和规则/词典版本。复核记录不覆写自动结果，也不自动沿用到正文版本或词典版本变化后的新结果。

**备选**：首轮只看远端命中清单，不留下复核记录。实施较少，但无法形成可比较的质量基线，也难以追踪规则改善是否有效；不推荐。

**本问题解锁**：解析结果与人工复核记录的关联方式、首轮质量验收指标和后续词典改进闭环。

### Round 17 — 2026-10-22 — 请求大计划守护者确认：首轮结果何时算验收通过

**需要确认的业务决定（通俗表述）**：首轮不是“系统跑完”就算完成；是否应先在远端做一轮像抽检产品一样的人工验收，确认结果可信后才发布为可用版本？

**推荐的最小验收**：

1. 每个实际产生过命中的“可启用”词典条目，至少人工复核一条远端证据；
2. 对每个存在多处命中、相似词边界或版本号的高风险规则，额外复核边界案例；
3. 对正文不含任何技术命中的岗位，抽样复核，避免系统因异常而漏掉整段文本；
4. 所有已复核的误判、暂不确定和规则缺口都留下独立记录；不能通过静默删除结果“修好”；
5. 仅当坐标验证、幂等重跑、隐私检查和上述复核均通过时，才将该解析/词典版本标为可发布。

**例子（均为合成示例）**：若某规则命中了十个岗位，至少回看其中一条远端证据，确认它确实对应目标技术；若一个规则从未命中，则用合成文本测试它的边界，而不因此声称它已在真实数据上验证通过。

**备选**：只要程序无报错且有结果就发布。成本低，却无法证明“结果正确”，也无法为后续词典改进建立质量基线；不推荐。

**本问题解锁**：远端验收清单、质量报告字段、首版发布门禁和后续回归测试基线。

**项目负责人确认**：同意首轮采用远端人工抽检后的发布门槛。

**确认的首轮验收门槛**：

- 程序无报错或有输出不等同于验收通过；只有通过远端验证、人工复核和隐私检查的解析/词典版本才可发布；
- 每个实际产生过命中的可启用词典条目，至少人工复核一条远端证据；
- 多处命中、相似词边界、版本号等高风险规则需额外复核边界案例；
- 对正文没有技术命中的岗位进行抽样复核，防止系统异常导致整段文本漏扫；
- 未在真实正文中命中的规则只能用合成文本验证边界，不能声称已经过真实数据验证；
- 所有误判、暂不确定和规则缺口均通过独立复核记录保留，不能靠静默删除结果消除；
- 发布前须验证证据坐标、幂等重跑和本地/日志不含原文的安全边界。

**状态**：已确认。

### Round 18 — 2026-10-22 — 请求大计划守护者确认：每日同步与 JD 分析的运行边界

**需要确认的业务决定（通俗表述）**：是否把“每天按时把岗位资料收好”和“给新资料做技术词分析”看作前后相接、但彼此独立的两项工作？

**为什么需要它**：可以把同步任务理解为每天收信的邮差，把分析任务理解为整理信件内容的管理员。即使管理员当天遇到问题，邮差也不应停止收信或重发同一批信；否则我们会丢失或延迟最重要的原始历史。反过来，只有成功收下的新正文或已变化正文才需要分析，没变化的正文应复用已有结果。

**推荐**：每日同步成功后，由独立的远端分析任务处理新增或正文变化的内容版本，并使用当前已发布词典。分析失败只记录分析审计和错误类型，保留已入库的同步结果；它不应让当天的原始采集回滚、重拉或被标记为失败。修复分析规则后，按已确认的版本化重算机制重新处理，不依赖重新访问来源接口。

**例子（均为合成示例）**：凌晨收到了 10 封新信，其中 1 封的自动分类器出错。10 封信仍应安全归档；出错的那封进入“待分析”清单。第二天照常继续收信，修复分类器后再对已归档信件重算，而不是要求来源网站重新提供旧信。

**备选**：将同步与分析捆成一个成败共同体。实现表面简单，但一次词典或分析故障会影响每日原始资料的连续性，也会诱导无意义的重复拉取；不推荐。

**本问题解锁**：分析任务调度、失败审计、重算入口和同步任务的成功语义。

**项目负责人确认**：同意每日同步与 JD 分析相互独立；这也是后续多种分析与图像生成任务共用的目标流水线原则。

**确认的流水线原则**：

- 每日同步是稳定的上游资料入口：先安全归档和记录岗位观察、来源元数据版本与正文内容版本；
- JD 技术提及解析是第一个下游消费者，只处理新增或正文变化的内容版本，并复用未变化正文的既有结果；
- 任一下游任务失败只影响自己的审计状态、结果发布和待处理清单，不能回滚、阻塞或诱导重跑原始同步；
- 下游任务修复或规则升级后，应读取已有的远端受控版本化输入进行重算，不依赖重新访问来源接口；
- 未来其他分析或图像生成任务也应作为独立下游消费者，分别保存输入版本、处理规则/模型版本、结果版本、审计和发布状态；
- 所有下游任务继续遵守真实 JD 与可还原证据仅在远端处理的安全边界。

**状态**：已确认。

### Round 19 — 2026-10-22 — 请求大计划守护者确认：为未来扩展预留接口，而非预建通用引擎

**需要确认的业务决定（通俗表述）**：既然未来会有更多分析和图像生成任务，我们现在应当造一台“包办所有工作的超级机器”，还是先把第一个 JD 技术分析站做好，并规定每个未来处理站都遵守同一套交接单？

**为什么需要它**：前者看起来一次解决未来问题，但未来任务的输入、耗时、成本、人工审核和输出形式可能完全不同。现在猜测所有需求，容易让首轮工程变大、变慢且难验证。后者像流水线预留统一插槽：每个站都拿到清楚的版本化输入，产出自己的结果与审计；新站出现时再按相同交接方式接入。

**例子（均为合成示例）**：技术提及站读取“某版正文”，输出“技术提及及证据”；未来图像生成站可能读取“已审核的聚合指标”，输出“图像文件和生成参数”。它们都应说明“输入哪一版、用什么规则/模型、何时完成、是否发布”，但不必现在强行使用同一套业务表或同一套复杂调度逻辑。

**推荐**：本期仅实现 JD 技术提及这个下游任务；同时固定最小交接约定——版本化输入、任务/规则版本、独立审计、可重算、发布状态和失败隔离。未来任务按该约定新增适配，不在本期预建通用工作流引擎或图像生成能力。

**备选**：现在搭建全能的任务编排平台。它会显著扩大本期范围，却没有足够已知的未来任务来验证抽象是否正确；不推荐。

**本问题解锁**：JD 分析任务的数据模型边界，以及未来分析/图像任务接入时应保持的一致性。

**项目负责人确认**：同意本期只实现 JD 技术提及处理站，并以最小交接约定支持未来独立下游任务；不预建通用工作流引擎或图像生成能力。

**确认的范围边界**：

- 本期下游实现范围限于“职责、任职要求及补充说明中的技术提及”；
- 本期不实现通用任务编排平台、其他分析维度、图像生成或对应展示能力；
- 未来处理站须各自关联版本化输入、任务规则/模型版本、独立审计、可重算结果、发布状态与失败状态；
- 未来任务可复用该交接约定，但不应被迫复用 JD 技术提及的业务表、词典或调度细节；
- 任何后续扩展仍须另行探索、提案和授权。

**状态**：已确认。当前探索已形成足以创建独立 OpenSpec 提案的范围、数据边界、版本/证据模型、运行语义和首轮验收口径；尚未创建提案，也未开始实现。

### Round 20 — 2026-10-23 — 首期确定性词典的本地人工确认门禁

**问题**：真实 JD 不能保存或复制到本地，而项目负责人不希望为首期精确词面逐条操作 CVM。如何保留人工质量责任，又不突破数据边界？

**项目负责人确认**：首期把人工确认拆为两部分：

1. 项目负责人在本地审核词典的技术身份、精确词面、边界和明确排除关系；本地只处理映射表和不含原文的验收汇总。
2. CVM 对真实正文执行确定性的证据重放校验，只输出状态、计数、规则键、坐标、哈希和安全错误码；不返回 JD 正文、命中片段或岗位信息。

**适用范围**：此替代门禁仅用于首期“技术词提及”的确定性精确匹配。它不判断硬性要求、任选关系或工作内容，也不适用于模糊匹配、上下文消歧、年限/学历等未来语义能力；这些能力仍须另设远端人工文本复核。

**首轮已取得的远端证据摘要**：候选配置保持未发布；164 个正文版本全部完成分析，产生 22 个岗位级提及和 29 条证据。字段哈希、规范化版本、Unicode 码点坐标、别名、正式 ASCII 标识符边界（含连字符）和冻结规则集归属的异常计数均为零；多命中与无命中正文的安全抽样也无异常。所有输出均不含真实正文。

**记录方式**：不修改已部署的 `technical-keyword-alias-map-v0.1.md`，以免改变词典内容哈希。项目负责人逐条确认写入独立的[技术词典 v0.1 人工确认记录](技术词典v0.1人工确认记录.md)，该记录绑定映射 blob、部署修订、解析器版本和冻结规则集指纹。

**状态**：质量门禁调整已确认；项目负责人在[技术词典 v0.1 人工审阅表](技术词典v0.1人工审阅表.md)中批量完成候选规则的本地政策确认后，再由独立确认记录固化本次决定。当前仍没有受控发布入口。
