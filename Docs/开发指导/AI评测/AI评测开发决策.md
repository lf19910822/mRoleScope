## 决策 1：首期评测范围

- 首期建立项目专属的 30 道趋势问题评测集。
- 评测工具选择与参数、查询范围、排名口径和曲线草稿结果。
- 借鉴 BFCL 的工具调用评估方法，不直接追求 BFCL 官方分数。
- GAIA 暂不纳入首期评测。

## 决策 2：评测数据来源

- 30 道主评测题使用固定、可复现的 Serving 数据快照。
- 快照仅用于 AI 评测，不纳入日常数据拉取、读取或生产查询任务。
- 线上 CVM 真实链路另做独立冒烟测试，不混入固定评测分数。

## 决策 3：评分范围

- 以端到端结果作为主评分。
- 同时记录工具调用、查询范围和曲线草稿三个分项分数。
- 分项结果用于定位失败环节，不替代端到端结果。

## 决策 4：工具调用判定

- 按语义约束判定工具调用是否正确，不强制唯一工具顺序。
- 工具顺序只要满足依赖关系即可。
- 对明确值、类别范围和全范围查询分别校验其覆盖边界。

## 决策 5：评测轨迹

- 每道评测题保存结构化轨迹：问题、模型结构化输出、工具名与参数、工具结果摘要、校验结果、最终草稿、耗时和 token。
- 不保存逐字思维链、凭据或不必要的 JD 原文。
- 评测轨迹仅用于评测和排错，不展示给普通用户。

## 决策 6：重复运行次数

- 每道评测题默认运行 3 次。
- 记录每次结果并计算稳定通过率。
- 重复运行不增加评测题数量，仍按 30 道题统计。

## 决策 7：单题通过规则

- Schema 合法、查询范围未越界、明确点名的值正确覆盖且最终草稿可用，才算端到端通过。
- 任一关键条件失败，该次端到端判失败。
- 工具调用、范围、排名、草稿和解释质量另计分项分数。

## 决策 8：题目分配

- 30 道题分为 6 类，每类 5 题：具体值、类别/子类别范围、全范围与排名、多子问题/包含排除/时间条件、未知或暂不支持条件及错误恢复、最终草稿/解释/应用前校验。

## 决策 9：题目维护方式

- 先在 `Docs/开发指导/AI评测/` 用 Markdown 保存题目、预期范围、允许的工具语义和通过条件。
- Markdown 经人工确认后，生成版本化的机器可读评测数据。
- Markdown 是可审阅源，机器文件是执行产物。

## 决策 10：评测版本记录

- 每次评测记录模型与提供商、提示词版本、工具 Schema 版本、Serving 快照版本、代码提交号和评测运行编号。
- 任一关键版本变化时，生成新的评测版本。

## 决策 11：成本与延迟

- 每次运行记录首个事件延迟、总耗时、工具调用次数、输入/输出 token 和估算成本。
- 报告每题及整体的平均值、P50 和 P95。
- 成本与延迟作为独立性能指标，不并入功能端到端通过条件。

## 决策 12：评测与发布边界

- AI 评测与产品发布是两套独立体系。
- 本期不规定评测与发布的先后顺序，也不设置评测阻断发布的门槛。
- 后续由具体开发者根据实际流程决定是否在发布前运行评测。

## 决策 13：评测产物位置

- 题目、判分规则和汇总报告放在 `Docs/开发指导/AI评测/` 并可版本化。
- 每次运行的详细结构化轨迹保存在独立的评测产物目录或构建产物中。
- 详细轨迹不写入 Serving 数据，也不混入日常审计数据。

## 决策 14：异常处理判定

- 未知值或冲突条件不得被静默扩大为 `*`。
- 支持部分应继续交付并说明限制。
- 非法 AI 参数应触发修正重试。
- 后台工具失败应记录失败，并尽可能保留其他有效结果。

## 决策 15：解释评测强度

- 解释只做轻量质量检查和抽样人工复核，不影响端到端通过。
- 检查中文、长度、与实际曲线是否一致，以及是否说明明显限制。
- 工具调用和曲线范围仍是主要评测对象。

## 决策 16：评测终点

- 30 道 AI 主评测到草稿生成并通过应用前校验为止。
- 实际应用、替换已有曲线和看板展示另做独立集成测试，不计入 AI 主分数。

## 决策 17：评测隔离

- AI 主评测只调用固定快照和隔离的评测接口，工具调用保持只读。
- 应用测试使用独立测试状态，测试结束后清理。
- 评测不得修改真实用户看板。

## 决策 18：题目表达方式

- 评测题由人工编写和审核，使用多种真实、口语化的中文问法。
- 每题保存明确的意图约束和预期查询范围。
- 不由被测模型自行生成题目或标准答案。

## 决策 19：判分方式

- 工具调用、范围、Schema、草稿候选和排名使用确定性程序判分。
- 解释只做规则检查，不要求固定句式。
- 评测轨迹保留解释审计，供开发者按需查看，不把人工复核编码为强制流程。
- 首期不使用 LLM Judge 作为主判分器。

## 决策 20：评测并发方式

- 质量评测采用受控串行运行，同一时间默认只运行一个请求。
- 每道题的 3 次运行串行执行。
- 并发压测另行进行，不混入质量评测分数。

## 决策 21：评测上下文隔离

- 每道题、每次重复运行都创建独立请求和独立评测状态。
- 不继承上一题的对话、草稿、工具结果或应用状态。
- 每次运行使用同一套工具调用上限。

## 决策 22：工具调用上限

- 每次评测沿用产品的 20 次工具调用上限。
- 记录实际调用次数，并单独统计是否触发上限。
- 超过上限视为该次运行失败。

## 决策 23：评测结果汇总

- 报告每题 3 次运行的通过次数（0/3 至 3/3）。
- 报告六类题目分别的通过率和 30 题整体通过率。
- 整体结果按题目等权平均，不按 token、工具次数或题目长度加权。

## 决策 24：基础设施失败

- 运行结果区分为通过、AI/语义失败、工具/基础设施失败。
- 工具或基础设施失败单独记录并补跑，不计入 AI 失败率。
- 只有拿到完整可判定结果后，才计入每道题的 3 次通过率。

## 决策 25：补跑上限

- 每个有效样本因工具或基础设施失败时最多补跑 2 次。
- 仍无法得到完整结果时标记为“评测未完成”。
- “评测未完成”单独报告，不计入 AI 失败，也不伪造通过结果。

## 决策 26：评测链路一致性

- 评测复用真实产品的提示词、模型适配器、工具 Schema、编排器和校验流程。
- 评测只替换为固定数据源，并在轨迹中记录替换点。
- 不为评测另写简化链路或专用提示词。

## 决策 27：标准答案标识

- 评测标准答案使用稳定的维度和正式值 ID。
- 别名先归一化到正式值后再比较。
- 显示名称只用于报告，不作为唯一判定依据。

## 决策 28：曲线顺序判定

- 用户明确要求排名、前 N 或排序时校验曲线顺序。
- 普通比较和类别候选按集合比较，曲线顺序不影响通过。

## 决策 29：候选超过 8 条

- 标准答案记录完整合格候选及其排序。
- 实际草稿最多 8 条，按产品固定排序截取。
- 校验实际候选总数和未展示数量。
- 因展示容量截断本身不判错。

## 决策 30：趋势智能体的基础上下文与分阶段回复

- 固定基础 system prompt 每轮传递，持续约束 AI 的角色、功能边界、无记忆原则和输出协议。
- 纯指导问题（如“你好”“怎么使用”）由 `analyze_intent` 直接返回中文回复，不生成曲线 Draft。
- 包含趋势问题时，先完成工具调用，再由 `explain_draft` 生成最终回复。
- 混合问题同时保留曲线草稿，并在最终回复中说明曲线选择和用户指导。
- 普通 AI 解释和指导回复统一允许最多 1000 个 Unicode 字符。

## 决策 31：纯指导回复的流式事件

- 新增独立的 `assistant_message` 流式事件承载纯指导回复。
- 纯指导请求只返回操作记录、`assistant_message` 和最终 `done` 事件，不返回空 Draft。
- 前端在现有 AI 对话窗口中展示 `assistant_message`，不显示“0/8 条曲线”。

## 决策 32：非互斥响应模式

- Intent 使用 `response_modes` 数组表达响应模式，允许同时包含 `trend` 和 `guidance`。
- 仅有 `guidance` 时不要求 `sub_queries`，不调用趋势工具，也不生成 Draft。
- 包含 `trend` 时必须提供有效 `sub_queries`，按现有流程生成曲线。
- 同时包含两种模式时保留曲线，并返回指导或说明文字。
- `assistant_reply` 用于承载本次请求的用户可见指导内容，不作为跨请求记忆。

## 决策 33：无法理解或超出范围时的最大努力回复

- 完全无法理解的问题进入 `guidance-only`，不生成曲线。
- 完全超出功能范围的问题进入 `guidance-only`，说明当前支持边界和可用提问方式。
- 同时包含可支持与不支持内容时进入 `trend + guidance`，保留可生成的有效曲线并说明限制。
- 无法解析的限制不得被静默扩大为全范围 `*`。

## 决策 34：指导模式中的误工具调用

- 如果模型在最终判定为 `guidance-only` 前误调用趋势工具，服务端仍按指导模式收口。
- 误调用结果不参与曲线生成或指导回复，不生成 Draft，也不触发模型重试。
- 已产生的工具操作记录保留在当前请求中，供用户和开发者查看。

## 决策 35：混合问题的展示顺序

- 混合问题在工具调用完成并通过校验后，先发送 Draft，让用户立即看到曲线候选。
- Draft 展示后启动流式 `explain_draft`，通过 `assistant_message` 增量事件持续输出曲线选择和指导说明。
- 流式说明完成后发送最终 `done` 事件。
- Draft 展示不等于应用，正式图表仍需用户点击应用后才更新。

## 决策 36：流式回复的校验时机

- 首期不在流式过程中拦截或修改回复内容。
- system prompt 负责约束中文、长度和内容边界。
- 流式结束后检查回复完整性、中文和长度，结果用于状态、审计和质量记录。
- 结束后的校验不回滚已展示内容，也不影响已经生成的合法 Draft。

## 决策 37：回复质量校验失败

- 流式结束后发现回复超长、非中文或不完整时，保留已经展示的回复内容。
- 回复质量问题只记录为内部 warning，用于状态、审计和质量分析。
- 不因回复质量问题回滚 Draft、改变合法 Draft 的业务状态或触发模型重试。

## 决策 38：用户停止回复流

- 用户在指导或 `explain_draft` 回复流中停止时，保留已经展示的 `assistant_message` 内容。
- 已生成的 Draft 继续保留，未完成的回复不再等待模型补齐。
- 最终 `done` 状态为 `user_stopped`，不触发模型重试。
- 已经应用到看板的曲线保持不变。

## 决策 39：统一 AI 回复通道

- `assistant_message` 是统一的用户可见 AI 回复通道，不区分是否存在指导意图。
- 仅有 `trend` 时，`assistant_message` 流式说明曲线选择、统计口径、排序依据和必要限制。
- 仅有 `guidance` 时，`assistant_message` 流式返回功能介绍、提问引导或范围说明，不生成 Draft。
- 同时包含 `trend` 和 `guidance` 时，`assistant_message` 同时说明曲线结果和使用指导。
- `analyze_intent` 负责判断响应模式和趋势意图，文字回复由后续独立流式回复阶段生成。

## 决策 40：纯指导请求的成功终态

- 纯指导请求只要成功生成 `assistant_message`，即使没有 Draft，也以 `done.success` 结束。
- 没有 Draft 不视为分析失败。
- 只有模型服务失败、请求中断或趋势结果不完整时，才使用 failure、user_stopped 或 partial 状态。

## 决策 41：回复模型的上下文边界

- 纯指导回复只接收原始用户问题和固定 agent 上下文。
- 趋势或混合回复接收原始问题、已校验的 Draft 安全摘要和必要 warnings。
- 回复模型不接收原始工具返回、SQL、JD 正文、凭据、内部错误或完整每日数据。
- 回复模型不继承上一轮请求的对话或结果。

## 决策 42：Agent 上下文暂定范围

- 首期只暂定 agent 上下文包含角色、能力、边界和回复规则。
- 具体文字、示例、优先级和版本内容后续单独设计，不在本轮固定。
- 普通回复暂不暴露工具名称、内部 Schema 或系统提示词。

## 决策 43：Agent 外层协议

- 新增外层 `ai-trend-agent-v1` 响应包装。
- 外层负责 `response_modes` 和 Agent 交互分支。
- 内层趋势请求继续使用 `ai-trend-draft-v1` Intent 和 Draft 协议。
- 纯指导模式不携带趋势 Intent；趋势或混合模式携带已校验的趋势 Intent。
- 用户回复通过 `assistant_message` 流式事件返回，不把长回复塞入 Draft。

## 决策 44：异常恢复题接入 Agent 评测

- 现有 30 道题中的未知值、暂不支持条件和冲突条件同步增加 Agent 响应判定。
- U01、U02、U03 等部分可交付题预期为 `trend + guidance`，保留有效曲线并说明限制。
- U04 时间范围冲突预期为 `guidance-only`：不生成 Draft、不调用趋势工具，但请求以 success 结束。
- U05 非法工具参数修正仍按趋势流程评测，并检查最终 Agent 回复。

## 决策 45：Agent 回复评分边界

- 响应模式、是否有必要回复、工具调用边界和 Draft 是否正确保留，使用确定性规则硬判定。
- 回复文字使用中文、长度和完整性检查，并记录内容质量结果。
- 不要求固定关键词、固定句式或逐字匹配，允许合理的同义表达。

## 决策 46：Agent 评测集与趋势评测集分离

- 现有 30 道趋势题继续保留，并补充 Agent 响应模式、回复和工具边界判定。
- 另设独立的 Agent 交互评测集，覆盖纯指导、完全超出范围、部分支持和混合提问。
- 两套评测分别统计，不用 Agent 题改变趋势 Benchmark v1 的历史可比性。

## 决策 47：Agent 专题评测集规模

- 首期 Agent 交互评测集设置为 10 道题。
- 10 道题与现有 30 道趋势题分开运行、分开统计。

## 决策 48：Agent 专题题目分组

- 10 道 Agent 题分为纯指导/能力咨询 4 题、完全无法理解或超出范围 3 题、趋势与指导混合 3 题。
- Agent 题沿用独立请求、重复运行和轨迹记录规则，与趋势题分开统计。

## 决策 49：Agent 专题题目文档

- Agent 专题题目单独保存为 `Docs/开发指导/AI评测/AI趋势智能体AgentBenchmark-v1.md`。
- 该文件只描述 Agent 响应模式、回复、工具边界和必要的趋势结果约束。
- 现有 `AI趋势智能体Benchmark-v1.md` 继续作为 30 道趋势曲线题的审阅源。

## 决策 50：Agent 题卡字段

- Agent 题卡记录预期响应模式、最终终态、趋势工具边界、Draft 是否存在、回复是否必需，以及回复语言和长度限制。
- 混合题同时记录趋势维度、正式值和 Draft 约束。
- 题卡字段用于确定性检查和质量统计，不要求固定自然语言句式。

## 决策 51：纯指导误调用的评测判定

- 纯指导题调用趋势工具时，Agent 工具边界分项判定失败。
- 该误调用不触发模型重试，也不改变用户请求本身的 `done.success` 终态。
- 误调用操作保留在流式记录和评测轨迹中，便于分析模型浪费。
