### 重要边界：可观测性不等于读取隐藏思维过程

这些产品能展示应用主动记录的 trace、span、模型请求/响应、工具调用、错误和耗时，不能自动获得模型没有返回的隐藏思维过程。对于当前 AI 作图，真正有排障价值且应该记录的是：

```text
分类 -> 模型请求/响应 -> 工具调用 -> 工具结果
     -> 参数校验失败 -> AI 修正重试
     -> 最终 Intent -> Draft 构建 -> 终态
```

这正好对应当前 `add-ai-debug-mode` 变更的目标。浏览器中的 NDJSON 是实时进度；排障平台是事后可检索的完整受控 trace，两者不能互相替代。

### LangSmith 核对结果

用户提供的 `langchain-ai/langsmith-javascript` 仓库确认了以下事实：

- 官方 JavaScript SDK 明确支持不依赖 LangChain 的自定义应用。
- `traceable` 可以包装任意函数；`RunTree` 可以建立父级 chain 与嵌套 LLM/tool run。
- SDK 支持输入、输出、metadata 隐藏和自定义 anonymizer。
- 官方仓库还提供了 OpenTelemetry 和流式查询示例。

官方 `langchain-ai/langsmith-go` 仓库也存在，并提供 OpenTelemetry ingestion、层级 waterfall trace 和 OpenAI 客户端示例。因此，LangSmith 不要求我们把 Go 服务重写成 LangChain。

但它不适合作为当前默认方案：

- 官方 Self-hosted 文档明确说明，自托管 LangSmith 是 Enterprise 计划的附加项，需要联系销售取得许可密钥。
- 自托管面向 Kubernetes，并涉及 PostgreSQL、ClickHouse、Redis/Valkey、对象存储及多个应用服务，超出当前单 CVM 的最小需求。
- 云端方案会把 prompt、模型响应、工具参数和结果发送到 LangChain 平台，与本项目默认不外发业务数据的理念不一致。
- 官方 SDK 的 SSE 示例主要是查询追踪数据流，不会自动捕获应用中所有模型流式 token；模型流式过程仍需应用侧主动记录。
- 当前 Go 仓库 README 写的是 Go 1.22+，但仓库 `go.mod` 当前声明 `go 1.26.7`；本项目当前是 Go 1.22.5，不能直接把该 SDK 当作无风险依赖。

结论：LangSmith 适合预算允许、接受 SaaS 或 Enterprise 自托管、优先需要成熟商业 UI 的团队；当前不作为首选，也不应为了使用它重写现有 Go 编排器。

### Langfuse 核对结果

Langfuse 是较完整的开源替代候选：官方仓库将其定位为 AI observability、agent tracing、prompt 管理和评测平台；官方文档支持 Docker Compose 单机自托管，并支持通过 OpenTelemetry 接收其他语言的 trace。

主要事实：

- 官方 OpenTelemetry 入口为 `/api/public/otel`。
- 当前文档说明支持 OTLP HTTP/JSON 和 HTTP/protobuf，不支持 gRPC。
- 没有官方 Langfuse Go SDK；Go 服务应使用 OpenTelemetry Go 或直接 HTTP/OpenAPI 接入。
- 可以表示 trace、generation、tool、retrieval 和 session 层级。
- 官方文档提供 masking、批处理、flush/shutdown 和数据留存配置方向。
- 核心平台仓库标注 MIT，但部分自托管附加能力需要 license key，不能把所有企业功能理解为永久免费。

优点是 prompt playground、评测集、质量指标和长期 AI 工程能力完整。限制是官方 Docker Compose 栈包含 Web/Worker、PostgreSQL、Redis/Valkey、ClickHouse、MinIO 等服务；如果没有明确留存策略，事件数据还可能长期增长。

结论：如果未来需要长期 prompt 版本管理、评测集、质量评分和多团队 AI 平台能力，Langfuse 是强候选；只为解决当前排障问题时，它比必要范围更大。

### Phoenix 核对结果

Phoenix 的官方仓库和文档明确支持基于 OpenTelemetry 的 LLM tracing、评测、数据集、实验和 prompt playground。官方 Self-hosting 文档明确说明可以免费自托管、没有功能限制、数据不发送到 Arize，并支持完全 air-gapped 部署。

官方 Docker Compose 示例的核心服务是 Phoenix + PostgreSQL，基础设施比 Langfuse、Opik 和 LangSmith 的完整栈轻。Go 服务可以直接使用 OpenTelemetry Go SDK/OTLP exporter，手动创建 root span 和 child span，不需要引入 LangChain 或 Phoenix 专用 Go SDK。

Phoenix 适合展示模型调用、工具调用、错误 span、耗时、token、session 和 trace waterfall，也保留后续评测与 prompt 调试空间。UI 可以只绑定 CVM 私网或 loopback，通过 SSH 隧道访问，不必增加公网入口。

必须记录的许可事实：Phoenix 当前 GitHub `LICENSE` 是 Elastic License 2.0（ELv2），不是 Apache-2.0 或 MIT。它允许在自己的基础设施内部使用，但禁止把 Phoenix 作为向第三方提供的托管服务；未来若把 Phoenix UI 对外提供给公众，必须重新核对许可边界。

结论：在“Go + 单 CVM + 低成本 + 不希望 JD 数据离开环境 + 先解决 trace 排障”的条件下，Phoenix 是当前第一候选。

### Helicone 与 Opik 核对结果

Helicone 官方仓库标注 Apache-2.0，支持 Docker 自托管，并提供请求日志、session/trace、成本、延迟和 playground。但它更偏 AI Gateway/LLM proxy；完整自托管架构仍包含 PostgreSQL、ClickHouse、MinIO、Redis、Web/Jawn 等服务。它适合希望统一代理多个模型供应商的团队，不是当前 Go 编排器的最小 trace 后端。

Opik 官方仓库标注 Apache-2.0，支持完整自托管、agent trace、评测和生产监控。但其官方 Docker Compose 基础设施包含 MySQL、Redis、ClickHouse、ZooKeeper、MinIO，完整栈还包含多个 backend、frontend 和 Python 服务；当前没有与 LangSmith Go SDK 同等级的官方 Go SDK。对现有 CVM 来说运维成本过高，暂不推荐。

### 产品对比结论

| 产品 | 自托管与数据边界 | Go 接入 | 主要优势 | 当前主要问题 | 当前判断 |
|---|---|---|---|---|---|
| LangSmith | 自托管 Enterprise 附加项；云端数据外发 | 官方 Go SDK + OTel，但版本门槛需核对 | UI、agent 调试和生态成熟 | 成本、许可、Kubernetes 复杂度 | 不作为首选 |
| Langfuse | 核心开源，可 Docker Compose 自托管；多服务栈 | 原生 OTel 接入 | 平台完整，prompt/评测能力强 | ClickHouse/Redis/MinIO 等运维负担 | 第二候选 |
| Phoenix | 官方支持免费自托管和 air-gap；ELv2 | 原生 OTel 接入 | trace 排障直接、栈较轻、数据留在 CVM | ELv2 许可；仍需独立 PostgreSQL | 第一候选 |
| Helicone | Apache-2.0，可 Docker 自托管 | HTTP/代理和 OTel 方向 | Gateway、成本和请求分析 | 偏代理平台，完整栈较重 | 备选 |
| Opik | Apache-2.0，完整自托管 | OTel/多语言，Go 需自行接入 | 评测、监控和 agent 平台完整 | MySQL/Redis/ClickHouse/ZooKeeper/MinIO 栈过重 | 暂不采用 |

### 对 mRoleScope 的推荐架构

不应把当前浏览器流式事件替换成第三方平台。两者解决不同问题：

```text
用户浏览器
  <-- 现有 NDJSON：实时进度、草稿、用户停止

Go AI 编排器
  -> 现有有界安全审计：哈希、计数、状态
  -> 仅受控 debug run 的 OpenTelemetry trace
       -> Phoenix（CVM 私网）
```

建议以 OpenTelemetry 作为项目内部的可观测性抽象，而不是直接依赖 Phoenix SDK：

- 根 span：一次 AI 作图请求。
- 子 span：服务模式分类、每次模型请求、每次模型响应、每次工具调用、工具结果、参数校验/修正、趋势聚合、Draft 构建和最终状态。
- span 属性只保留有限、可脱敏的结构化信息：操作名、工具名、维度、候选数量、错误码、状态、耗时、token 数和 trace ID。
- 默认生产请求不发送完整 prompt、模型原文、JD 正文或完整工具结果。
- 显式开启 debug 的单次受控运行，才允许保存经过脱敏、大小限制和保留期限限制的完整模型/工具交换，供操作人员排障。
- exporter 或 Phoenix 不可用时不能阻断 AI 作图；浏览器结果和现有安全审计继续工作。
- Phoenix UI 只绑定 CVM 私网或 loopback，通过 SSH 隧道供操作人员访问，不增加公网入口。

### 最终推荐

当前不建议直接购买或接入 LangSmith。建议先完成现有 `add-ai-debug-mode` 的 loopback-only 诊断链路，并预留 OpenTelemetry exporter seam；随后在本地或 CVM 私网以 Phoenix 做一次小规模验证。若验证后发现需要长期 prompt 版本、评测集、质量评分和多团队平台能力，再评估 Langfuse。

无论选择哪款，都保留 mRoleScope 自己的确定性审计表：外部平台负责“可视化排障”，本地审计负责“稳定口径、留存策略和业务审计”。

### 本轮结论

本轮完成产品调研和方案判断，不修改业务代码、不部署第三方平台、不改变当前生产数据留存策略。下一步若用户确认，需单独创建或更新 OpenSpec 变更，明确 OpenTelemetry span 字段、脱敏策略、Phoenix 部署边界、保留期限和验收样本后再实现。

### 官方 Langfuse 资源要求

Docker Compose 指南给出的单机入门建议是：至少 **4 个 CPU、16 GiB 内存、约 100 GiB 存储**。同一指南还提醒观测数据会持续增长，Docker 默认 `json-file` 日志如果不配置轮转也可能耗尽磁盘。

官方 `scaling.md` 进一步按组件列出最低资源：

| 组件 | 官方最低资源 |
|---|---:|
| Langfuse Web | 2 CPU / 4 GiB |
| Langfuse Worker | 2 CPU / 4 GiB |
| PostgreSQL | 2 CPU / 4 GiB |
| Redis/Valkey | 1 CPU / 1.5 GiB |
| ClickHouse | 2 CPU / 8 GiB |
| MinIO/SeaweedFS | 2 CPU / 4 GiB；使用外部 S3 时可不承担该计算资源 |

按组件最低值直接相加，完整自托管栈约需要 **9 CPU、25.5 GiB RAM**，且还没有计算宿主机、Docker、文件系统缓存和突发流量余量。4 CPU / 16 GiB 是官方单机入门建议，不能理解成每个组件最低资源相加后仍有充足余量；它更适合低规模验证或将部分基础设施外置的部署。

其他与容量相关的官方事实：

- Langfuse v4 要求 PostgreSQL 至少 15，推荐 16；当前 Compose 示例使用 PostgreSQL 17。
- Redis 至少 7，Langfuse v4 推荐 7.2，并要求 `maxmemory-policy=noeviction`。官方扩容文档以约 100,000 events/min 为例建议约 1 GiB Redis 内存；这不是当前小规模事件量的承诺容量，而是容量规划参考。
- ClickHouse 是 trace、observation、score 的主要 OLAP 存储。官方最低值为 2 CPU / 8 GiB；较大部署通常建议至少 16 GiB，生产 Helm 示例从 100 GiB 持久盘起步，并建议生产至少 3 个副本。
- Blob Storage 用于 raw events、多模态输入和导出。官方生产建议优先使用托管 S3/GCS/Azure/R2；自托管 MinIO/SeaweedFS 时，持久化、备份和生命周期管理都由部署方承担。
- 官方建议为 ClickHouse 的 traces、observations、scores、event_log 设置 TTL；S3 生命周期和 Langfuse 数据留存也要一起规划。多数客户的事件保留参考为 30 天，但这是运营策略示例，不是系统默认容量保证。
- Docker Compose 是单机垂直扩容方案，不提供高可用和水平扩展；高吞吐场景应考虑 Kubernetes 或托管 ClickHouse/对象存储。

### 当前 CVM 只读观测（2026-11-25）

| 项目 | 观测值 |
|---|---:|
| CPU | 2 vCPU |
| 内存 | 1.9 GiB 总量；约 1.1 GiB available；2 GiB swap |
| 系统盘 | 50 GiB 总量；约 36 GiB 可用 |
| Docker | Docker 29.1.3，Compose 2.40.3 |

Langfuse Compose 常见的 3000、3031、6379、8123、9000、9090、9091 端口在本次观测时没有监听者，因此“端口已被占用”不是当前首要阻碍；但这些端口也不应因此直接暴露公网，UI 和 MinIO 应继续通过 loopback、私网或 SSH 隧道访问。

当前 PostgreSQL 16.4 和 Docker 版本本身没有构成阻碍；真正的阻碍是 CPU、内存和持久盘容量。当前可用内存只有 Langfuse 官方 ClickHouse 最低内存（8 GiB）的约七分之一，也低于 Redis 单组件参考值；剩余磁盘约 36 GiB，低于官方单机约 100 GiB 建议，还要继续承载 mRoleScope 的 PostgreSQL、镜像、日志和归档。

### 结论：当前 CVM 不具备完整 Langfuse 自托管条件

在当前 2 vCPU / 1.9 GiB RAM / 50 GiB 磁盘的 CVM 上，不应启动官方完整 Docker Compose 栈。即使复用 mRoleScope 现有 PostgreSQL，也仍需新增 Web、Worker、ClickHouse、Redis 和对象存储；单是 ClickHouse 的官方最低 8 GiB 已超过当前整机内存，swap 不能替代这类常驻服务内存。裁剪组件或把多个服务硬塞进同一台机器只能得到未受支持、不可稳定验收的实验环境，不能作为“已接入 Langfuse”的依据。

这不是“磁盘暂时够不够”的单一问题：

1. 内存会先成为硬阻塞，尤其是 ClickHouse、Node Web/Worker 和 PostgreSQL 同时运行时。
2. CPU 不足以支撑官方组件的最低并发预算，也没有为现有 API、数据库和采集任务预留余量。
3. 36 GiB 可用磁盘不足以按照官方约 100 GiB 的单机建议规划 trace、ClickHouse 系统表、raw event、MinIO 和日志增长。
4. 现有 Compose 不是 Langfuse 的部署栈，不能把已有 PostgreSQL 容器的低即时占用当成新平台的容量证明。

### 建议的落地门槛

- **当前 CVM：不部署 Langfuse。** 继续使用已完成的 loopback-only AI Debug 模式完成当前模型排障。
- **小规模受控验证：** 单独准备至少 4 vCPU、16 GiB RAM、约 100 GiB 持久盘的实例；最好把对象存储外置，并明确只保留短期 trace。4/16/100 是官方单机起步建议，不代表高吞吐生产规格。
- **长期运行：** 将 Langfuse 与 mRoleScope 主服务隔离，优先使用托管 PostgreSQL、ClickHouse 和 S3；如果必须自托管，使用独立更大 CVM 或 Kubernetes，并设置 ClickHouse TTL、对象存储生命周期、日志轮转、备份和恢复演练。
- **接入方式：** 保留 OpenTelemetry exporter seam。无论 Langfuse 是否最终采用，生产默认只发送脱敏结构化 span；完整 prompt、模型响应、工具结果只允许在受控 debug run 中发送，并设置 trace 保留期限。

本轮没有下载、启动或部署 Langfuse，没有修改 CVM，也没有改变当前数据留存策略。以上资源数字和结论以 2026-11-25 访问的官方文档与该日 CVM 只读观测为准。

## 第七十四轮：选择性接入与开发机 227 可行性（2026-11-25）

### 先区分“接入 Langfuse”与“在本机运行 Langfuse”

Langfuse 的接入面和自托管平台是两个独立问题：

1. **应用接入**：mRoleScope 使用 OpenTelemetry OTLP/HTTP 发送 span。官方 Langfuse 入口是 `/api/public/otel`，支持 HTTP/JSON 和 HTTP/protobuf，不支持 gRPC；Go 服务可以使用 OpenTelemetry Go HTTP exporter。应用侧不需要运行 ClickHouse、Redis 或 MinIO。
2. **平台运行**：为了提供 Langfuse UI、队列、ClickHouse 查询、PostgreSQL 状态和对象存储，需要运行或购买相应基础设施。完整平台才会产生上一轮列出的资源开销。

因此可以选择性接入，但必须明确选择哪一种边界：

| 方案 | 本机额外资源 | 数据边界 | 适用性 |
|---|---:|---|---|
| 当前 Debug 模式 + 不接 Langfuse | 近似 0 | 数据留在本地/CVM | 当前排障首选 |
| Debug run 发送少量 OTLP 到 Langfuse Cloud | 仅 exporter 缓冲和网络 | prompt/响应是否外发取决于脱敏策略和 Cloud 区域 | 最省本机资源；需接受外部平台数据边界 |
| 227 上完整自托管 Langfuse Compose | 需要 Web、Worker、ClickHouse、Redis、Postgres、对象存储 | 数据可留在开发机 | 当前资源不足，不建议 |
| 227 上运行 Web/Worker，数据库和对象存储外置 | 仍需约 Web/Worker 的运行资源 | 大部分数据在外置服务 | 可行性取决于外置服务和 227 的空闲内存 |
| 独立 Langfuse 实例，mRoleScope 只作为 OTLP 客户端 | mRoleScope 侧很小 | 可把平台与主服务隔离 | 最适合后续验证 |

### 开发机 227 只读观测（2026-11-25）

本机只读观测结果：

- 4 vCPU，AMD EPYC Milan；当前 load 约 `0.21 / 0.12 / 0.15`。
- 7.8 GiB RAM，约 3.1 GiB available，**没有 swap**。
- 97 GiB 根盘，约 24 GiB 可用（76% 已使用）。
- Docker Server/Client 26.1.3。
- 已有 14 个运行容器、143 个 Docker volume、54 个镜像；其中包含多个 PostgreSQL 测试/验收实例和其他长期运行容器。
- 当前没有 Langfuse 常见的 3000、3031、6379、8123、9000、9090、9091 端口监听者，因此端口冲突暂时不是阻碍。
- 主机整体负载较低，但内存和磁盘余量不能按“空闲瞬间”直接当作 Langfuse 可用配额；已有容器和 Docker volume 必须保留，不能为了试验直接清理。

227 的 CPU 数量达到官方单机入门建议，但内存只有官方建议的一半，当前可用内存更少；磁盘虽然总量接近 100 GiB，实际可用空间只有约 24 GiB。完整 Compose 栈还会引入 ClickHouse、Redis、MinIO 和 Langfuse Web/Worker，在无 swap 的情况下很容易造成内存压力，ClickHouse 数据和系统日志也会迅速压缩磁盘余量。

即使把 PostgreSQL、ClickHouse、Redis 和对象存储全部外置，官方 Web + Worker 的最低值仍是约 8 GiB RAM；这已经超过 227 的整机 7.8 GiB 总内存，更没有为现有 Node、Chrome、IDE、测试数据库和 Docker daemon 留出余量。因此“只在 227 本地运行 Langfuse Web/Worker”也不能作为当前默认方案。

所以 227 **不适合直接启动完整官方 Langfuse Compose**。除非先迁移或停止现有工作负载、扩容到至少 16 GiB RAM、重新规划磁盘，并为 Langfuse 独立分配资源；这些操作会影响现有开发环境，不能作为本轮自动动作。

### 可行的选择性接入方案

#### 方案 A：只把受控 Debug trace 发送到 Langfuse Cloud

这是本机资源最轻的方式：在 Go 服务中加入 OTLP/HTTP exporter，只在显式开启的 debug run 中启用，默认不发送生产请求。Langfuse 官方 OpenTelemetry 文档直接给出了 Cloud endpoint 和本地 endpoint 两种配置形式。

建议发送：

- root span：一次 AI Debug 请求；
- child span：分类、每次模型请求/响应、工具调用/结果、校验修正、最终 Intent、Draft、终态；
- 属性：模型名、工具名、错误码、候选数量、token 数、耗时、状态；
- 完整 prompt、模型响应、工具结果只在受控 debug 开关、脱敏和大小限制同时满足时发送。

优点是 227 不需要新增平台容器。缺点是 trace 可能离开本地环境，必须得到本次外发授权，并选择合适的数据区域、保留期限和字段脱敏策略。当前项目默认不向外部模型发送 JD 内容，这个方案不能绕过该边界。

#### 方案 B：227 只作为 OTLP 客户端，Langfuse 平台放到独立资源

可以在独立的 4c/16GiB/100GiB 以上实例，或使用托管 Langfuse/托管 ClickHouse、PostgreSQL、S3 的组合上运行平台。227 只负责发送受控 trace 和运行评测脚本，不承载平台数据库。

这是更适合长期评测的边界：开发机资源不会与 ClickHouse 争抢，平台数据也不会与 mRoleScope 的测试卷混杂。需要额外解决网络访问、密钥存放、数据区域和备份策略。

#### 方案 C：完全本地但只做短暂实验

理论上可以临时停止现有容器、使用外部 S3、限制 ClickHouse 和 trace retention，再在 227 上启动裁剪栈；但这仍然低于官方内存建议，而且会破坏当前开发环境的复现稳定性。它可以作为一次明确批准的实验，不应作为持续评测服务或生产依赖。

### 对当前项目的建议顺序

1. **近期排障**：继续使用现有 loopback-only AI Debug 模式，不引入 Langfuse 平台。
2. **接入设计**：在项目内增加 OpenTelemetry exporter seam，只在受控 Debug run 开启；先用本地 collector 或可替换 sink 验证 span 结构，不发送完整敏感内容。
3. **评测试验**：如果接受数据外发，优先用 Langfuse Cloud 做小样本评测；如果必须本地留存，准备独立 4c/16GiB/100GiB 以上资源，而不是复用当前 CVM 或 227。
4. **长期平台**：在确认评测集、prompt 版本、评分和保留策略后，再决定是否部署完整 Langfuse，并把平台与 mRoleScope 主服务隔离。

### 本轮结论

Langfuse 的完整平台开销确实较大，但 mRoleScope 不必一次性接入全部组件。选择性接入的最小合理形态是“mRoleScope 作为受控 OTLP 客户端，Langfuse 平台使用 Cloud 或独立资源”；在当前 227 上直接运行完整 Langfuse 仍受内存、磁盘和现有 Docker 工作负载限制。本文没有停止容器、清理 volume、启动 Langfuse 或发送任何业务数据。

## 第七十五轮：完整业务 Trace 与独立部署边界（2026-11-25）

### 未脱敏完整 Trace 在技术上可行

Langfuse 官方 OpenTelemetry 映射支持将完整业务交互放入 observation：

- generation 的输入可使用 `langfuse.observation.input`、`gen_ai.prompt` 等属性。
- generation 的输出可使用 `langfuse.observation.output`、`gen_ai.completion` 等属性。
- tool observation 的参数和返回值可使用 `gen_ai.tool.call.arguments`、`gen_ai.tool.call.result`。
- observation 类型可显式标记为 `generation`、`tool`、`chain`、`agent` 等。
- token 用量可使用 `langfuse.observation.usage_details` 或 `gen_ai.usage.*`。

因此，若发送端明确允许完整 payload，Langfuse UI 可以展示模型输入、模型输出、工具参数、工具结果、Intent 和 Draft 等开发排障细节。Go 服务只需要使用 OpenTelemetry OTLP/HTTP；官方端点为 `/api/public/otel`，支持 HTTP/JSON 和 HTTP/protobuf，不支持 gRPC。

这不会自动绕过项目的数据边界：未脱敏 JD、prompt、模型响应和工具结果仍是业务数据。发送到 Langfuse Cloud 属于向外部平台发送业务数据；本轮用户已明确表示允许为开发观察保留未脱敏内容，但真正配置 Cloud key、endpoint 和发送数据仍应作为单独的受控发布操作记录。

### “独立放到 CVM”有两种完全不同的含义

#### 1. CVM 只运行发送端或中转端

可行。CVM 可以运行 mRoleScope API、OpenTelemetry HTTP exporter，或一个轻量 OTLP collector，把 span 发往 Langfuse Cloud/独立 Langfuse 实例。这类组件不需要 ClickHouse、Redis、MinIO，也不会提供 Langfuse UI；CVM 当前资源足够承担发送端。

#### 2. CVM 运行 Langfuse UI 和后端

当前不可行。Langfuse 官方自托管 Compose 仍需要 Web、Worker、ClickHouse、PostgreSQL、Redis 和对象存储。即使 PostgreSQL、ClickHouse、Redis、对象存储全部外置，Web + Worker 官方最低仍约 8 GiB RAM；当前 CVM 只有 1.9 GiB，开发机 227 也只有 7.8 GiB，均不满足。

如果必须让数据留在腾讯云私网内并通过 UI 观察完整 Trace，应准备独立 Langfuse 主机：

- 官方单机入门建议：至少 4 vCPU / 16 GiB RAM / 约 100 GiB 持久盘。
- 由于完整组件最低值约 9 CPU / 25.5 GiB RAM，若 PostgreSQL、ClickHouse、Redis、对象存储都自托管，实际建议至少 8 vCPU / 32 GiB RAM，并为 ClickHouse 和对象存储单独规划磁盘。
- 若使用外部托管 S3、PostgreSQL、ClickHouse 和 Redis，4 vCPU / 16 GiB 可以作为低吞吐验证起点，但仍应配置 trace retention、ClickHouse TTL、日志轮转和备份。
- Langfuse UI 只绑定私网或 loopback，通过 SSH 隧道访问；不应为了调试把 3000、9090 或数据库端口暴露公网。

### 推荐的实际方案

| 目标 | 方案 | 是否适合当前 CVM |
|---|---|---|
| 立即排障并观察完整模型细节 | Langfuse Cloud + 受控 OTLP exporter | 技术可行；需按本次授权配置数据外发 |
| 业务数据必须留在 CVM 私网 | 新建独立 Langfuse CVM，mRoleScope 通过私网 OTLP 发送 | 当前 CVM 不可行；扩容或新建实例后可行 |
| 只在 CVM 上运行一个轻量服务 | OTLP collector/转发端，不运行 Langfuse UI | 可行，但 UI 在别处 |
| 把完整 Langfuse Compose 加到现有 CVM | 复用现有 2c/2GiB 主机 | 不可行 |
| 把完整 Langfuse Compose 加到开发机 227 | 复用现有 4c/8GiB 主机 | 不可行，且会与 14 个容器和测试卷争抢资源 |

对当前项目最合理的顺序是：先在代码层定义 Langfuse/OTel trace seam，只在受控 Debug run 发完整 payload；评测初期使用 Langfuse Cloud 或临时独立实例；如果确认需要长期保留未脱敏 Trace，再购买独立 CVM 并将平台与 mRoleScope 主服务隔离。不要为了节省一台机器，把 Langfuse 后端塞入当前 CVM 或 227。

本轮只核对了官方 OTLP 字段映射和部署边界，没有创建 Langfuse 项目、配置 API key、发送业务数据或启动第三方容器。
