# AI 作图开发决策

> 本文记录 AI 作图功能在 OpenSpec Explore 阶段形成的事实、判断、决策和未决问题。
> 每轮探索完成后追加记录，避免后续设计遗漏已经确认的边界。

## 文档信息

- 功能：AI 作图
- 阶段：Explore，尚未进入实现
- 首次记录：2026-11-18
- 对应指导：`Docs/开发指导/AI作图_01/AI作图开发指导.md`

## 第一轮：现状与一期边界

### 已确认事实

1. 当前系统已经具备趋势看板和曲线配置能力，支持技术关键词、岗位族、项目、工作地点、学历、工作年限及自定义时间范围等维度。
2. 当前系统已有受控 AI 语义分析能力，但它面向单个 JD 的学历、经验和技术要求抽取，不等同于面向用户的自然语言作图能力。
3. 现有 AI 语义分析已经具备版本化配置、受控输入、严格结构化输出、预算限制和审计机制。AI 作图应优先复用这些工程边界，而不是建立第二套不受控的 AI 数据链路。
4. 趋势看板的统计和历史重建由 Serving 层与现有趋势 API 负责。AI 不应自行统计岗位数量，也不应直接查询数据库或改写数据。
5. 当前没有现成的 AI 作图用户入口，也没有现成的 AI 作图 OpenSpec change 或正式 spec。

### 推荐的一期交互边界

一期采用“自然语言问题 -> 曲线配置草稿 -> 用户确认 -> 现有趋势看板绘图”的单轮流程：

```text
用户输入自然语言问题
        |
        v
AI 理解意图并提取必要参数
        |
        v
生成最多 8 条曲线配置草稿 + 简短说明
        |
        v
用户手动添加、删除或修改曲线
        |
        v
用户点击应用
        |
        v
复用现有趋势 API 和曲线绘制能力
```

例如用户输入：

> 我想了解 MHY 当前使用的游戏引擎

AI 可以生成以下曲线草稿：

- Unity
- Unreal Engine
- Unreal Engine 4
- Unreal Engine 5

用户可以删除不需要的曲线，或者补充其他曲线；只有用户点击“应用”后，配置才进入趋势看板。

### 一期边界建议

- AI 只负责理解用户意图、提取参数、选择候选曲线并生成说明。
- AI 最多生成 8 条曲线配置。
- AI 不直接执行任意 SQL。
- AI 不直接修改数据库。
- AI 不直接替用户应用结果。
- 实际统计、历史数据读取、同比环比计算和绘图全部复用现有 Serving API 与前端曲线能力。
- 一期暂不引入连续多轮聊天；用户可以先修改 AI 草稿，再应用到趋势看板。

### 本轮未决问题

后续需要先确认一期是否正式采用上述单轮模式。该决定会影响：

- AI 请求接口的生命周期
- 草稿的保存方式
- 是否需要会话状态
- 是否需要连续对话记忆
- AI 调用成本和审计容量
- 前端入口和确认交互

## 当前状态

- 已确认：AI 作图应作为现有趋势能力之上的受控推荐层。
- 已确认：AI 不应替代现有统计和绘图逻辑。
- 已确认：一期采用单轮草稿模式。
- 已确认：一期最多生成 8 条曲线草稿及说明，用户手动调整并点击应用后才进入趋势看板。

## 第二轮：单轮草稿模式确认

用户确认一期采用以下流程：

```text
自然语言问题
    -> AI 生成最多 8 条曲线草稿和说明
    -> 用户手动添加、删除、修改
    -> 用户点击应用
    -> 现有趋势看板绘图
```

该决定明确了 AI 的角色是“推荐配置”，不是“自动操作员”。AI 不能在用户尚未确认时改变当前看板，也不能绕过现有 Serving 统计逻辑自行计算结果。

## 第二轮待决问题

指导文档中的“目前投入最多的项目”与“使用哪些后台数据库”不是同一种需求：

```text
简单需求：画出 C++、Unity、PostgreSQL
    -> AI 只需识别维度和值

排名需求：目前投入最多的项目
    -> AI 需要枚举候选项目
    -> 按统一口径统计岗位数量
    -> 排序并选出前若干项
    -> 生成曲线草稿
```

因此下一步需要确认：动态排名是否属于一期能力，以及“最多”的统计口径是否定义为“当前最新成功观察中仍有效岗位的数量”。

## 第三轮：复杂二次指标的设计方向

用户提出了“增长最快”“变化最大”等复杂二次指标的设计问题。本轮形成以下分析结论。

### 复杂指标不应由模型直接计算

模型适合把自然语言转换成结构化分析意图，但不适合直接对岗位历史数据做最终计算：

```text
用户问题
    |
    v
AI：识别指标、维度、时间范围和排序意图
    |
    v
受控校验器：检查枚举、范围、数量和歧义
    |
    v
确定性分析服务：读取正式历史数据并计算
    |
    v
曲线草稿或二次指标结果
```

这样可以避免模型把“岗位数量”“事件数量”“同比增长率”混为一谈，也可以保证同一个问题每次得到相同的计算结果。

### 建议的结构化分析意图

AI 只输出受控的分析计划，不输出自行计算的数字。分析计划至少需要表达：

- 指标类型：岗位数量、绝对变化、变化率、事件数量、排名等。
- 数据维度：技术关键词、项目、岗位族、工作地点等。
- 统计对象：当前有效岗位、历史观察岗位、进入曲线、修改、下线、重上线等。
- 当前周期和比较周期：当前、环比、同比或用户指定的日期范围。
- 排序方向：从高到低或从低到高。
- 结果数量：最多 8 条曲线。
- 输出方式：用指标选择曲线，或直接绘制二次指标曲线。

### 需要明确区分的三类指标

#### 1. 存量指标

表示某个周期或某个观察日有多少岗位符合条件。

例如：

> 当前使用最多的游戏引擎

可以定义为：最新成功观察中，仍有效且匹配某个技术关键词的去重岗位数量。

#### 2. 流量指标

表示周期内发生了多少事件。

例如：

> 哪些项目最近新增岗位最多

可以定义为：周期内“进入曲线”的去重岗位数量，必要时再明确是否包含修改后新归属到该项目的岗位。

#### 3. 变化指标

表示两个周期之间的差异。

例如：

> 哪些技术关键词增长最快

至少要先明确是：

- 绝对变化：当前岗位数 - 对比周期岗位数。
- 相对变化：
  `(当前岗位数 - 对比周期岗位数) / 对比周期岗位数`。
- 事件变化：新增、修改、下线或重上线数量的差异。

“变化最大”本身不能直接交给模型猜测，必须转换成上述某一种正式口径；如果用户没有说明，应要求用户选择或采用界面明确展示的默认口径。

### 边界规则

复杂指标必须继续复用现有趋势数据规则：

- 缺失日期保持不可用，不伪造为 0；允许分析服务按照已有最大努力原则跳过缺失日。
- 完整观测中的真实 0 仍然是合法数据。
- 比较周期分母为 0 时，变化率显示 `-`，不能生成无穷大。
- 首次历史基线沿用现有规则：2026-10-22 首次观察到的数据可以参与统计。
- 排名必须使用统一的确定性排序和并列处理规则。
- “增长最快”需要防止小样本误导，例如 1 个岗位增长到 2 个岗位不能无条件压过 100 个增长到 150 个岗位的条件；可采用最低基数、同时展示绝对变化，或要求用户选择指标。

### 推荐分阶段支持

复杂指标可以分为两个阶段，避免一期同时重构曲线 API 和图表语义。

#### 阶段 A：二次指标只用于选择曲线

例如：

> 当前岗位数量增长最多的 5 个项目

系统先计算排名，选择出 5 个项目；随后仍使用现有趋势曲线绘制每个项目的每日岗位数量。

```text
排名结果：项目 A、项目 B、项目 C、项目 D、项目 E
                    |
                    v
现有项目曲线：展示每日岗位数量变化
```

优点是可以复用现有最多 8 条曲线、历史缺失、下钻和事件统计能力，用户也能继续查看原始曲线事实。

#### 阶段 B：二次指标本身作为图表数据

例如直接绘制：

- 每个项目的环比增长率曲线。
- 每个技术关键词的岗位数量绝对变化曲线。
- 每个项目的新增/下线事件趋势曲线。

这不是普通曲线配置的简单扩展，因为图表的 Y 轴含义从“岗位数量”变成了“百分比”或“事件数量”。届时需要新增：

- 二次指标的公开数据契约。
- 指标单位和 Y 轴语义。
- 分母为 0、缺失周期、基线不足等状态。
- 指标曲线的下钻语义。
- 与现有岗位数量曲线的视觉区分。

### 本轮推荐

先采用“阶段 A”：复杂指标用于确定哪些曲线值得展示，但最终仍绘制现有岗位数量曲线。阶段 B 作为独立能力规划，不把增长率和岗位数量混在同一张普通曲线里。

### 本轮待决问题

需要确认复杂指标是否分两阶段实现：

1. 先支持“根据增长、变化或事件排名选择曲线”，曲线本身仍展示岗位数量。
2. 后续再支持“直接绘制增长率、绝对变化或事件数量曲线”。

## 第四轮：阶段 A 确认与 AI 框架调研

### 已确认决策

用户同意采用阶段 A：

- 复杂指标先用于筛选、排序和选择曲线。
- 选出的曲线仍使用现有趋势看板绘制每日岗位数量。
- 直接绘制增长率、绝对变化和事件数量曲线留到后续独立能力。

### 新增调研点

需要评估是否引入成熟 AI 框架，例如 LangChain 或 LangGraph，以支持：

- AI 自动发现并调用 MCP 或 function 工具。
- 记录实际调用过的工具和工作流程。
- 处理多次模型调用、工具结果回传和失败重试。

### 与当前代码的对照

当前项目已经具备一套较窄但受控的 AI 基础设施：

- Go 服务内已有 OpenAI 兼容的 Qwen 客户端。
- 已有严格 JSON Schema 响应校验。
- 已有固定模型配置、输入输出 token 限制、重试策略和安全错误分类。
- 已有预算预留、审计记录和输出审计边界。
- 当前没有 LangChain、LangGraph 或 MCP 运行时依赖。

因此，框架调研不能只比较功能数量，还必须比较它是否会破坏当前的安全边界、成本边界和可测试性。

### 初步架构选项

#### 选项 A：Go 内部受控编排器

```text
Go API
  -> Qwen 结构化意图解析
  -> Go 工具注册表
  -> 确定性排名/聚合服务
  -> 曲线草稿
```

优点：依赖少、易于限制工具集合、易于测试和审计，最符合一期单轮草稿模式。

#### 选项 B：MCP 工具边界 + 自有编排器

```text
Go API
  -> Qwen 意图解析
  -> MCP 适配层
  -> 受控数据工具
  -> 确定性分析结果
```

MCP 可以提供标准化工具描述和调用边界，但本项目仍需自己负责权限、参数校验、超时、结果大小和审计。引入 MCP 不会自动解决这些问题。

#### 选项 C：LangChain/LangGraph 等框架

框架可以提供工具调用循环、状态图和流程编排，但也会增加：

- 运行时依赖和镜像体积。
- 多语言或额外服务边界。
- 隐式重试、隐式上下文和不可预测的模型调用次数。
- 需要重新适配现有预算、审计、超时和安全错误机制。

对于一期“单次请求生成草稿”的目标，暂时看不到必须引入完整 Agent 框架的理由。

### 初步推荐

一期优先采用选项 A：保留当前 Go + 受控 Qwen 客户端，在服务内增加明确的工具注册表和分析计划执行器。工具调用轨迹由项目自己记录，不依赖框架提供的黑盒 tracing。

如果后续出现以下需求，再重新评估选项 B 或 C：

- 工具数量明显增加且需要跨服务发现。
- 一个请求需要多轮工具调用和条件分支。
- 需要可视化、暂停、恢复复杂工作流。
- 多个模型或多个 Agent 需要共享标准化工具协议。

### 本轮待决问题

是否同意一期暂不引入 LangChain/LangGraph，先采用现有 Go 服务内的受控编排器；MCP 作为后续工具标准化方向单独调研，不作为一期运行时前置依赖？

## 第五轮：时间范围采用现有看板能力

### 已确认决策

用户同意：

- 一期不引入 LangChain/LangGraph。
- 一期不把 MCP 作为运行时前置依赖。
- 一期采用现有 Go 服务内的受控编排器和明确的工具注册表。
- MCP 保留为后续跨进程、跨语言和多客户端工具标准化方向。

### 用户对复杂时间语义的简化决定

用户认为不需要把时间维度设计成复杂的追问流程。AI 作图直接复用现有看板的时间范围能力：

```text
“目前使用哪些技术？”
“正在进行的项目有哪些？”
“最近变化最大的项目是什么？”
```

### 简化后的规则

1. 用户明确给出时间范围时，AI 使用该范围：
   - 可以使用现有的本周、本月、本季度、本年。
   - 也可以使用现有的自定义日期范围。
   - 不需要再询问用户确认周期含义。
2. 用户没有给出明确时间范围时，不询问、不深究时间维度：
   - 直接沿用趋势看板现有默认周期。
   - 当前看板默认周期为本周。
   - 用户应用曲线后，仍可以像手动配置曲线一样切换本周、本月、本季度、本年或自定义范围。
3. “目前”“当前”“正在进行”等词不触发额外的时间追问；它们只帮助 AI 理解用户想查看当前有效岗位或当前状态。
4. 排名、聚合和事件统计仍必须调用确定性后端方法，但时间范围不作为对话阻断条件。

### 需要坚持的历史事实边界

- 最新数据必须来自最新成功发布的观察，而不是请求发生时临时抓取的数据。
- 历史数据必须复用现有正式趋势解释和岗位历史逻辑。
- 缺失日期保持不可用，不伪造为 0。
- 手动修补后的日期和正常同步日期使用同一套统计接口，不向用户暴露修补来源。

### 本轮结果

- 已确认：明确时间范围时使用现有预设或自定义范围。
- 已确认：没有明确时间范围时不向用户追问。
- 已确认：未指定时间范围时沿用趋势看板默认周期。
- 已确认：用户应用后仍可在看板中自由切换已有周期。

## 第六轮：技术词典更新与 AI 作图同步

### 已确认决策

用户确认 AI 作图必须遵循现有技术词典更新规则：

- AI 作图只使用当前已发布的最新技术词典和分析配置。
- AI 作图不得内置一份独立的技术关键词列表。
- AI 生成技术曲线时，候选值必须来自与岗位筛选相同的 active technology publication。
- 技术词典更新完成并正式发布后，AI 作图、岗位筛选、岗位详情、趋势看板等功能都应同步使用新版本结果。
- 候选词典或未完成分析结果不能提前出现在 AI 草稿、技术筛选或趋势曲线中。
- 新版本发布失败时，继续使用上一版完整的 active 配置，不显示混合版本结果。

### 推荐的同步方式

AI 作图不直接读取词典文件，也不把完整词典长期放入模型上下文，而是调用与筛选选项相同的数据边界：

```text
技术词典候选
    |
    v
历史重算与完整性校验
    |
    v
原子切换 active technology publication
    |
    +--> 岗位筛选选项
    +--> 岗位详情技术结果
    +--> 趋势正式解释
    +--> AI 作图可用技术候选
```

AI 作图工具可以按需读取当前可用技术值，或者让确定性排名工具直接在 active 结果上筛选，避免模型接收过大的完整词典上下文。

### 缓存和并发边界

- AI 工具不得使用没有版本边界的长期内存词典缓存。
- 如果为了性能缓存技术候选，缓存必须绑定 active publication 的新鲜度标识。
- 词典正式发布后，旧候选缓存必须失效，新的 AI 请求只能看到新版本。
- 词典发布过程中的候选配置继续不可见，直到发布事务完成。
- AI 草稿在真正应用时仍需重新校验曲线值是否属于当前 active 配置，防止草稿生成后词典发生升级。

### 本轮待决问题

需要继续确定：技术词典升级后，已经生成但尚未应用的 AI 草稿，以及已经显示在看板中的旧曲线，分别如何处理。推荐在应用时重新校验，失效值显示为不可用并要求用户调整，不静默替换为其他技术。

## 第七轮：词典升级后的草稿和旧曲线

### 已确认决策

用户同意技术词典升级后的处理方式：

#### 尚未应用的 AI 草稿

- 在用户点击应用时重新校验所有曲线值。
- 仍属于当前 active 词典的值继续保留。
- 已从当前词典移除的值标记为不可用。
- 不自动替换为相似技术，不静默改变用户意图。
- 用户可以删除失效值、手动补充新值或重新生成草稿。

#### 已经显示的曲线

- 词典发布后再次读取时使用最新技术分析配置和趋势正式解释。
- 仍有效的值正常重新绘制。
- 已失效的值显示当前词典不可用状态。
- 不回退到旧词典结果，不混合新旧分析结果，不自动替换曲线。

### 下一项设计问题

需要确定 AI 与数据工具之间的调用方式。为了满足速度、成本和安全要求，建议不要让模型自由循环调用任意工具，而是采用固定工具集合和 Go 编排器：

```text
Qwen：输出结构化用户意图
    |
    v
Go 编排器：根据意图选择白名单工具
    |
    +--> 查询可用维度和值
    +--> 计算排名和聚合
    +--> 读取趋势或事件摘要
    |
    v
Go 校验器：生成最多 8 条曲线草稿
```

模型可以表达“按项目岗位数排序”或“选择前 5 条”，但不直接决定 SQL、表名、连接方式或任意工具参数。

### 本轮待决问题

是否同意一期采用“模型输出结构化意图，Go 编排器调用固定白名单工具”的方式，而不是让模型自主进行多轮任意工具调用？

## 第八轮：结构化意图与固定工具编排

### 已确认决策

用户同意一期采用固定白名单工具编排：

- 模型只输出结构化用户意图。
- Go 编排器根据意图选择允许调用的工具。
- 工具集合由服务端固定注册，模型不能创建工具或调用任意方法。
- 工具参数经过服务端 schema 校验、范围限制和当前 active 数据校验。
- 模型不能直接访问 SQL、数据库连接、内部表名或运行时密钥。
- 工具调用次数、超时、返回结果大小和总 token 消耗由服务端控制。
- 最终曲线草稿由服务端校验并限制为最多 8 条。

### 推荐的结构化意图内容

一期意图对象可以包含：

- 用户想看的数据维度。
- 用户请求的指标类型。
- 是否需要排名或聚合。
- 排序方向和最多返回数量。
- 用户明确提供的时间范围；未提供时使用看板默认周期。
- 是否需要比较、事件或趋势摘要。
- AI 对用户问题的简短解释。

意图对象不应包含 SQL、任意函数名、任意数据库字段或模型自行计算出的最终统计数字。

### 推荐的最小工具类别

- `list_available_values`：读取当前 active 配置下可用的技术、项目、岗位族和地点值。
- `rank_values`：按确定性指标对一个维度的现有值排序。
- `read_trend_summary`：读取候选曲线的已有趋势摘要。
- `read_event_summary`：读取进入、修改、下线、重上线等已有事件统计。
- `validate_curve_draft`：检查值、维度、时间范围和最多 8 条曲线限制。

这些工具返回展示安全的结构化结果，不返回 JD 正文、数据库标识、内部版本号或敏感诊断信息。

### 下一项设计问题

当前趋势看板支持技术关键词、岗位族、学历、项目、工作地点和工作年限等多个维度，但 AI 作图是否需要一期全部覆盖，仍需要单独确定。维度范围会直接影响意图 schema、工具数量、提示词和验收样本。

### 本轮待决问题

是否同意一期 AI 作图先支持全部现有趋势维度，还是先限定为技术关键词、项目、岗位族和工作地点四类更适合排名与曲线展示的维度？

## 第九轮：一期维度范围

### 已确认决策

用户同意一期先支持四类维度：

- 技术关键词
- 项目
- 岗位族
- 工作地点

学历和工作年限暂不纳入 AI 自动作图，保留给后续独立设计。现有手动曲线配置和趋势看板能力不受影响。

### 范围原因

四类首期维度都可以直接复用现有结构化值、筛选选项、岗位数量趋势和事件统计。学历和工作年限涉及数值比较、最低要求、区间、未配置状态和正式资格语义，后续需要单独定义自然语言口径。

### 下一项设计问题

需要确定 AI 作图入口的产品范围。AI 生成的是趋势曲线草稿，因此最小闭环可以只放在趋势看板：

```text
趋势看板
  -> 输入自然语言问题
  -> 查看 AI 曲线草稿
  -> 手动调整
  -> 应用到当前趋势看板
```

如果做成全站聊天入口，则还需要设计岗位筛选、岗位详情、岗位历史等页面如何理解和响应 AI 请求，范围会显著扩大。

### 本轮待决问题

一期 AI 作图是否只在趋势看板提供入口，并将输出限制为趋势曲线草稿，不做全站通用聊天入口？

## 第十轮：AI 作图入口范围

### 已确认决策

用户同意一期只在趋势看板提供 AI 作图入口：

- AI 输入和结果都属于趋势看板上下文。
- 输出限制为最多 8 条趋势曲线草稿和简短说明。
- 不建设全站通用聊天入口。
- 不在岗位筛选、岗位详情或岗位历史页面引入 AI 作图对话。
- AI 结果在用户确认前不改变当前已应用曲线。

### 推荐的页面关系

```text
趋势看板
  +--> 当前已应用曲线
  +--> AI 作图输入
  |       |
  |       v
  |    待确认草稿
  |       |
  |       +--> 修改草稿
  |       +--> 应用草稿
  |
  +--> 现有手动配置曲线
```

AI 草稿应与当前已应用曲线分开显示，避免模型请求返回时覆盖用户正在查看的图表。

### 下一项设计问题

当用户已经配置了曲线时，AI 草稿应用可能有两种语义：

- 替换：用 AI 草稿整体替换当前曲线。
- 追加：保留当前曲线，将 AI 草稿加入当前配置，超过 8 条时由用户处理冲突。

两种语义会直接影响按钮文案、草稿预览、最多 8 条限制和用户误操作风险。

### 本轮待决问题

AI 草稿应用到已有曲线时，应默认替换当前曲线，还是默认追加到当前曲线？

## 第十一轮：AI 草稿应用方式

### 已确认决策

用户同意不设置隐藏的替换或追加默认值：

- 当前没有已应用曲线时，显示“应用草稿”。
- 当前已有曲线时，明确提供“应用并替换当前曲线”。
- 当前已有曲线时，明确提供“追加到当前曲线”。
- 追加后超过 8 条曲线时，必须明确提示容量冲突，不得静默丢弃或自动替换曲线。
- AI 草稿确认前不改变当前已应用曲线。

### 下一项设计问题：审计内容和容量

AI 作图需要保留足够信息来优化意图识别、工具选择和失败原因，但不能把每次请求的完整上下文、完整工具结果和模型原始输出无限保存。

推荐将审计拆成有限大小的安全记录：

- 请求的不可逆哈希和时间。
- 结构化意图及其校验结果。
- 实际调用的白名单工具名称、状态和耗时。
- 工具返回的数量摘要或安全错误分类，不保存完整 JD 正文和完整数据库结果。
- 生成的曲线草稿摘要。
- 模型调用次数、输入输出 token 数、总耗时和最终状态。
- 失败时的安全错误代码，不保存密钥、连接串、原始响应或敏感诊断。

原始用户问题是否需要保存、保存多久、是否允许抽样保存，仍需单独决定。审计记录必须有明确的大小上限、保留期限和清理策略，不能因为 AI 作图请求增长造成数据库容量或查询等待问题。

### 本轮待决问题

是否同意一期只保存“结构化意图、白名单工具调用摘要、曲线草稿摘要、耗时/token/安全错误”等有界审计信息，不保存完整用户原文、完整工具结果和模型原始响应？

## 第十二轮：AI 作图审计内容

### 已确认决策

用户同意一期只保存有界的 AI 作图审计摘要，不保存完整请求和完整模型上下文：

- 保存请求的不可逆哈希和发生时间，用于识别重复请求与追踪时间范围，不保存可还原的用户原文。
- 保存模型输出的结构化意图及其校验结果，用于判断请求是否被正确解析和拦截。
- 保存实际调用的白名单工具名称、成功/失败状态、耗时和安全错误代码。
- 保存统计结果摘要和曲线草稿摘要，不保存完整岗位结果、完整 JD 正文或完整数据库返回值。
- 保存模型调用次数、输入/输出 token 数、总耗时和最终状态。
- 不保存模型原始响应全文、密钥、连接串、内部诊断信息或其他敏感材料。
- 不因单条 AI 请求或单个工具失败阻断其他请求；失败只形成可审计的安全摘要并向用户返回可理解的失败提示。

### 数据边界

审计摘要只服务于问题定位、容量控制和产品质量改进，不作为面向用户的业务数据展示。前端不得展示 AI、词典/解析器版本、覆盖率、回退量、审计状态或内部错误细节。

### 下一项设计问题：保留与清理

审计记录不能无限增长，需要同时规定保存多久、最多保存多少条，以及达到上限后的清理行为。为了保持一期实现简单，建议采用时间和数量双重上限：

```text
保留最近 30 天，且最多保留固定数量的记录；
达到任一上限时删除最旧记录；
清理失败只告警，不阻断 AI 作图。
```

### 本轮待决问题

是否同意一期按“保留 30 天 + 固定最大记录数”的双重上限清理审计摘要，并在清理失败时只告警、不阻断 AI 作图？

## 第十三轮：AI 作图审计保留策略

### 已确认决策

用户同意一期采用时间和数量双重上限：

- 审计摘要最多保留最近 30 天。
- 审计摘要最多保留 10,000 条。
- 任一上限达到时，删除最旧的记录，优先保证新请求可以继续使用。
- 清理失败只产生运维告警，不阻断 AI 作图，也不把清理失败展示为业务错误。
- 审计写入或清理异常不得扩散为趋势看板或其他岗位服务的整批失败。

### 下一项设计问题：固定工具白名单

下一步需要明确 AI 编排器究竟可以调用哪些工具。这里的“工具”不是让模型直接访问数据库，而是服务端提供的几个固定、安全的查询能力。

可以把它理解成餐厅菜单：模型只能从菜单中点菜，不能自己走进后厨拿食材。每个工具都应当有固定参数、固定返回结构和固定数据范围。

一期建议至少包括：

- 获取当前有效技术关键词选项。
- 获取当前有效项目选项。
- 获取当前有效岗位族选项。
- 获取当前有效工作地点选项。
- 按一个已校验的维度和值生成普通岗位数量趋势数据。
- 批量生成最多 8 条已校验曲线的趋势数据。

模型不能调用任意 SQL、读取数据库表、读取 JD 正文、访问密钥或自行创造技术关键词。

### 本轮待决问题

是否同意一期只允许 AI 编排器调用上述固定白名单工具，并且所有参数必须经过服务端 schema、数量范围和最新有效词典校验？

## 第十四轮：复杂聚合、排序与二次指标

### 设计澄清

前一轮列出的工具不是“只能逐条查询的六个按钮”，而是一期最小的安全基础能力。固定白名单还可以包含服务端实现的高层分析工具，只要工具的指标、参数和返回结构都是预先定义的，模型不能把它们扩展成任意 SQL 或任意聚合。

可以把它理解成餐厅菜单：

- 简单趋势查询是“做一份 C++ 岗位数量曲线”。
- 复杂聚合工具是“统计所有技术关键词，并找出增长最快的前 5 个”。
- 模型只能点菜单里的菜，不能进入后厨自行取数据库、改写配方或临时发明一条 SQL。

### 一期的复杂分析方式

一期仍然遵守“复杂指标用于筛选/排序，最终绘制普通岗位数量曲线”的决策。服务端可以增加以下受控分析能力：

- 枚举一个维度下的候选值：候选值必须来自当前有效技术词典或现有筛选选项。
- 按固定指标聚合候选值：例如当前周期岗位数、进入数量、修改数量、下线数量、重上线数量。
- 计算固定的变化指标：例如绝对变化、同比变化、环比变化及其百分比。
- 按指定方向排序，并限制最多返回 8 条曲线候选。
- 返回候选曲线、排序指标摘要和简短的可读说明，再由现有趋势接口生成普通岗位数量曲线。

例如用户输入：

> “找出本季度进入岗位最多的 5 个技术关键词，并画出它们的趋势。”

服务端应当执行：

1. 从最新技术词典中取得全部有效技术关键词。
2. 使用已有事件统计口径计算每个关键词本季度的进入数量。
3. 按进入数量从高到低排序，取前 5 个。
4. 对这 5 个关键词重新生成普通的每日岗位数量曲线。
5. 把“按进入数量排序”作为说明展示给用户，但不把进入数量冒充成曲线纵轴。

再例如：

> “展示岗位数环比增长最快的 3 个项目。”

一期可以用环比增长率筛选出 3 个项目，但图表仍显示这 3 个项目的普通每日岗位数量；环比增长率只作为筛选依据，不直接作为图表曲线。

### 需要严格区分的三类数据

- **存量指标**：某日或某个时点仍有效的岗位数量，不能把每日岗位数简单相加。
- **流量指标**：周期内新增、修改、下线、重上线等事件数量，可以按既有事件去重口径聚合。
- **变化指标**：当前周期与环比/同比周期之间的绝对差或百分比差，分母为 0 时按现有规则展示为 `-`。

因此，“本月岗位最多”“本月进入最多”和“环比增长最快”不是同一种排序，必须在结构化意图中使用不同的固定指标枚举，不能靠模型自由解释。

### 二期再支持直接绘制二次指标

如果未来要直接绘制“进入数量曲线”“环比百分比曲线”或“修改数量曲线”，需要单独扩展趋势数据契约：

- 明确曲线的指标类型和单位。
- 定义缺失日期、分母为 0 和不可比周期的展示规则。
- 调整纵轴、图例、悬浮提示、下钻语义和导出结构。
- 保证普通岗位数量曲线与事件/变化曲线不会在同一坐标轴上产生误读。

这属于新的图表数据能力，不应在一期通过自然语言说明或前端临时计算伪装实现。

### 失败与边界

- 候选值为空时返回“没有匹配候选”，不创造新词或静默替换为其他值。
- 某些候选值的历史数据不足时，按既有缺失日静默跳过规则处理，不制造虚假事件。
- 排序结果超过 8 条时只返回前 8 条，并明确告知用户还有更多候选，不静默丢弃排序规则。
- 复杂分析工具超时或局部失败时，返回安全错误摘要，不允许模型退化为自由 SQL。

### 本轮待决问题

是否同意采用“服务端固定分析工具 + 结构化指标枚举”的方式支持复杂聚合和排序：一期允许复杂指标用于选择最多 8 条普通岗位数量曲线，但不直接绘制二次指标曲线？

## 第十五轮：复杂指标仅用于曲线选择

### 已确认决策

用户同意一期采用两阶段方案：

- 复杂聚合、排序和二次指标由服务端固定分析工具执行，不由模型自由计算，也不由前端临时拼接。
- 复杂指标可以用于筛选、排序和选择最多 8 条曲线。
- 最终展示仍使用普通的每日岗位数量曲线。
- 一期不直接绘制进入数量、修改数量、下线数量、重上线数量、同比百分比或环比百分比曲线。
- 一期不允许模型访问任意 SQL、数据库表、完整 JD 正文、密钥或连接串。
- 所有复杂分析必须复用已有的事件统计、历史岗位和最新技术词典口径。

### 处理示例

```text
“找出本季度进入数量最多的 5 个技术关键词”
  -> 统计每个技术关键词的进入数量
  -> 排序并取前 5 个
  -> 绘制这 5 个关键词的普通岗位数量曲线
```

```text
“找出环比增长最快的 3 个项目”
  -> 计算项目的环比变化指标
  -> 排序并取前 3 个
  -> 绘制这 3 个项目的普通岗位数量曲线
```

### 下一项设计问题：固定指标枚举

复杂指标不能只依靠自然语言理解，还必须有正式的枚举名称和计算口径。特别是“岗位最多”存在多种可能含义：

- 看当前周期最后一个成功观察日的岗位数。
- 看当前周期内每日岗位数的平均值。
- 看当前周期内岗位数的峰值。
- 看周期内曾经出现过的去重岗位数。

这几种口径得出的排序可能完全不同。例如一个技术关键词月初数量很高、月底已经下降，另一个关键词每天都比较稳定；用“峰值”和“平均值”排序，结果可能不一样。

### 本轮待决问题

是否同意下一步先把一期允许的排序指标逐项列出来，并为每个指标确定唯一口径；在口径未确定前，不让 AI 自由解释“最多”“增长最快”“变化最大”等词？

## 第十六轮：岗位数量排序的默认口径

### 设计拆分

为了避免“岗位最多”被模型自由解释，建议把岗位数量相关说法固定映射为以下几种指标：

- **周期内平均岗位数**：计算周期内所有成功观察日的岗位数量平均值，缺失日静默跳过。适合用户说“本月岗位最多”“整体岗位量最高”。
- **周期末岗位数**：取周期内最后一个成功观察日的岗位数量。适合用户说“截至目前”“现在岗位最多”。
- **周期峰值岗位数**：取周期内单日岗位数量的最高值。适合用户说“最高峰”“最高一天”。
- **周期内去重岗位数**：统计岗位在周期内曾经出现过的去重数量。只有用户明确说“期间出现过多少个不同岗位”时使用，不作为普通“岗位最多”的默认口径。

这些指标不能混用。例如：

```text
C++：月初 100 个，之后逐步下降，月底 20 个
Unity：每天约 60 个
```

- 按周期峰值排序，C++ 排在前面。
- 按周期平均值排序，Unity 可能排在前面。
- 按周期末排序，Unity 明显排在前面。

因此，必须先确定没有修饰词时的默认含义。

### 推荐默认规则

当用户只说“本月岗位最多的技术关键词”而没有说“截至目前”“峰值”或“出现过”，建议默认使用**周期内平均岗位数**：

- 不会被某一天的短时异常峰值主导。
- 更能代表整个周期的岗位供给水平。
- 对少量缺失观察日可以沿用“缺失日静默跳过”规则。
- 不会把每日独立岗位观察错误地累加成收入式总量。

### 本轮待决问题

是否同意：没有额外修饰时，“岗位最多/数量最高”默认按周期内平均岗位数排序；“截至目前”按周期末岗位数，“峰值/最高一天”按周期峰值，“期间出现过的不同岗位”才按周期内去重岗位数？

## 第十七轮：约束 AI 指标理解的方式

### 设计澄清

不能只依靠 Prompt 约束 AI 理解“周期内平均岗位数”。Prompt 只能告诉模型应该怎么理解，不能保证模型每次都遵守；真正的业务口径必须由服务端的结构化协议和确定性代码兜底。

可以把 Prompt 理解成“给 AI 的操作说明”，把服务端校验理解成“收银台和门禁”：即使 AI 误解了说明，也不能把不合法的指标提交到数据层。

### 推荐的四层约束

#### 1. Prompt 说明规则

Prompt 明确告诉模型：

- 用户没有额外修饰时，“岗位最多”对应 `avg_daily_active_jobs`。
- “截至目前”对应 `period_end_active_jobs`。
- “峰值/最高一天”对应 `peak_daily_active_jobs`。
- “期间出现过的不同岗位”对应 `period_unique_jobs`。
- 一期最终曲线指标固定为 `daily_active_jobs`。

Prompt 只负责帮助模型更容易输出正确意图，不作为最终安全边界。

#### 2. 结构化意图 Schema

模型不能返回“我认为应该按平均值排序”这种自由文本作为执行依据，而必须输出固定结构，例如：

```json
{
  "dimension": "technology",
  "time_range": {"kind": "month"},
  "ranking": {
    "metric": "avg_daily_active_jobs",
    "order": "desc",
    "limit": 5
  },
  "output": {"series_metric": "daily_active_jobs"}
}
```

指标只能从服务端定义的枚举中选择，不能写公式、SQL、字段名或任意表达式。

#### 3. 服务端硬校验

Go 编排器在执行前必须重新校验：

- JSON 结构和字段类型是否合法。
- 指标是否属于允许的枚举。
- 维度和指标是否可以组合。
- `limit` 是否不超过 8。
- 显式技术关键词是否存在于当前 active technology publication。
- 项目、岗位族和工作地点是否存在于现有筛选选项。
- 输出曲线是否仍然是普通 `daily_active_jobs`。

如果指标缺失但用户表达属于“普通岗位最多”，服务端可以按已确认规则补成 `avg_daily_active_jobs`；如果模型输出未知指标或任意公式，则拒绝执行并返回安全错误，不能猜测或静默换成其他指标。

#### 4. 确定性分析与说明

服务端负责真正的平均值、排序、同比/环比和事件聚合计算，模型不参与数值计算。最终展示的“按周期内平均岗位数排序”说明也应由服务端根据规范化后的意图生成，不能直接相信模型生成的解释。

### 例子

用户输入：

> “找出本月岗位最多的 5 个技术关键词。”

模型即使输出了错误的 `sum_daily_active_jobs`，服务端也必须拒绝；只有 `avg_daily_active_jobs` 才能通过。

用户输入：

> “找出本月岗位数最高的一天对应的技术关键词。”

服务端应识别为 `peak_daily_active_jobs`，而不是套用默认平均值。

### 本轮待决问题

是否同意采用“Prompt 负责引导、结构化 Schema 负责表达、服务端枚举和硬校验负责约束、确定性代码负责计算与解释”的四层机制，而不是单独依赖 Prompt？

## 第十八轮：服务端校验反馈与有限重试

### 已确认决策

用户同意服务端在硬校验失败时，将经过安全处理的失败理由反馈给 AI，让 AI 尝试修正结构化意图后重试，但重试必须有明确上限。

### 重试流程

```text
用户问题
  -> AI 输出结构化意图
  -> 服务端 Schema 和业务规则校验
  -> 校验失败
      -> 可修复：返回安全错误给 AI，允许有限重试
      -> 不可修复：立即停止，返回用户可理解的失败提示
  -> 校验通过后才执行分析工具
```

服务端反馈给 AI 的应是结构化、安全的修正信息，例如：

```json
{
  "code": "INVALID_METRIC",
  "field": "ranking.metric",
  "message": "该指标不在一期允许范围内，请选择有效指标。"
}
```

不得把以下内容返回给 AI 或用户：

- 原始 SQL、表名、数据库错误堆栈或连接信息。
- 密钥、连接串、内部服务地址或内部版本号。
- 完整数据库结果、完整 JD 正文或未过滤的诊断信息。
- 可以绕过校验的内部规则细节。

### 可重试与不可重试错误

#### 可以让 AI 修正后重试

- JSON 格式错误。
- 缺少必填字段。
- 指标不在允许枚举中。
- 维度与指标组合不兼容。
- 曲线数量超过 8 条。
- 时间范围或排序方向格式不正确。

#### 不应让 AI 重试解决

- 数据库不可用。
- 最新技术词典发布不可用。
- 趋势数据服务超时。
- 服务端内部异常。
- 用户明确指定的值在当前有效选项中不存在。

后一类问题不是“换一种措辞”能够解决的，继续让 AI 重试只会增加等待时间和模型成本。

### 重试安全边界

- 每次重试只能修正结构和已知枚举，不得改变用户原始意图。
- 重试不能放宽权限、扩大数据范围或绕过最新词典校验。
- 每次尝试都记录次数、错误代码、耗时和最终状态，不保存模型原始响应。
- 只有最终通过校验的结构化意图才能调用分析工具。
- 最终失败时不应用任何曲线草稿，不改变趋势看板当前配置。

### 推荐上限

建议设置为：**首次生成 1 次，最多修正重试 2 次，总计最多 3 次 AI 尝试**。这样既能修复常见的字段错误，又能避免模型进入无限纠错循环。

例如：

```text
第 1 次：metric = sum_daily_active_jobs       -> 拒绝
第 2 次：metric = avg_daily_active_jobs       -> 通过，继续执行
```

如果第 3 次仍然失败，则结束本次请求并返回安全提示。

### 本轮待决问题

是否同意采用“最多修正重试 2 次、总计最多 3 次 AI 尝试”的上限，并仅对结构化校验错误进行重试？

## 第十九轮：有限重试确认与现有后台结构核对

### 已确认决策

用户同意采用有限重试机制：

- 首次生成 1 次，最多修正重试 2 次，总计最多 3 次 AI 尝试。
- 只有 JSON、Schema、必填字段、固定枚举、维度组合、曲线数量、时间范围和排序方向等结构化校验错误允许重试。
- 数据库不可用、趋势数据超时、最新词典不可用、用户指定值不存在和服务端内部异常不得通过再次调用 AI 解决。
- 每次尝试只允许修正结构和已知枚举，不得扩大数据范围、放宽权限或改变用户原始意图。
- 每次尝试记录次数、错误代码、耗时和最终状态，但不保存模型原始响应。
- 第三次仍未通过时结束请求，不应用曲线草稿，也不改变趋势看板当前配置。

### 远程后台结构核对

在用户授权的只读范围内，通过 SSH 检查了 CVM 当前运行环境和数据库结构。核对结果如下：

- 当前 Compose 项目位于 `/opt/mrolescope/remote-development.compose.yaml`，运行中的服务为 `api`、`web-edge` 和 `postgres`。
- Serving 趋势历史通过 `trend_formal_releases` 与不可变的 `trend_formal_release_components` 固定解释版本；数据库当前只有一个已发布趋势解释版本。
- 已有六类趋势维度：技术关键词、岗位族、学历、项目、工作地点和工作年限。技术维度通过技术分析配置身份关联，其他维度记录确定性解析器、词典或项目屏蔽版本。
- 现有趋势接口已经提供每日岗位存量曲线，以及 `entered`、`modified`、`left`、`reopened` 四类周期事件统计；接口只接受展示安全的维度和值，不接受任意 SQL 或内部版本参数。
- `aggregate_snapshots` 是已有的聚合快照表，但目前没有面向自然语言请求的 AI 趋势分析编排接口。
- 现有 `ai_analysis_*` 与 `ai_output_audit_reviews` 表属于 JD 语义分析流水线，不应直接当作用户趋势草稿的持久化协议。远程库核对到 9 次 AI 分析运行、59 次尝试和 13 条输出审阅记录。
- 远程库核对到约 184 个岗位、210 个 JD 版本、191 个正文版本、36 次采集运行、179 个技术身份和 2,547 条技术提及；本次只读取结构与计数，没有读取岗位正文或运行时凭据。

### 设计边界

AI 趋势编排应复用现有 Serving 的已发布趋势解释和安全查询能力，而不是直接读取 ODS/DWD 表、复用 JD 语义分析任务表，或绕过正式发布版本自行计算展示事实。复杂排序和二次指标可以作为服务端固定分析能力继续讨论，但其输入范围、时间口径和输出上限必须独立定义。

### 下一项设计问题：分析结果是否只生成曲线草稿

现有 Serving 已经能返回单条趋势曲线和事件统计，但 AI 请求还需要一个安全的中间结果。建议一期把 AI 的成功结果限制为：

- 最多 8 条经过服务端校验的普通 `daily_active_jobs` 曲线条件。
- 每条曲线附带服务端确定的展示标签、时间范围和选择理由摘要。
- 复杂指标（平均岗位数、周期末岗位数、峰值、进入/修改/下线/重上线、同比或环比）只用于筛选和排序曲线，不直接作为图表纵轴。
- AI 不直接返回完整 TrendSeries 数据；曲线数据仍由现有 Serving 查询生成。
- 失败或部分失败时不覆盖趋势看板上一次成功结果。

这样可以把 AI 变成“生成并解释曲线配置”的编排器，而不是第二套事实查询服务。

本轮待决问题：是否同意一期将 AI 成功结果固定为“最多 8 条经过校验的普通岗位数量曲线草稿 + 服务端生成的安全解释”，并由现有 Serving 负责实际曲线数据；AI 不直接生成或持久化 TrendSeries 数值？

## 第二十轮：AI 结果边界确认与部分成功处理

### 已确认决策

用户同意一期将 AI 定位为曲线配置编排器：

- 成功结果最多包含 8 条经过服务端校验的普通 `daily_active_jobs` 曲线条件。
- 每条曲线的展示标签、时间范围和选择理由摘要由服务端确定或生成。
- 平均岗位数、周期末岗位数、峰值、进入/修改/下线/重上线、同比和环比等复杂指标只用于筛选与排序，不直接作为图表纵轴。
- 曲线实际数值继续由现有 Serving 趋势接口生成。
- AI 不直接生成或持久化 `TrendSeries` 数值。
- AI 请求失败或部分失败时，不覆盖趋势看板上一次成功结果。

这使 AI 更像“根据用户描述整理图表配置的助手”，而不是另一套拥有数据事实的查询系统：

```text
用户描述
   -> AI 整理曲线条件
   -> 服务端校验条件和指标
   -> Serving 读取正式趋势数据
   -> 返回最多 8 条曲线草稿
```

### 下一项设计问题：一部分曲线失败时怎么办

现在需要明确“部分成功”的行为。比如用户说：

> “画本月 Go、Unity、上海和一个不存在的技术词的趋势。”

服务端校验后，可能得到：

- Go：有效
- Unity：有效
- 上海：有效
- 不存在的技术词：无效

这里有两种做法：

1. **整批失败**：因为有一条无效，四条都不生成。优点是结果整齐；缺点是一个错误会连累三个有效请求。
2. **部分成功**：生成三条有效曲线，同时明确告诉用户有一条没有找到；不擅自替换成相近词。优点是符合项目的最大努力原则；缺点是用户需要看到并处理缺失项。

建议采用第二种：只要至少有一条曲线通过校验，就返回有效曲线草稿，并在安全解释中列出未生成的条件；只有全部曲线都失败时，才把请求视为失败并保留看板原状。

本轮待决问题：当用户请求的多条曲线中只有一部分条件有效时，是否同意“保留有效曲线、明确列出失败条件、不自动替换；全部失败才整体失败”的规则？

## 第二十一轮：部分成功确认与宽匹配方向

### 已确认决策

用户同意多条曲线请求采用最大努力处理：

- 多条条件中只有部分有效时，保留有效曲线并明确列出失败条件。
- 一个无效条件不得连累其他有效条件。
- 不把不存在的值静默替换成相近值。
- 只有全部条件都无效时，才把请求视为整体失败，并保留看板原状。
- 用户希望有效匹配范围更大，可以适当牺牲匹配准确性，优先让用户看到结果。

### 当前实现的限制

现有 Serving 趋势查询本身要求规范化后的正式值。例如技术趋势最终按 `technology_key` 精确读取；它不会把“GoLang”“golang”“Go 语言”等自然表达自动当成同一个值。技术词典已有正式别名、规范名和排除规则，但这些规则属于确定性发布数据，不能由 AI 临时创造。

因此，AI 趋势编排需要增加一层“用户说法 -> 当前有效展示值”的解析，但不能把解析结果直接当成事实。可以把它理解成地图搜索：

```text
用户输入
  -> 先找精确地名
  -> 再找官方别名和格式变体
  -> 最后找相似地名
  -> 把找到的地名交给正式路线服务
```

### 下一项设计问题：宽匹配遇到多个候选时怎么办

为了扩大匹配范围，可以按以下顺序尝试：

1. 规范化后精确匹配：大小写、首尾空格、常见标点和中英文格式差异。
2. 当前正式词典或筛选选项中的别名匹配：例如 `GoLang` -> `Go`。
3. 当前有效展示值的前缀、包含关系或相似度匹配：例如 `前端` 可以找到“前端工程师”相关岗位族。

问题出现在多个候选同时接近时。例如用户说“Java”，候选可能包括：

- `Java`
- `JavaScript`
- `Java 后端`（如果岗位族或项目选项中存在）

这里有三种处理方式：

1. **只取最高分**：结果最简洁，但可能把用户想要的 JavaScript 错配成 Java。
2. **多个候选都展示**：更符合“尽量看到结果”，但可能多出不完全符合意图的曲线；每条曲线应标为“可能匹配”，不能伪装成精确匹配。
3. **遇到歧义就失败**：最准确，但会重新回到用户最不希望的“完全没有结果”。

建议采用第二种：保留多个高相似候选，每个候选显示实际匹配到的正式名称和“可能匹配”提示；单个用户条件最多展开 3 个候选，总曲线数仍受 8 条上限约束。这样即使匹配不完美，用户仍能看到可用结果，也能知道结果不是精确命中。

本轮待决问题：当一个用户说法对应多个相似的有效值时，是否同意“最多展开 3 个高相似候选、标明可能匹配、总曲线仍不超过 8 条”，而不是只选一个或直接让请求失败？

## 第二十二轮：宽匹配候选展开确认

### 已确认决策

用户同意宽匹配遇到多个相似有效值时：

- 一个用户说法最多展开 3 个高相似候选。
- 每个候选显示实际匹配到的正式名称。
- 非精确命中的候选标记为“可能匹配”，不能伪装成精确命中。
- 不因为候选有歧义就让整批请求失败。
- 整张图仍然最多 8 条曲线。

宽匹配只在当前正式词典和当前展示选项中寻找值；AI 不能创造一个数据库中不存在的新技术、岗位族、项目或地点。

### 下一项设计问题：超过 8 条时保留哪些曲线

候选展开后可能超过整张图的 8 条上限。例如用户说：

> “比较 Java、前端和上海。”

如果每个说法都找到 3 个候选，就会得到 9 条曲线。此时需要一个固定的取舍顺序，不能让 AI 随机删掉一条。

建议按以下顺序保留：

1. 精确匹配和正式别名匹配优先于模糊的“可能匹配”。
2. 用户明确说出的前一个条件优先于后一个条件。
3. 同一个说法内部按相似度从高到低保留。
4. 超过 8 条时删除最低优先级候选，并在说明中告诉用户还有候选因上限未展示。

例如：

```text
Java       -> Java（精确）、JavaScript（可能）、Java 后端（可能）
前端       -> 前端工程师（精确）、Web（可能）、UI（可能）
上海       -> 上海（精确）、上海市（可能）
```

如果总数超过 8 条，应先保留三个条件的精确结果，再按用户输入顺序和相似度补齐，而不是只保留第一个条件的全部候选。

本轮待决问题：是否同意上述“精确/别名优先、用户输入顺序其次、相似度再次、超出 8 条时明确告知被截断”的固定取舍规则？

## 第二十三轮：候选超限取舍确认与类别型问题

### 已确认决策

用户同意宽匹配候选超过 8 条时采用固定取舍：

- 精确匹配和正式别名匹配优先于模糊的“可能匹配”。
- 用户较早说出的条件优先于较晚说出的条件。
- 同一条件内部按相似度从高到低保留。
- 超过 8 条时删除最低优先级候选，并在安全说明中告知还有候选因上限未展示。
- 不让 AI 随机删曲线，也不因为候选超限而让整批请求失败。

### 现有类别事实

当前 Serving 的技术选项已经带有确定性类别，例如：

- 数据库与存储
- 模型与训练工具
- 机器学习框架
- 模型推理服务
- 图形 API 与着色语言

这些类别来自已发布技术分析配置，不是 AI 临时发挥的标签。因此用户说“后台数据库”或“模型训练工具”时，AI 可以先把自然说法映射到正式类别，再由服务端从当前有效技术值中筛选。

### 下一项设计问题：用户只说一个类别时展示什么

例如用户问：

> “米哈游现在使用哪些后台数据库？”

系统可能在“数据库与存储”类别下找到 MySQL、Redis、PostgreSQL 等多个技术值。此时有三种口径：

1. **全部列出**：只要当前有岗位提到就全部展示，可能超过 8 条，图表无法容纳。
2. **按岗位供给排序取前 8 个**：使用已确认的周期内平均岗位数排序；少于 8 个就全部展示，超过 8 个就展示前 8 个并说明还有更多。
3. **只看周期末**：按最后一个成功观察日的岗位数排序，更接近“现在”，但容易受当天缺失或短期波动影响。

建议采用第二种，因为它把“使用哪些”转成可解释的有限结果，同时沿用已经确认的默认排序口径：

```text
用户说“哪些后台数据库”
  -> 匹配正式类别“数据库与存储”
  -> 找出当前有效的数据库技术值
  -> 按周期内平均岗位数排序
  -> 最多生成 8 条普通岗位数量曲线
```

例如类别下有 3 个值就展示 3 条；有 12 个值就展示平均岗位数最高的 8 条，并明确提示“还有 4 个候选未展示”。

本轮待决问题：当用户只说“哪些/使用了哪些”类别时，是否同意从当前有效类别值中按周期内平均岗位数排序，最多展示 8 条；超过 8 条时明确提示被截断的候选数量？

## 第二十四轮：类别映射确认与自主工具编排

### 已确认决策

用户同意类别型问题采用以下口径：

- AI 可以理解“后台数据库”“模型训练工具”等自然语言类别表达。
- 服务端提供当前正式发布的技术关键词类别和类别内具体关键词列表。
- 类别内候选按周期内平均岗位数排序，最多生成 8 条普通岗位数量曲线。
- 候选超过 8 条时明确提示未展示的候选数量。

用户进一步明确：类别映射应由 AI 自主完成，我们需要提供足够全面的工具。例如：

- 返回全部正式技术关键词类别。
- 返回某个类别下的具体技术关键词列表。
- 返回某个关键词或类别的岗位数量排序。
- 返回候选曲线的趋势或事件摘要。
- 校验并生成最终曲线草稿。

### 对“自主”的边界说明

这里的自主不是让 AI 直接访问数据库，而是让它像一个会自己查资料的分析员：

```text
用户：“想知道米哈游使用哪些模型训练工具。”
   |
   v
AI 选择：查询技术类别
   |
   v
AI 选择：查询“模型与训练工具”下的关键词
   |
   v
AI 选择：按岗位供给排序
   |
   v
AI 选择：生成最多 8 条曲线草稿
```

AI 可以自主决定调用哪些已注册工具、调用顺序以及是否需要下一步数据，但每个工具都必须经过服务端注册、参数校验、结果限量和安全过滤。AI 仍不能执行任意 SQL、读取 JD 正文、读取密钥或创建新工具。

这与之前的“固定白名单工具”并不冲突：白名单规定“能选哪些工具”，自主编排规定“在白名单内自己选择和组合哪些工具”。

### 下一项设计问题：自主调用的安全上限

如果完全不设上限，AI 可能反复查询同一类别、把所有类别逐个展开，或者在工具报错后不断尝试，导致响应变慢和成本失控。

建议服务端设置硬上限：

- 单次用户请求最多调用 12 次工具。
- 单个工具返回的候选值最多 100 条，排序结果最多 8 条。
- 工具调用总耗时达到固定上限就停止继续调用。
- 达到上限时保留已经得到的有效结果，并向用户说明分析范围受限。
- AI 的结构化意图修正仍遵守最多 3 次尝试；工具调用次数不因重试而无限增加。

可以把它理解成给分析员一张限额卡：他可以自由选择查哪几本目录，但最多翻 12 次、每次最多拿 100 条摘要，超过时间就先用已经找到的内容回答。

本轮待决问题：是否同意让 AI 在完整的安全工具白名单内自主选择和串联工具，同时采用“单请求最多 12 次工具调用、单次候选最多 100 条、结果曲线最多 8 条、达到时间或调用上限就保留已有有效结果并说明范围受限”的硬边界？

## 第二十五轮：自主工具调用上限修正与批量工具

### 已确认决策

用户同意 AI 在安全工具白名单内自主选择和串联工具，并将单次用户请求的工具调用上限修正为：

- 单次用户请求最多调用 20 次工具，以本轮修正值为准。
- 单个工具返回的候选值最多 100 条。
- 最终曲线最多 8 条。
- 达到调用或时间上限时，保留已经得到的有效结果，并向用户说明分析范围受限。
- 结构化意图修正仍最多 3 次；工具调用总数不能因重试而无限增加。

### 当前前端能力与效率问题

现有趋势看板可以并行读取多条曲线，但 Serving 的公开趋势接口目前是“一次请求读取一条曲线”。如果 AI 找到 8 个候选后逐条调用，就会消耗 8 次工具调用；如果还要先查类别、查候选、做排序和读事件摘要，很容易接近 20 次上限。

因此，工具菜单除了“单个查询”外，可能还需要提供批量工具：

```text
AI 找到 8 个候选
  -> 一次批量读取 8 条趋势
  -> 一次批量读取 8 条事件摘要
  -> 一次校验并生成草稿
```

批量工具不是放宽权限，而是把多个相同类型、相同时间范围的安全查询合并成一次调用。每个元素仍然独立校验；其中一条失败时，其余结果继续返回。

### 下一项设计问题：是否提供批量查询工具

有两种实现方式：

1. **只有单条工具**：AI 自己循环调用，每条曲线一次。工具简单，但更容易耗尽 20 次上限，也增加模型等待时间。
2. **同时提供批量工具**：例如“一次读取最多 8 条趋势”“一次读取最多 8 条事件摘要”“一次校验最多 8 条曲线”。工具参数仍由服务端限制，返回结果按输入逐条标记成功、不可用或失败。

建议采用第二种：AI 仍自主决定是否使用批量工具，但在需要比较多个候选时可以一次完成，减少等待和调用次数；单条工具保留给只需要一个值或补查失败项的情况。

本轮待决问题：是否同意在保留单条工具的同时，增加每次最多处理 8 个候选的批量趋势、批量事件和批量草稿校验工具，并允许 AI 自主选择单条或批量调用？

## 第二十六轮：批量工具确认与 AI 数据摘要边界

### 已确认决策

用户同意在安全白名单内同时提供单条和批量工具：

- 单条工具用于只查询一个值或补查某个失败项。
- 批量趋势、批量事件和批量草稿校验工具每次最多处理 8 个候选。
- AI 可以自主选择单条或批量工具。
- 批量结果按候选逐条返回成功、不可用或失败，不因单个候选失败而丢弃其他结果。

### 下一项设计问题：工具结果是否返回完整每日点位

批量趋势工具如果直接把完整每日点位交给 AI，数据量会很快变大：

```text
年度范围 × 8 条曲线 × 每天一个点
约等于数千个数字
```

这些数字最终本来就要由 Serving 返回给浏览器绘图，AI 通常只需要知道“哪些曲线值得画”和“为什么选它们”。因此可以把数据分成两条路径：

```text
AI 工具：接收小型摘要，用于判断和解释
   - 曲线正式名称
   - 周期平均岗位数
   - 周期末岗位数
   - 周期峰值及日期
   - 进入/修改/下线/重上线摘要
   - 有效观察日数量和缺失日数量

Serving：向浏览器返回完整每日点位，用于真正绘图
```

两种方案的差异：

1. **完整点位给 AI**：AI 能看到每一天，但响应更慢、token 成本更高，也更容易让模型被数字细节淹没。
2. **摘要给 AI，点位给浏览器**：AI 仍能完成排序、筛选和解释，图表数据走现有 Serving；速度和成本更可控。

建议采用第二种。复杂指标由服务端先计算成摘要，AI 只根据安全摘要选择曲线；AI 不需要重新计算每日数字。

本轮待决问题：是否同意批量分析工具只向 AI 返回有限的安全摘要，不返回完整每日 TrendSeries 点位；用户确认草稿后，再由现有 Serving 向浏览器读取完整曲线数据？

## 第二十七轮：AI 的职责边界

### 已确认决策

用户补充确认：AI 的最终职责是判断“应该画哪些曲线”，而不是生成图像本身。具体来说：

- AI 输出曲线选择、曲线配置、排序理由和必要的简短说明。
- AI 不负责生成图片、前端图表或最终的绘图数据。
- 用户确认草稿后，由现有 Serving 向浏览器提供正式曲线数据，再由前端绘制图表。

可以把 AI 理解成“帮用户挑选和编排要看的线路的分析员”，而不是“拿画笔直接画图的人”。例如用户询问“哪些模型训练工具值得看”，AI 负责判断应展示 PyTorch、TensorFlow 等哪些曲线；每条曲线的每日点位仍由 Serving 提供给浏览器。

上一轮的“AI 是否只接收有限摘要、不接收完整每日点位”仍未确认；用户回复“继续”不等同于同意该技术边界。

### 本轮待决问题：AI 是否只接收摘要

既然 AI 只负责挑选曲线，它是否同意只接收服务端计算好的有限摘要，不接收完整每日点位？例如 AI 可以看到“周期平均岗位数、周期末岗位数、峰值日期、进入/修改/下线/重上线数量、有效日和缺失日”，据此决定哪些曲线值得画；用户确认后，浏览器再通过 Serving 获取完整点位完成绘图。

如果同意，AI 就像先看“排行榜和要点”来选线路，浏览器再拿到完整路线坐标绘制地图；如果不同意，则需要让 AI 直接读取完整每日点位，响应会更慢、数据量也更大。

## 第二十八轮：AI 摘要与绘图数据分工确认

### 已确认决策

用户同意把 AI 可见数据限制为服务端生成的有限安全摘要：

- AI 读取曲线名称、周期平均岗位数、周期末岗位数、峰值及日期、进入/修改/下线/重上线摘要、有效日和缺失日等摘要字段。
- AI 不读取完整每日 `TrendSeries` 点位，也不负责生成图像或绘图数据。
- 用户确认曲线草稿后，浏览器通过现有 Serving 获取完整每日点位并绘制图表。

因此数据流固定为：

```text
服务端摘要 -> AI 选择和解释曲线
用户确认草稿 -> Serving 返回完整点位
完整点位 -> 浏览器绘图
```

这样 AI 负责“挑选要画的线路”，Serving 和浏览器负责“拿到坐标并画出来”，两边各自使用适合自己的数据粒度。

### 下一项设计问题：一句话包含多个子问题时如何分配 8 条曲线

指导文档中的典型问题可能同时包含多个子问题，例如：

> “MHY 使用哪些后台数据库、模型训练工具，以及有哪些正在进行的项目？”

这句话可能同时命中“技术类别：数据库与存储”“技术类别：模型训练工具”和“项目”三个分析任务。总曲线仍只能有 8 条，因此需要决定是否保证每个有效子问题都能看到结果。

建议采用“先照顾每个子问题，再按排名补齐”的方式：

1. AI 先为每个有效子问题至少保留 1 条最合适的曲线；
2. 剩余名额按周期内平均岗位数、匹配置信度和用户原始顺序补齐；
3. 某个子问题没有有效候选时，其他子问题仍继续生成；
4. 超过 8 条时，按子问题分组展示，并明确说明哪些候选因总上限没有展示。

例如三个子问题共有 14 个候选，可以先保证三个类别各有 1 条，再把剩余 5 个名额给排名更高的候选。这样不会因为第一个类别恰好有 8 个候选，就让后面的项目完全没有结果。

本轮待决问题：是否同意多子问题共用最多 8 条曲线，并采用“每个有效子问题至少保留 1 条、再按排名和用户顺序补齐”的分配规则？

## 第二十九轮：多子问题曲线配额确认

### 已确认决策

用户同意多个子问题共用最多 8 条曲线，并采用以下配额规则：

- 先为每个有效子问题保留至少 1 条最合适的曲线。
- 剩余名额再按周期内平均岗位数、匹配置信度和用户原始顺序补齐。
- 某个子问题没有有效候选时，其他子问题继续生成结果。
- 超出总上限时，按子问题分组说明被截断的候选，不静默丢弃用户请求。

### 现有看板能力核对

现有前端的曲线状态已经允许一组曲线同时包含技术关键词、项目、岗位族和工作地点等不同维度；每条曲线仍使用同一个“岗位数”纵轴，并在图例中显示维度和正式名称。因此，AI 草稿不需要为每个子问题创建一套新的图表数据协议，应用后可以复用当前最多 8 条曲线的看板状态。

### 下一项设计问题：不同子问题是否共用一张图

现在需要确定展示方式。比如：

> “后台数据库、模型训练工具、正在进行的项目”

可以有两种呈现：

1. **共用一张趋势图**：所有曲线都放在现有同一张岗位数量图中，草稿列表按子问题分组；优点是用户一次就能比较全部结果，也完全复用当前看板。
2. **每个子问题单独一张图**：数据库、训练工具和项目分别绘制；阅读更清楚，但需要新增多图布局、独立图例和更多移动端交互。

鉴于所有曲线的纵轴都是岗位数量，且当前看板已经支持混合维度曲线，建议一期采用第一种：草稿和图例分组说明，应用后仍使用一张趋势图。

本轮待决问题：是否同意多个子问题的曲线在应用后共用现有一张趋势图，只在草稿列表和图例中按子问题分组说明？

## 第三十轮：多子问题共用一张图确认

### 已确认决策

用户同意多个子问题的曲线应用后共用现有一张趋势图：

- 例如“后台数据库、模型训练工具、正在进行的项目”会生成一份曲线草稿。
- 用户确认后，数据库、训练工具和项目曲线一起进入当前趋势看板。
- 草稿列表按子问题分组，图例继续显示每条曲线的维度和正式名称，帮助用户区分不同类别。
- 不为每个子问题新增独立图表页面或多图布局。

可以把它理解成一张“岗位数量地图”：数据库、训练工具和项目是地图上的不同路线，路线可以用不同颜色区分，但仍在同一张地图上查看。

### 下一项设计问题：AI 草稿是否跨页面保留

现在需要决定用户生成草稿后，如果暂时不点击应用，草稿要不要保留。例如：

```text
用户输入：“哪些后台数据库？”
AI 返回：MySQL、Redis、PostgreSQL 三条草稿
用户暂时离开趋势页面，或刷新浏览器
```

有两种简单做法：

1. **临时草稿**：草稿只保留在当前页面；用户点击“应用”后进入看板，点击“放弃”或刷新页面后草稿消失。实现简单，也不会把过期的技术词典候选带回来。
2. **保留草稿**：用户返回趋势页面时仍能看到未应用草稿，可以继续修改。体验更像“购物车”，但需要处理草稿过期、词典升级和长期保存。

建议一期采用临时草稿：AI 草稿像“试衣间里暂存的搭配”，确认购买（应用）后才进入正式衣柜；没有确认就不长期保存。已经生成的安全审计记录仍按前面确认的保留策略保存，但不等同于可继续编辑的草稿。

本轮待决问题：如果用户刷新页面或离开趋势看板，是否同意未应用的 AI 草稿直接清除；只有点击“应用”后才保留为正式曲线？

## 第三十一轮：自然问题是否默认生成曲线草稿

### 已确认决策

用户同意未应用的 AI 草稿只在当前趋势页面临时存在：

- 用户点击“应用”后，曲线才进入正式看板配置。
- 用户点击“放弃”、刷新页面或离开趋势页面时，未应用草稿清除。
- 安全审计摘要仍按既定保留策略保存，但审计记录不能恢复成可继续编辑的草稿。

可以把它理解成“试衣间里的搭配”：确认购买后才放进衣柜，离开试衣间没有购买就清空。

### 下一项设计问题：用户是否必须说“画趋势”

用户最初的例子是：

> “MHY 使用哪些后台数据库？使用哪些模型训练工具？有哪些正在进行的项目？”

这句话没有出现“画趋势”“生成图表”等词，但它发生在趋势看板的 AI 输入框里。这里有两种体验：

1. **直接生成曲线草稿**：AI 把“哪些后台数据库”理解成“请帮我找出应该画的数据库曲线”，直接返回 MySQL、Redis、PostgreSQL 等草稿；用户不需要学习特殊口令。
2. **要求用户明确说画图**：只有用户写“画出后台数据库趋势”时才生成草稿；否则先追问“你是想看列表还是趋势图”，过程更准确但更容易让用户卡住。

建议采用第一种。因为入口本身就在趋势看板，用户输入“哪些数据库”“目前有哪些项目”等问题时，默认目标就是得到可确认的曲线草稿；用户仍然可以在草稿中删除、修改或放弃结果。

本轮待决问题：在趋势看板的 AI 输入框中，用户只说“哪些数据库”“哪些项目”这类自然问题时，是否同意直接生成曲线草稿，不要求额外写出“画趋势”？

## 第三十二轮：自然问题默认进入曲线草稿流程

### 已确认决策

用户同意在趋势看板的 AI 输入框中，直接把自然问题当作曲线草稿请求：

- “哪些数据库？”直接进入数据库候选识别和曲线草稿流程。
- “哪些项目正在增加岗位？”直接进入项目排名和曲线草稿流程。
- 用户不需要额外写“画趋势”“生成图表”等固定口令。
- AI 草稿仍然需要用户确认，不能因为默认进入流程就自动改变当前看板。

这就像在地图页面里说“附近有哪些咖啡店”：用户不必再说“请画一张咖啡店地图”，页面已经知道要把结果放到地图上；在本项目里，趋势页面已经知道结果要以曲线草稿呈现。

### 下一项设计问题：草稿中是否显示选择理由和摘要

例如用户输入“哪些后台数据库”，AI 找到 MySQL、Redis、PostgreSQL 后，草稿可以这样显示：

```text
数据库与存储
  [ ] MySQL       本周期平均 12 个岗位，类别内第 1
  [ ] Redis       本周期平均  9 个岗位，类别内第 2
  [ ] PostgreSQL  本周期平均  7 个岗位，类别内第 3

      [应用草稿]
```

也可以只显示三条曲线名称，把岗位数和排名全部隐藏，界面更干净但用户不容易理解 AI 为什么选它们。

建议显示简短的服务端摘要：每条曲线最多展示一行“选择理由”，例如平均岗位数、排名、是否为可能匹配；不展示完整每日点位，也不把模型内部思考过程展示给用户。这样用户像看商品推荐旁边的“销量和推荐原因”，可以快速删掉不想要的曲线。

本轮待决问题：是否同意在 AI 草稿的每条曲线旁显示一行简短的服务端摘要和选择理由（例如“平均岗位数 12，类别内第 1”），帮助用户决定保留或删除？

## 第三十三轮：曲线摘要展示与提问方式确认

### 已确认决策

用户同意在 AI 草稿中为每条曲线显示一行简短的服务端摘要和选择理由：

- 例如“平均岗位数 12，类别内第 1”。
- 如果是宽匹配候选，还要显示“可能匹配”等明确提示。
- 不显示完整每日点位，不展示模型内部思考过程。
- 用户可以根据这行摘要决定删除、保留或调整曲线。

### 提问方式调整

用户明确要求：每次对话中的设计问题必须自包含，不能要求用户打开决策文档才能理解。后续提问都应在当前消息中直接说明：

1. 要决定的具体行为；
2. 用户会看到的实际例子；
3. 推荐选项及推荐原因；
4. 其他选项会带来的不同结果。

决策文档继续作为会话留档，但不再作为理解问题的前置条件。

### 下一项设计问题：完全找不到候选时如何尽量给结果

例如用户输入：

> “哪些量子数据库？”

如果当前正式技术词典和类别中都没有“量子数据库”或相近值，系统可以有两种行为：

1. **严格提示没有找到**：告诉用户“没有找到匹配的正式技术”，保留当前看板不变，并给出几个当前可选的数据库类别或关键词，让用户重新选择。这样最准确，但这次请求看不到新曲线。
2. **扩大到最近的正式类别**：如果系统能识别“数据库”这一部分，就从“数据库与存储”类别中选出当前岗位数最高的候选，例如 MySQL、Redis、PostgreSQL，并明确标记为“扩展推荐，不是精确匹配”。这样更容易让用户看到结果，但可能偏离“量子”这个限定词。

结合你已经确认的“匹配范围可以更大、优先让用户看到结果”，我建议采用第二种，但必须在草稿上写清楚“扩展推荐”，不能伪装成用户原话的精确命中；只有连“数据库”这样的类别也无法识别时，才使用第一种提示。

本轮待决问题：当用户的说法完全找不到正式值，但能识别出一个更宽的类别时，是否同意自动展示该类别的热门曲线，并标注“扩展推荐、不是精确匹配”？

## 第三十四轮：扩展推荐确认与完全无法识别时的处理

### 已确认决策

用户同意当精确值不存在、但可以识别出更宽类别时，继续给出扩展推荐：

- 例如“量子数据库”没有正式值，但能识别“数据库与存储”类别时，可以展示该类别的热门曲线。
- 每条扩展曲线必须明确标注“扩展推荐，不是精确匹配”。
- 用户仍然要在草稿阶段确认，扩展推荐不会自动改动当前看板。
- 扩展推荐遵循最多 8 条曲线和既定排序、分组规则。

这相当于用户说“我要找蓝色的电动车”，系统没有找到“蓝色电动车”这一精确商品，但能先展示“电动车”类别中的热门商品，并告诉用户颜色条件没有精确命中，避免把推荐伪装成完全符合。

### 下一项设计问题：连类别都无法识别时怎么办

例如用户输入：

> “哪些量子跃迁技术？”

系统既找不到“量子跃迁技术”这个正式值，也不能判断它属于数据库、模型训练工具、项目、岗位族或地点中的哪一类。此时有两种行为：

1. **不乱画，给出可行动提示**：保持当前看板不变，告诉用户“暂时没有找到可匹配的曲线”，并列出几个可以直接点击或参考的例子，例如“哪些后台数据库”“哪些模型训练工具”“哪些项目”。这样不会把完全无关的曲线塞给用户，同时用户可以马上换一种说法。
2. **全局兜底推荐**：从所有支持维度中挑岗位数最高的 8 条曲线，标成“广泛推荐”。这样一定能看到图，但很可能与用户真正想问的内容无关。

建议采用第一种：当连类别都无法识别时，不生成无关曲线，但提供具体可复制的例子和当前可用类别入口；这仍然是最大努力处理，因为用户不会只得到一句“失败”，而是能马上继续尝试。

本轮待决问题：当用户的问题连正式类别都无法识别时，是否同意不自动生成无关曲线，保留当前看板，并给出几个可以直接参考的有效提问例子？

## 第三十五轮：完全无法识别时的兜底与记录方式

### 已确认决策

- 连正式类别都无法识别时，不生成无关曲线。
- 保留当前看板不变，并给出可复制的有效提问例子，例如“哪些后台数据库”“哪些模型训练工具”“哪些项目”。
- 后续决策记录只保留关键结论、必要例子和下一道问题，减少重复背景与长篇方案比较。
- 当前历史暂不删除，以免丢失已经确认的决策依据。

### 下一项设计问题：扩展推荐是否默认勾选

例如用户输入“哪些量子数据库”，系统只能识别出“数据库”大类，于是给出 MySQL、Redis、PostgreSQL，并标注“扩展推荐”。需要决定这些候选出现时是否默认勾选：

- **默认勾选**：用户一眼就能看到系统建议的结果，之后可以删掉不想要的曲线；符合“优先看到结果”。
- **默认不勾选**：只把它们当建议，用户必须手动勾选；更谨慎，但容易让用户误以为系统没有给出结果。

建议默认勾选，但保留“扩展推荐”标签，并且仍需用户点击“应用草稿”后才进入看板。

本轮待决问题：扩展推荐候选出现时，是否同意默认勾选，让用户可以直接看到并按需删除？

## 第三十六轮：扩展推荐默认选择

### 已确认决策

- 扩展推荐候选默认勾选。
- 草稿中继续显示“扩展推荐，不是精确匹配”。
- 用户可以删除不想看的候选，再点击“应用草稿”。
- 未经用户点击“应用草稿”，扩展推荐不会进入正式看板。

### 下一项设计问题：应用后是否保留扩展标记

例如用户输入“哪些量子数据库”，系统推荐 MySQL 并标记为扩展推荐。点击应用后，图例可以显示：

- `技术关键词 · MySQL`
- `技术关键词 · MySQL（扩展推荐）`

建议保留“扩展推荐”标记。这样用户之后看到曲线时仍知道它是根据较宽的“数据库”类别推荐出来的，不会误以为 MySQL 精确回答了“量子数据库”。

本轮待决问题：扩展推荐被应用到看板后，是否同意在图例或曲线说明中继续保留“扩展推荐”标记？

## 第三十七轮：扩展推荐应用后的显示

### 已确认决策

- 扩展推荐只在 AI 草稿阶段显示“扩展推荐，不是精确匹配”。
- 用户点击“应用草稿”后，图例使用正式曲线名称，不再显示扩展标记。

### 下一项设计问题：无结果提示里的例子是否可点击

当系统完全无法识别用户问题时，页面会提示：

> 暂时没有找到可匹配的曲线。你可以试试“哪些后台数据库”“哪些模型训练工具”或“哪些项目”。

这些例子可以只是文字，也可以做成按钮。建议做成按钮：用户点击“哪些后台数据库”后，自动把这句话填入输入框，但不自动提交；用户可以直接发送，也可以先修改文字。这样用户不会卡在错误提示里，也不会因为一次点击就意外发起请求。

本轮待决问题：无结果提示中的示例是否同意做成可点击按钮，点击后只填入输入框、不自动提交？

## 第三十八轮：无结果示例按钮

### 已确认决策

- 无结果提示中的示例做成可点击按钮。
- 点击示例只把文字填入 AI 输入框，不自动提交。
- 用户可以直接发送，也可以先修改示例内容。

### 下一项设计问题：AI 分析时显示什么

一次请求可能需要查询类别、候选和摘要，用户可能要等待几秒。建议在等待期间显示一行简单提示：

> 正在整理曲线草稿，请稍候……

同时暂时禁用重复提交，避免同一个问题被连续发送多次。提示只说明用户能理解的进度，不显示工具名称、数据库表名或模型内部过程。

另一种做法是只显示一个转圈图标，不显示文字；界面更简洁，但用户不知道系统是否仍在工作。

本轮待决问题：AI 分析期间，是否同意显示“正在整理曲线草稿，请稍候……”这类简单文字，并暂时禁用重复提交？

## 第三十九轮：流式展示 AI 工作流程

### 已确认决策

用户补充确认：

- AI 分析期间必须禁用重复提交。
- 不能只显示静态“请稍候”，需要流式展示 AI 正在执行的工作步骤。
- 用户希望看到类似“调用了什么工具”的过程，以便知道系统确实在分析，而不是页面卡住。

当前还需要确定展示名称的层级。内部工具可能使用 `list_available_values`、`rank_values`、`validate_curve_draft` 这样的工程名称；页面也可以把它们翻译成“读取可用类别和关键词”“按岗位数排序”“校验曲线草稿”。

### 下一项设计问题：显示友好步骤还是内部工具名

例如用户问“哪些后台数据库”，流式过程可以显示：

**方案 A：用户友好的步骤（建议）**

```text
✓ 正在读取技术类别
✓ 正在查询“数据库与存储”中的关键词
→ 正在按岗位数量排序
○ 正在生成曲线草稿
```

**方案 B：内部工具名称**

```text
✓ list_available_categories
✓ list_category_values(category="database_storage")
→ rank_values(dimension="technology")
○ validate_curve_draft
```

方案 A 更容易理解，也不会把 Go 函数名、参数、内部类别键或后续实现细节固定到用户界面；方案 B 更透明，但用户需要理解工程术语，工具改名时页面也会跟着变化。无论选择哪种，都不会显示 SQL、密钥、原始 JD、模型内部思考或内部错误堆栈。

本轮待决问题：流式工作流程是否同意使用方案 A 的用户友好步骤，同时在每一步显示“进行中 / 已完成 / 未完成”状态，而不直接展示内部工具名和参数？

## 第四十轮：流式显示内部工具调用

### 已确认决策

- 流式过程直接显示实际调用的内部工具名称和经过过滤的参数。
- 例如可以显示 `rank_values(dimension="technology", category="database_storage")`。
- 仍然禁止显示 SQL、密钥、连接串、原始 JD 正文、模型内部思考、未过滤的内部错误堆栈。
- 每次调用继续显示进行中、已完成或未完成状态，重复提交继续禁用。

### 下一项设计问题：是否显示工具返回结果

例如工具调用完成后，可以显示：

```text
✓ rank_values(dimension="technology", category="database_storage")
  返回 12 个候选，已按平均岗位数排序，草稿保留前 8 个
```

也可以进一步把工具返回的全部候选逐条打印出来。建议只显示“返回多少条、筛选了多少条、是否有失败项”等简短摘要，具体候选放到下面的草稿列表中；这样既能看见工具确实工作，也不会让过程区域变成一大段原始数据。

本轮待决问题：工具调用完成后，是否同意流式显示简短结果摘要，而不直接展开工具返回的全部原始数据？

## 第四十一轮：流式过程只显示操作，不显示结果摘要

### 已确认决策

- 流式区域不显示工具返回数量、排序结果或其他结果摘要。
- 流式区域只显示工具调用和其他 AI 执行动作本身。
- 最终候选曲线及其用户可见说明仍放在曲线草稿列表中。

### 下一项设计问题：操作名称还是模型推理文字

“其他 AI 操作”可以显示成简短的动作名称：

```text
✓ 解析用户问题
✓ 识别时间范围
✓ 匹配技术类别
→ 生成曲线草稿
```

也可以把模型正在形成的自然语言推理逐字显示出来。建议只显示前一种动作名称和状态，不显示模型的逐字推理；这样用户能看到 AI 正在做哪些步骤，但不会把不稳定的内部思考误认为最终事实。

本轮待决问题：是否同意流式区域只显示“解析问题、匹配类别、调用工具、生成草稿”等操作名称和状态，不显示模型的逐字推理文字？

## 第四十二轮：流式操作名称确认

### 已确认决策

- 流式区域显示操作名称、工具调用和进行中/已完成/未完成状态。
- 不显示模型逐字推理文字。
- 不显示工具返回数量、排序结果或其他结果摘要。
- 候选曲线及其选择理由只出现在最终草稿列表中。

### 下一项设计问题：某个工具失败后是否继续

例如 AI 正在处理“哪些后台数据库”：

```text
✓ 解析用户问题
✓ list_available_categories()
✗ rank_values(...)
```

此时可以：

- **继续**：把失败标记留在流程里，再用已经拿到的有效信息生成部分草稿；
- **停止**：因为排序工具失败，整次请求不生成草稿。

建议继续执行，符合“单个工具失败不拖垮整个请求”的原则；只要仍有可校验的候选，就把结果放进草稿，并说明部分分析没有完成。

本轮待决问题：某个工具失败时，是否同意在流式记录中标记失败，但继续执行其他可用步骤并尽量生成草稿？

## 第四十三轮：AI 参数错误与后台工具错误的责任边界

### 已确认决策

- 用户同意局部工具失败时继续处理，并尽量保留其他有效结果。
- 如果 AI 输出的请求参数没有通过 Schema、枚举、维度组合、数量或时间范围校验，错误原因回报给 AI，允许 AI 按既定上限修正重试。
- 如果 AI 参数已经全部校验合法，后续工具调用、数据库、趋势服务或其他后台错误默认归后台责任处理。
- 后台责任错误只在流式过程中标记失败，并继续其他互不依赖的步骤，不要求 AI 为后台故障重试。
- 用户指定的正式值不存在时，按数据不可用处理，不通过反复调用 AI 伪造或替换成新值。

判断顺序固定为：

```text
AI 输出参数
  -> 参数校验失败：反馈安全错误给 AI，有限修正重试
  -> 参数校验通过：执行工具
       -> 工具或后台失败：标记失败，继续其他可行步骤
```

### 下一项设计问题：参数修正重试是否显示在流式过程

例如 AI 第一次给出了不允许的指标：

```text
✗ rank_values(metric="sum_daily_active_jobs")
↻ AI 正在修正请求参数
→ rank_values(metric="avg_daily_active_jobs")
```

建议把“校验失败、反馈 AI、AI 修正、再次调用”这几步显示出来，让用户知道为什么同一个动作出现了两次。后台数据库超时则只显示一次失败，不显示 AI 重试：

```text
✗ read_trend_summary(...)
```

本轮待决问题：AI 参数非法时，是否同意在流式过程明确显示“校验失败 -> AI 修正 -> 重试”，而后台工具失败只显示失败并继续其他步骤？

## 第四十四轮：错误流程的流式区分

### 已确认决策

- AI 参数非法时，流式过程明确显示“校验失败 -> AI 修正 -> 重试”。
- AI 参数合法但后台工具失败时，只显示工具失败，并继续其他可行步骤。
- 两类错误使用不同的状态和说明，不把后台故障误显示成 AI 需要修正的问题。

### 下一项设计问题：是否允许用户停止分析

例如用户提交“哪些后台数据库、模型训练工具和项目”，系统正在连续调用工具。用户如果已经等够了，或者发现问题写错了，可以有一个“停止分析”按钮：

- 点击后结束本次 AI 请求，保留当前已应用曲线不变。
- 已经生成但尚未完成的草稿不进入看板。
- 流式记录显示“用户已停止分析”，用户可以修改输入后重新提交。

如果不提供停止按钮，用户只能等到工具调用和重试全部结束，等待期间也无法撤回这次请求。

本轮待决问题：分析进行期间，是否同意提供“停止分析”按钮，让用户主动结束本次请求？

## 第四十五轮：用户停止分析

### 已确认决策

- 分析进行期间提供“停止分析”按钮。
- 用户停止后立即结束本次 AI 请求。
- 已应用曲线保持不变。
- 未完成的请求不会自动应用到看板。
- 流式记录显示“用户已停止分析”，用户可以修改输入后重新提交。

### 下一项设计问题：停止时是否保留已找到的部分草稿

例如系统已经找到 3 条数据库曲线，还在查询第 4、5 条时，用户点击“停止分析”。可以有两种行为：

- **保留部分草稿**：显示这 3 条，并标记“分析已停止，结果可能不完整”；用户可以删改后应用。
- **全部丢弃**：因为请求没有完成，不显示这 3 条，用户重新提交后重新开始。

建议保留部分草稿，符合优先展示结果的要求，同时明确标记结果不完整。它像下载文件时暂停，已经下载的部分仍可查看，但用户知道文件还没有完整下载。

本轮待决问题：用户停止分析后，是否同意保留已经找到的曲线作为“可能不完整”的临时草稿，供用户继续编辑和应用？

## 第四十六轮：停止分析后的部分草稿

### 已确认决策

- 用户停止分析后，保留已经找到的曲线。
- 部分草稿明确标记“分析已停止，结果可能不完整”。
- 用户可以继续删除、修改并决定是否应用这些曲线。
- 用户停止不会改变当前已经应用的曲线。

### 下一项设计问题：分析结束后是否保留操作记录

例如请求完成后，页面上已经显示过：

```text
✓ list_available_categories(...)
✓ list_category_values(...)
✓ rank_values(...)
✓ validate_curve_draft(...)
```

可以让这段记录继续留在当前草稿上方，用户以后还能回看 AI 做过哪些操作。也可以在草稿生成后自动收起，只保留一个“查看操作记录”按钮，让页面更简洁。

建议默认收起但保留查看入口。用户仍能查看完整操作记录，草稿区域不会被长流程占满。

本轮待决问题：分析完成或用户停止后，是否同意默认收起操作记录，但保留“查看操作记录”按钮？

## 第四十七轮：操作记录默认收起

### 已确认决策

- 分析完成或用户停止后，操作记录默认收起。
- 页面保留“查看操作记录”按钮。
- 用户点击后可以查看本次请求的完整操作顺序。

### 下一项设计问题：操作记录保留到什么时候

例如用户已经应用了 MySQL、Redis 两条曲线。操作记录可以继续留在当前页面，也可以在草稿应用后收起并结束本次记录。

建议操作记录只属于本次临时 AI 草稿。用户点击“应用草稿”后，记录仍可以在当前页面查看，用户刷新或离开趋势页面时随临时会话一起清除。这样用户可以马上核对这次请求，页面重新进入时不会出现上一轮旧流程。

本轮待决问题：是否同意操作记录只保留在当前 AI 请求和当前页面，应用后仍可查看，但刷新或离开趋势页面后清除？

## 第四十八轮：操作记录的页面生命周期

### 已确认决策

- 操作记录只属于当前 AI 请求和当前趋势页面。
- 用户应用草稿后，仍可在当前页面查看这次操作记录。
- 用户刷新或离开趋势页面后，操作记录清除。
- 长期保留的只有已经确认的安全审计摘要，不保留可展开的完整操作记录。

### 下一项设计问题：后台全部失败时是否允许手动重试

例如用户问“哪些后台数据库”，但数据库暂时不可用：

```text
✗ read_trend_summary(...)
暂时无法读取趋势数据
```

这时 AI 不会因为后台错误自动重试。页面可以提供“重新分析”按钮，由用户决定稍后再试；也可以只显示失败提示，不提供任何按钮，让用户重新输入问题。

建议提供“重新分析”按钮。点击后重新发起一次完整请求，并重新遵守工具调用上限；不自动连续点击，避免后台故障时不断增加请求。

本轮待决问题：后台工具失败导致没有可用曲线时，是否同意显示“重新分析”按钮，由用户手动发起一次新的请求？

## 第四十九轮：后台全部失败时的处理

### 已确认决策

- 后台工具失败且没有任何可用曲线时，只显示失败提示。
- 不提供“重新分析”按钮，也不自动重试后台请求。
- 用户需要修改问题或重新提交，才会发起新的 AI 请求。

### 下一项设计问题：重复曲线是否合并

例如用户同时问：

> “哪些后台数据库？哪些技术正在使用 MySQL？”

两个子问题可能都选中 MySQL。如果不合并，草稿和最终图里会出现两条完全相同的 MySQL 曲线。建议合并为一条，并在草稿说明中标记它同时回答两个子问题；这样可以把名额留给其他候选，也避免图例重复。

本轮待决问题：不同子问题选中同一条正式曲线时，是否同意合并为一条，并在说明中标记它对应多个子问题？

## 第五十轮：重复曲线合并

### 已确认决策

- 不同子问题命中同一条正式曲线时合并为一条。
- 合并后的草稿说明它同时回答哪些子问题。
- 合并可以节省 8 条曲线名额，并避免图例出现相同曲线。

### 下一项设计问题：岗位族的主岗位族开关是否算不同曲线

现有岗位族曲线有两个可选口径：

- `岗位族 · 后端（仅主岗位族）`
- `岗位族 · 后端（含副岗位族）`

这两条线名称接近，但统计范围不同，岗位数量也可能不同。建议只有“维度、正式值、比较条件和岗位族开关都相同”时才合并；主岗位族和含副岗位族应保留为两条不同曲线，并在图例中写清楚口径。

本轮待决问题：岗位族的“仅主岗位族”和“含副岗位族”是否视为两条不同曲线，不进行合并？

## 第五十一轮：岗位族统计口径与时间范围冲突

### 已确认决策

- `岗位族 · 后端（仅主岗位族）` 与 `岗位族 · 后端（含副岗位族）`保留为两条不同曲线。
- 只有维度、正式值、比较条件和岗位族开关都相同，曲线才会合并。

### 下一项设计问题：一句话出现两个时间范围

现有趋势看板一次只使用一个时间范围。例如用户输入：

> “本月哪些后台数据库？去年哪些项目？”

这句话里有“本月”和“去年”两个范围，但一张当前趋势图只能使用一个范围。可以：

- 统一使用一个范围，例如按第一个明确范围“本月”生成全部曲线；
- 发现范围冲突时，请用户先选择“本月”或“去年”，再生成草稿；
- 拆成两张图，分别展示两个范围，这需要新的多图能力。

建议只在用户明确写出互相冲突的时间范围时请用户选择一次，其他情况继续沿用既定默认范围，不增加额外追问。

本轮待决问题：一句话明确包含两个不同时间范围时，是否同意先请用户选择一个统一范围，再生成同一张图的曲线草稿？

## 第五十二轮：时间范围冲突改为提示用户修改

### 已确认决策

- 一句话同时出现“本月”和“去年”等冲突时间范围时，不弹出范围选择器。
- 直接提示用户时间范围冲突，请用户把问题改成一个统一范围后重新提交。
- 当前已应用曲线保持不变，也不自动选择第一个时间范围。

### 下一项设计问题：支持和暂不支持的内容混在一句话里

一期 AI 作图支持技术关键词、项目、岗位族和工作地点。学历和工作年限暂不支持自然语言作图。例如用户输入：

> “哪些项目最多？哪些岗位要求硕士？”

此时可以：

- 继续处理“哪些项目最多”，生成项目曲线；同时明确提示“学历要求暂不支持”；
- 因为一句话里包含暂不支持的内容，整次请求都停止。

建议保留可以处理的项目曲线，并单独说明学历问题暂不支持。这样用户仍能看到一部分结果，也知道哪一部分需要以后再处理。

本轮待决问题：一句话同时包含支持和暂不支持的内容时，是否同意继续生成支持部分的曲线，并明确提示暂不支持的部分？

## 第五十三轮：支持与暂不支持内容混合

### 已确认决策

- 一句话同时包含支持和暂不支持内容时，继续生成支持部分的曲线。
- 对暂不支持的部分给出明确提示，不让它阻断其他有效子问题。
- 当前看板和已应用曲线保持不变，用户仍可编辑并应用生成的部分草稿。

### 下一项设计问题：用户指定当前不支持的图表类型

当前趋势看板展示岗位数量折线。例如用户输入：

> “哪些后台数据库？请用柱状图展示。”

可以：

- 继续识别数据库候选，生成可用的岗位数量折线草稿，同时提示“当前看板使用折线图”；
- 因为用户指定了柱状图而停止整次请求。

建议保留数据库曲线结果，并明确提示当前展示方式。这样用户仍能看到想比较的数据库，图表样式限制不会让整次请求没有结果。

本轮待决问题：用户指定柱状图、饼图等当前看板不支持的展示方式时，是否同意继续生成可用的折线曲线草稿，并提示当前展示方式？

## 第五十四轮：不支持的图表类型兼容处理

### 已确认决策

- 用户指定柱状图、饼图等当前看板不支持的展示方式时，继续生成可用的岗位数量折线草稿。
- 草稿说明当前看板使用折线图，不把未实现的图表类型伪装成已经支持。
- 用户仍可编辑草稿并决定是否应用。

### 下一项设计问题：用户要求“占比”时显示什么

例如用户输入：

> “我想看后台数据库各自占全部岗位的比例。”

当前正式曲线的纵轴是岗位数量，不能直接把纵轴改成百分比。可以：

- 继续找出数据库候选，生成岗位数量折线，并提示“当前只展示岗位数量，暂不绘制占比”；
- 因为占比曲线暂不支持，整次请求不生成结果。

建议继续生成岗位数量曲线，并把“占比暂不支持”写在草稿说明里。这样用户仍能看到数据库的变化，结果口径也不会被伪装成百分比。

本轮待决问题：用户要求“占比”或其他当前不能作为纵轴的指标时，是否同意生成普通岗位数量曲线，同时明确提示该指标暂不支持直接绘制？

## 第五十五轮：不支持纵轴指标的兼容处理

### 已确认决策

- 用户要求“占比”等当前不能作为纵轴的指标时，继续生成普通岗位数量曲线。
- 草稿明确提示该指标暂不支持直接绘制，不把岗位数量冒充成百分比。
- 用户仍可编辑并决定是否应用这些曲线。

### 下一项设计问题：候选数量不足时是否照常展示

例如用户输入：

> “请给我岗位最多的前 5 个后台数据库。”

当前有效数据里可能只有 MySQL 和 Redis 两个候选。可以：

- 展示这 2 条，并说明“当前只找到 2 个有效候选”；
- 因为没有凑够 5 条而整次失败。

建议展示已有的 2 条。用户仍能看到全部可用结果，系统也不会为了凑数而创造不存在的曲线。

本轮待决问题：请求数量大于当前有效候选数量时，是否同意展示已有候选，并明确说明实际找到的数量？

## 第五十六轮：候选数量不足时展示已有结果

### 已确认决策

- 请求数量大于当前有效候选数量时，展示全部已有候选。
- 草稿明确说明实际找到的数量，例如“当前只找到 2 个有效候选”。
- 不为了凑足目标数量而创造不存在的曲线，也不因为数量不足而丢弃已有结果。

### 下一项设计问题：类别中的零岗位候选是否展示

例如用户问“哪些后台数据库”，当前类别里有：

- MySQL，周期平均 12 个岗位；
- PostgreSQL，周期平均 7 个岗位；
- Redis，周期平均 0 个岗位。

可以只展示当前周期确实有岗位的 MySQL 和 PostgreSQL，也可以把 Redis 的全 0 曲线一起展示，让用户看到它当前没有岗位。建议类别型“哪些”问题只展示周期内有有效岗位的候选，避免把“没有被使用”的值当成使用结果；用户明确点名某个正式值时，即使岗位数为 0，也保留该曲线，让用户看到它的真实状态。

本轮待决问题：类别型“哪些/使用了哪些”问题是否只展示当前周期有岗位的候选，同时保留用户明确点名的零岗位正式值？

## 第五十七轮：类别推荐过滤零岗位候选

### 已确认决策

- 类别型“哪些/使用了哪些”问题只推荐当前周期有岗位的候选。
- 用户明确点名的正式值即使岗位数为 0，也保留该曲线。
- 类别推荐不把零岗位候选伪装成当前正在使用的结果。

### 下一项设计问题：类别中全部候选都是零岗位

例如用户问“哪些后台数据库”，但本月数据库类别下所有候选的岗位数都是 0。可以：

- 不生成类别推荐曲线，直接提示“当前周期没有数据库岗位”；
- 展示几条全 0 曲线，让用户看到每个候选都没有岗位。

建议提示没有当前岗位，并保留用户可以点击的其他问题示例。用户如果明确点名 MySQL，仍按上一轮规则展示 MySQL 的零岗位曲线。

本轮待决问题：类别内所有候选都是零岗位时，是否同意不生成类别推荐曲线，直接提示当前周期没有该类别岗位？

## 第五十八轮：全零类别仍生成草稿

### 已确认决策

- 类别内所有候选都是零岗位时，仍生成全零曲线草稿。

### 当前流式能力核对

现有 API 使用普通 HTTP JSON 请求，项目中还没有现成的 SSE 或 WebSocket 流式接口。AI 工作流程需要让服务器在每个操作发生时把事件推送到浏览器，例如：

```text
用户提交问题
  -> 服务器推送：解析用户问题
  -> 服务器推送：调用 rank_values(...)
  -> 服务器推送：生成曲线草稿
```

### 下一项设计问题：采用哪种流式连接

可以把两种方式理解成：

- **HTTP 流式 / SSE**：服务器像广播一样持续向浏览器发送步骤，适合“AI 做一步就播报一步”；
- **WebSocket**：浏览器和服务器像打电话一样双向持续通信，能力更强，但连接和状态管理更复杂。

一期只需要服务器向浏览器推送操作步骤，用户停止分析可以通过普通取消请求完成。建议采用 HTTP 流式响应或 SSE，不为一期引入 WebSocket 的双向连接复杂度。

本轮待决问题：AI 操作步骤的流式传输，是否同意采用 HTTP 流式响应或 SSE，由服务器单向推送到浏览器？

## 第六十九轮：采用单向 HTTP 流式传输

### 已确认决策

- AI 操作步骤采用服务器到浏览器的单向 HTTP 流式传输或 SSE。
- 一期不引入 WebSocket 双向长连接。

### 下一项设计问题：单请求流式还是任务加订阅

可以有两种连接方式：

- **单请求流式**：浏览器一次提交问题，服务器在同一个 HTTP 请求中连续返回“解析问题、调用工具、生成草稿”等事件，最后返回草稿结果；
- **任务加订阅**：先提交请求得到任务 ID，再用第二个连接订阅任务事件，状态管理更多。

建议采用单请求流式。它像一次点餐后，服务员在同一桌持续报菜品进度；浏览器可以用 `AbortController` 直接停止请求，不需要额外维护任务订阅状态。

本轮待决问题：是否同意 AI 作图采用“一个提交请求对应一条持续返回事件的 HTTP 流”，请求结束时返回最终草稿或失败状态？

## 第七十轮：单请求流式传输

### 已确认决策

- 一次用户提交对应一条持续返回事件的 HTTP 流。
- 服务器按顺序推送操作开始、完成或失败事件。
- 请求结束时推送最终草稿、部分草稿或失败状态。
- 用户停止分析时取消这条请求，不创建额外任务订阅。

### 下一项设计问题：流式事件使用什么格式

为了让前端区分不同状态，建议每条消息使用结构化 JSON 事件，例如：

```json
{"type":"operation","status":"running","tool":"rank_values","params":{"dimension":"technology"}}
{"type":"operation","status":"completed","tool":"rank_values","params":{"dimension":"technology"}}
{"type":"draft","status":"partial","curves":[]}
{"type":"done","status":"success"}
```

纯文本也能显示步骤，但前端需要猜每行是什么意思，工具失败、用户停止和最终草稿容易混在一起。结构化事件可以稳定渲染状态、工具名、过滤后的参数和最终结果，同时仍不包含 SQL、密钥、原始 JD 或模型逐字推理。

本轮待决问题：是否同意流式接口使用结构化 JSON 事件，每条事件带类型和状态，最后用独立事件表示成功、部分成功、失败或用户停止？

## 第七十一轮：结构化流式事件确认与探索收束

### 已确认决策

- 流式接口使用结构化 JSON 事件。
- 每条事件带事件类型和状态，至少能表达操作进行中、完成、失败、草稿部分成功、最终成功、最终失败和用户停止。
- 工具名称和过滤后的参数可以出现在操作事件中。
- 工具结果摘要、原始工具返回、模型逐字推理、SQL、密钥和原始 JD 不进入流式事件。
