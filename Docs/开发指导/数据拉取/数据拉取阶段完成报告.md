# 数据拉取阶段完成报告

> 状态：阶段完成，等待首次自动定时运行验收  
> 日期：2026-10-22  
> 适用范围：米哈游技术类社会招聘岗位的每日同步、原始证据归档和历史入库

## 1. 结论

本阶段的目标已经达成：系统能够在 CVM 上执行一次受控的真实数据同步，将经校验的原始证据归档到私有 COS，并把岗位及其历史状态增量写入 PostgreSQL。

首次人工初始化同步已经成功完成。每日 `02:00`（`Asia/Shanghai`）的本机定时器已启用，下一步不是继续开发，而是等待并验收首次自动定时同步。首次自动同步成功后，本阶段即可按运行验收流程收口。

本报告不记录 COS 密钥、数据库密码、Docker 凭据、完整原始响应或岗位 JD 正文。

## 2. 本阶段交付内容

### 2.1 受控采集与完整性校验

- Python collector 负责向公开招聘来源发起采集，并生成任务目录与 manifest。
- Go worker 负责校验 manifest、相对路径、文件计数和每个文件的 SHA-256；任一缺失、篡改或不完整结果均不可发布。
- 同一观察范围同一时间只允许一个同步运行，防止重复采集和并发改写历史。
- 运行仅在 CVM 的一次性 worker 容器中进行；不作为常驻公网服务运行。

### 2.2 私有原始证据归档

- 通过腾讯云 COS 的 S3 兼容接口将校验后的批次归档到私有桶。
- 归档完成后还会核对对象存在性、长度及 SHA-256 元数据，确认成功才允许数据库发布。
- 原始文件不作为 CVM 长期本地文件保存；worker 的临时目录会在结束后清理。
- COS 保存完整证据，PostgreSQL 仅保存运行索引、规范化内容、版本历史和审计信息。

### 2.3 PostgreSQL 增量历史模型

- 岗位身份以 `(source_company, source_job_id)` 为准；首期米哈游岗位以来源岗位 ID 识别。
- 内容经规范化后计算确定性 SHA-256。内容未变时复用既有 JD 版本，不重复写入正文版本。
- 内容发生变化时，新建或复用对应的 JD 版本，并关闭旧内容期、开启新内容期。
- 岗位从列表消失时，系统先重新请求详情确认；只有来源明确表示不可用才关闭可见期。超时、限流、服务端错误或未知响应均保持原可见期。
- 岗位 ID 后续重新出现时，保留同一岗位身份，并开启新的可见期；此前的可见期和内容期完整保留。

该设计同时保留“岗位何时可见”和“JD 在何时发生内容变化”两类历史，满足后续展示岗位变动时间线的需要，但本阶段未开发展示页面。

### 2.4 运行审计与失败边界

- 每次同步记录运行摘要、阶段状态、触发方式、尝试次数和归档摘要。
- 阶段审计事件使用稳定错误码、限长且脱敏的诊断信息。
- 审计日志不保存密码、Token、DSN、完整请求头、原始 JSON 或完整 JD 正文。
- 归档或数据库事务失败不会推进当前可用基线，也不会把不完整数据当作岗位消失。

### 2.5 远端运行与调度

- `mrolescope-sync` 由 root 管理，使用本机锁防止重叠运行，并创建、清理私有临时目录。
- `mrolescope-sync.timer` 仅由 CVM 本机 systemd 调度；GitHub self-hosted runner 仅用于构建、测试和受控部署，不承担生产采集调度。
- 每日计划时间为 `02:00 Asia/Shanghai`；错过时间不会补跑。
- 整轮运行失败时，最多在 15 分钟和 45 分钟后各重试一次；重试不与已有运行重叠。
- PostgreSQL 不公开端口；API 仅绑定 `127.0.0.1:8080`；worker 不发布入站端口。

## 4. 容量与运行基线

截至本报告日期，CVM 的本地容量不存在风险：

| 指标 | 当前值 | 判断 |
| --- | ---: | --- |
| 根分区总容量 | 50G | 固定资源 |
| 根分区已用 | 约 9.64GB（20%） | 低水位 |
| 根分区可用 | 约 38GB 以上 | 余量充足 |
| inode 使用率 | 5% | 低水位 |
| PostgreSQL 数据目录 | 约 48MiB | 数据规模很小 |
| PostgreSQL WAL | 16MiB | 无积压迹象 |
| PostgreSQL replication slots | 0 | 无复制槽滞留 WAL |
| `/var/lib/containerd` + `/var/lib/docker` | 约 611MiB | 正常容器运行时占用 |
| systemd journal | 32MiB | 无日志膨胀 |

根盘的固定占用中，`/swapfile` 为 2GiB 的系统交换文件，并非业务数据增长。COS 原始归档不占 CVM 本地磁盘，但会随成功批次累积；其容量与费用应在形成多个实际日批次后单独观测。

当前只有首次基线这一真实数据点，不能以此准确预测 SCD2 的长期增长率。建议在累计 7 次自动同步后重新统计 PostgreSQL、Docker、根盘与 COS 桶用量，再基于实测增量制定长期容量策略。

## 5. 仍待完成的运行验收

本阶段没有待开发功能；下列事项是首次自动运行后的验收动作：

1. 等待下一次每日 `02:00` 的 systemd 自动触发；不需要手动重复初始化同步。
2. 核对该次 `collection_runs` 的状态、计数、审计事件及归档摘要。
3. 在 COS 中确认产生新的私有归档批次，并核对 manifest 摘要。
4. 确认 CVM 临时目录已清理、worker 未残留、定时器仍处于正常计划状态。
5. 自动运行验收通过后，合并验收记录并归档 `implement-daily-job-sync` OpenSpec change。

若自动同步失败，应优先查看脱敏后的同步 service 日志、运行摘要和审计事件；不要为排错而删除 PostgreSQL 历史记录、COS 归档或直接公开存储桶。
