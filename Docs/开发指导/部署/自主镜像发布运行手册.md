# mRoleScope 自主镜像发布运行手册

> 本文是远端开发环境的现行发布入口。它替代 GitHub Actions / self-hosted
> runner 的构建与部署职责；GitHub Actions CI 不再触发、重跑或作为发布门，
> GitHub 仍只是受保护的源码来源。运行时密钥、
> Docker Hub 登录凭据、数据库连接串与私钥均不进入本手册、Git 或终端输出。

## 发布链与边界

```text
本机 clean main
  → 本机完整验证
  → 本机构建四个 linux/amd64 镜像并推送 Docker Hub
  → 以四个 immutable digest SSH 调用 CVM 受控部署器
  → CVM 迁移、健康检查、发布记录、保留两代并清理旧镜像
```

当前目标固定为 Docker Hub `daud1991` 与 CVM
`root@118.89.68.77`。CVM 不构建应用源码，也不保存 Docker Hub 写入凭据。
API 和 PostgreSQL 继续保持 Docker 私网；本流程不会开启 Web Edge 的公网
profile。

每次发布会先用当前 `main` 的不可变提交刷新 CVM 的 root-owned Compose 与
受控 helper。该步骤从固定提交下载部署资产，并以本机已审阅的
`bootstrap.sh` SHA-256 验证入口文件；它不拉取应用镜像、不读取运行时密钥、
也不启动服务。随后唯一的应用变更入口仍是：

```bash
sudo -u mrolescope-deploy sudo -n /usr/local/sbin/mrolescope-deploy \
  <api@digest> <migrate@digest> <worker@digest> <web-edge@digest>
```

部署器会独立确认四个 digest 都属于允许的命名空间，且
`org.opencontainers.image.revision` 都等于同一 40 位 Git 提交；它自身负责
migration、API / Edge 健康检查、必要回滚、release 记录和两代镜像保留。

## 本机前提

- 已检出受保护 `main`，并能 `git fetch origin main`。
- Docker daemon 正常；Docker CLI 具有 Linux/amd64 构建能力。
- 可用 `go`、`python3`、`sqlc`、Node 20 / `npm`、`make`、`ssh` 和 `sha256sum`。
- 维护者已在**本机交互式**登录 Docker Hub：

  ```bash
  docker login -u daud1991
  ```

  密码或 access token 只在该提示中输入；发布脚本不会读取、请求、回显或
  持久化它。
- 本机已有到 CVM 的密钥式 `root` SSH 访问。脚本用 `BatchMode=yes`，因此
  不会回退到密码认证或弹出密码提示。

## 正常发布

自主发布是默认且唯一的远端发布路径。不要触发或重跑 GitHub Actions，也不
要等待其状态；本机质量门是发布前验证依据，受保护主线合并仍按仓库规则执行。

在仓库根目录执行：

```bash
git switch main
git pull --ff-only
git status --short
scripts/release-remote-development.sh --dry-run
scripts/release-remote-development.sh --deploy
```

`--dry-run` 只确认工作树为空、当前分支为 `main`，且 `HEAD` 与刚获取的
`origin/main` 完全相同；不会构建、推送、SSH 或改变 CVM。`--deploy` 才会
执行外部写入。

发布前会执行 `make remote-release-verify`，其内容与原远端发布质量门保持
一致：生成代码一致性、Go/Python 测试、部署资产检查、一次性 PostgreSQL
migration + SCD2 集成测试、前端类型/单元/构建检查、Web Edge 容器检查和
`git diff --check`。临时 PostgreSQL 仅使用名为
`mrolescope-release-verify-<pid>` 的容器和 `127.0.0.1:54329`；结束后会删除
该临时容器，绝不触碰项目 Compose 数据库或 CVM。

四个镜像会先按提交 SHA 作为交付 tag 推送，再从 Docker `RepoDigests` 中
解析为下列形式。tag 从不作为部署输入：

```text
docker.io/daud1991/mrolescope-api@sha256:...
docker.io/daud1991/mrolescope-migrate@sha256:...
docker.io/daud1991/mrolescope-worker@sha256:...
docker.io/daud1991/mrolescope-web-edge@sha256:...
```

最后的 `Remote release completed for <SHA>` 表示 CVM helper 已完成受控部署。
如果 Edge 的人工公网门槛仍未开启，这是正常的：四个镜像会发布，但 Web
Edge 不会自行监听 `80/443`。

## 失败时的停止点

- **本机验证失败**：修复代码或环境后从头执行；不要跳过质量门。
- **Docker push 认证或网络失败**：在本机解决登录/网络问题后重新开始；不
  向 CVM 传递 tag 或半成品 digest。
- **CVM bootstrap 校验或 SSH 失败**：检查主机可达性、固定提交是否已在
  `main`、以及 CVM 的 Docker/Compose 基础环境；不要手工复制 helper 或
  Compose 文件绕过校验。
- **CVM helper 报错**：它已写入受限的失败 release 记录，并在 API/Edge
  健康失败时按自身规则回滚。先查看其脱敏输出和容器状态，再决定下一次
  显式发布；不要手工删除 PostgreSQL volume、执行 `docker system prune`、
  使用 `latest` 或直接修改运行时密钥。

如果发布曾在本次历史观测修补迁移的 35 号版本失败，受控部署器只会识别
完全匹配的迁移工具 dirty 输出（当前版本为 `35 (dirty)`，旧版本可能为
`Dirty database version 35`），自动将迁移标记恢复到 34 后继续应用 35/36。
其他 dirty 版本仍会停止发布，不能手工执行 SQL 或强制跳过迁移。

成功部署后，CVM 自动仅保留当前和上一成功 release 的四个镜像，并只移除
其他未被任一容器引用的同命名空间 digest 镜像。清理是 best effort，失败
不会把已健康的 release 标为失败。

## 维护约定

- 正常发布只使用 `scripts/release-remote-development.sh --deploy`；不要触发或
  恢复 GitHub Actions CI/部署，也不要在 CVM 本地 build。
- 修改 `deploy/remote-development/` 时无需另找人工同步步骤：正常发布会先
  刷新同一 SHA 的受控资产。修改 runtime secret、网络、域名或 Web Edge
  开关仍属于独立的人工安全变更，不由发布脚本处理。
- 需要复验流程本身时，运行：

  ```bash
  bash scripts/test-release-remote-development.sh
  make deploy-config-check
  ```

## 历史观测修补

正式发布后，缺失的自然日只能通过 Worker 的受控修补操作补齐。它只接受
源日期和目标日期，源必须是同一观察范围内的成功发布；目标已有正式观测时
会拒绝覆盖，重复执行同一修补会返回已有结果。修补不会移动当前岗位列表的
发布指针，也不会向前端暴露修补标记：

```bash
docker compose \
  --project-name mrolescope-remote-development \
  --file /opt/mrolescope/remote-development.compose.yaml \
  --env-file /etc/mrolescope/secrets/remote-development.env \
  --profile sync run --rm --no-deps worker \
  repair-observation --source-date YYYY-MM-DD --target-date YYYY-MM-DD
```

该命令只能由 CVM root 维护路径执行；不要改用 `psql` 手工复制表，也不要
传入 run ID、岗位 ID、SQL 或任意连接串。修补完成后，趋势曲线和下钻复用
普通正式观测查询。
