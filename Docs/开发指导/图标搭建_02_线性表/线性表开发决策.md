# 图表二期：线性表开发决策

## 使用方式

本文件是图表二期的决策日志。每一轮澄清都先记录问题、推荐方案与答复；
未得到答复的项目不能当作已决定，更不能据此开始开发。

## 已从《线性表开发指导》确认的目标基线

- 产品是一个泛用的时间折线图功能，与“岗位筛选”并列，入口在左侧导航。
- 时间范围提供：本周、本月、本季度、本年、全部历史；按真实自然日期计算，
  一天是最小统计单位。
- 一个点表示该日快照中符合条件的**去重 JD 数**，不能把岗位跨日存量相加。
- 没有采集到的日期是“缺失”，显示为空档并保留真实日期距离；只有完成采集且
  没有匹配岗位的日期才是 `0`。
- 可配置维度：技术关键词、岗位族、学历、项目、工作地点、最低工作年限。岗位族
  可选“只算主岗位族”或“主、副岗位族都算”；学历和年限支持 `>`、`<`、`>=`、
  `<=`、`==`，默认 `==`。
- 一张图最多 8 条不同颜色的曲线；可混合同一维度的多个条件，所有曲线共用“岗位数”
  Y 轴。曲线应圆润但不能改变真实整数值。
- 本周、本月、本季度、本年固定坐标轴；只有“全部历史”允许在图内滚轮缩放和
  拖拽平移。节点本期只提供图内轻量点击反馈；不预留下钻载荷或跳转岗位列表。
- 优先采用 Apache ECharts 与 `vue-echarts`；外围配置沿用 Naive UI。默认复用既有
  Serving 与筛选逻辑，只有明确且严重的性能问题才讨论新 Serving 或每日物化快照。

## 第 1 轮：数据口径与首期范围

状态：已确认（2026-11-04）。

### R1-Q1：一天按哪个时区划分

问题：是否以 **中国标准时间（Asia/Shanghai）** 的自然日作为一天？
例如，`2026-11-04 00:30`（上海时间）归入 11 月 4 日，而不是按服务器所在地或
UTC 归入前一天。

推荐：是。岗位来源、页面语言和运营节奏都面向中国；全链路使用一个明确时区，
跨月、跨季统计才不会在午夜附近出现一天偏移。

答复：同意推荐方案。按 `Asia/Shanghai` 自然日划分。

### R1-Q2：每日默认统计哪些岗位

问题：是否默认只统计**该日快照中仍有效**的岗位，并保留当日事实而不被后来状态
改写？例如，一个岗位周一有效、周五确认下线：周一曲线计 1，周五计 0；不能因为
周五下线而把周一回写为 0。

推荐：是。这表达的是“当时可见的招聘需求趋势”，也与现有岗位列表默认只展示
仍有效岗位一致。以后可把“包括已下线岗位”作为显式高级选项，而非默认混入曲线。

答复：同意推荐方案。只统计该日快照中仍有效的岗位，后续状态不回写历史。

### R1-Q3：历史不足与缺采如何让用户看懂

问题：是否从**最早一个可信日快照**开始画“全部历史”？若某段没有采集记录，就留
空档；若当前只有一天真实快照，就只显示一个点和清楚的“可用历史从该日开始”说明，
绝不为了让图好看补造 0 或趋势。

推荐：是。这样既保留真实数据边界，也让面试官不会误把“尚未采集”理解成“没有岗位”。

答复：同意推荐方案。从最早可信日快照开始；缺采留空，不伪造 `0` 或趋势。

### R1-Q4：六种统计维度是否同一期交付

问题：首个正式版本是否就让用户配置全部六种维度：技术关键词、岗位族、学历、项目、
工作地点、最低工作年限？例如，用户既能加“Go”，也能加“上海”，而不是先只支持技术词。

推荐：是。将六种条件统一成“曲线条件”模型，UI 和接口不会因为后续补维度而推倒重来；
各维度的选择器可以复用现有筛选字典和控件。

答复：同意推荐方案。六种维度均属于首期范围。

### R1-Q5：一张图是否允许混合不同维度

问题：一张图是否允许混合不同维度的曲线？例如同图比较“Go 岗位数”“上海岗位数”和
“主岗位族为后端的岗位数”，它们都以“岗位数”为单位，因此共用一个 Y 轴；而不是
强制一张图只能放技术词或只能放地点。

推荐：是。混合比较正是泛用看板的价值；保留最多 8 条线、稳定配色、图例单独隐藏或
聚焦某条曲线，即可控制可读性。

答复：同意推荐方案。同图允许混合维度曲线，最多 8 条并共用岗位数 Y 轴。

## 第 2 轮：每条曲线到底代表什么

状态：已确认；学历缺失的歧义已由 R3-Q1 消除（2026-11-04）。

### R2-Q1：未明确学历或年限的岗位是否不计入比较曲线

问题：学历和最低工作年限都有“未明确”的岗位。是否在任何比较条件中都**不计入**它们？
例如“学历 >= 本科”不把“学历未明确”当作本科；“年限 == 3 年”也不把“年限未明确”
当作 3 年。

推荐：是。缺失只代表来源没有明确要求，不等于“学历不限”或“经验为零”；混入会让
趋势看似增长，却只是解析缺失造成的错觉。

答复：同意推荐方案。学历或年限未明确时，不计入对应维度的任何比较曲线。

### R2-Q2：学历比较以哪个要求值为准

问题：是否用 JD 的**最低学历门槛**来比较？例如“本科及以上”在 `学历 >= 本科` 和
`学历 == 本科` 两条线上都算 1；“硕士及以上”在 `学历 >= 本科` **和** `学历 > 本科`
两条线上都算 1，但不在 `学历 == 本科` 中算；“本科至硕士”仍以最低门槛“本科”处理。

推荐：是。这与“最低工作年限”的口径对齐，回答的是岗位进入门槛，而不是候选人可拥有
的任意学历。

答复：同意按最低门槛比较。用户已更正示例：`硕士及以上` 明确匹配 `> 本科`。
“学历缺失按最低门槛比较”这一原话与 R2-Q1 的“缺失不计入”可能有歧义，留待 R3-Q1
确认；在确认前不得把缺失学历映射为任何门槛。

### R2-Q3：岗位族默认只统计主岗位族吗

问题：岗位族曲线是否默认只统计**主岗位族**，并给每条岗位族曲线一个可选开关
“也算副岗位族”？例如某 JD 的主岗位族是“后端”、副岗位族含“运维”：默认只进入
“后端”曲线；打开“也算副岗位族”后，它也进入“运维”曲线。

推荐：是。主岗位族是每份 JD 的唯一归属，默认趋势最容易解释；副岗位族开关仍能满足
交叉能力观察。

答复：同意推荐方案。默认只统计主岗位族；每条曲线可选择也统计副岗位族。

### R2-Q4：多地点岗位在各地点曲线中是否分别计一次

问题：一份 JD 同时写“北京、上海”时，是否让它在“北京”曲线计 1、在“上海”曲线也
计 1？同一条曲线内部仍按 JD 去重，不会因文本中重复地点而变成 2。

推荐：是。每条曲线回答“符合这个地点的独立 JD 有多少”；不同曲线可以有同一岗位，
因此不应把北京线和上海线相加后再当作全站总数。

答复：同意推荐方案。多地点 JD 在每个命中地点的独立曲线中各计一次，曲线内按 JD 去重。

### R2-Q5：每条曲线只对应一个条件值吗

问题：是否让一条曲线只代表一个清楚的条件值？例如添加“技术关键词：Go”和
“技术关键词：Python”会生成两条线；若要观察两者同时要求的岗位，首期不提供
“Go 且 Python”组合曲线，而是保留给后续高级筛选。

推荐：是。图例会直接读成“Go”“Python”“上海”，避免“Go 或 Python”与“Go 且 Python”
这类组合语义让人误解；也有助于把每张图控制在 8 条可解释曲线内。

答复：同意推荐方案。一条曲线只对应一个条件值；首期不支持“且／或”组合曲线。

## 第 3 轮：缺失值、字典匹配与默认视图

状态：已确认（2026-11-04）。

### R3-Q1：确认“学历缺失”的含义

问题：为消除 R2 答复中的一句歧义，是否确认以下规则？**没有明确学历要求的 JD 不参与
任何学历比较；只有明确学历的 JD 才按其最低门槛比较。**例如“学历未明确”不属于
`== 本科`、`>= 本科` 或 `> 本科`；“硕士及以上”属于 `> 本科`。

推荐：是。这样保留 R2-Q1 的缺失值规则，也落实你对 `> 本科` 的更正。

答复：同意推荐方案。未明确学历要求的 JD 不计入任何学历比较；明确学历按最低门槛比较。

### R3-Q2：技术词是否只按词典中的同一技术概念匹配

问题：是否让一条技术词曲线只选择一个**规范技术概念**，同时自动包含该概念在词典中的
别名？例如用户添加“Go”，系统把正文中的 `Go`、`go`、`Golang` 识别为同一条“Go”曲线，
但不会把它们显示为三条线，也不让用户直接输入未收录的任意字符串。

推荐：是。这样与当前技术词筛选、词典治理和前端标签保持一致，趋势不会因为大小写或
别名被拆散。

答复：同意推荐方案。一条规范技术概念曲线合并词典中的大小写和别名匹配。

### R3-Q3：项目是否只使用已有的结构化项目标签

问题：项目曲线是否只根据已有的项目标签统计，而不在图表查询时重新从标题猜项目？
例如标题含“原神”且已被当前项目规则标成“原神”时计入；没有结构化标签的 JD 不因为
图表临时关键词匹配而被算入。

推荐：是。图表与岗位列表会给出完全一致的结果，且不会在展示层悄悄引入另一套解析器。

答复：同意推荐方案。项目统计只使用已有的结构化项目标签。

### R3-Q4：首次打开时默认看哪个时间范围

问题：用户第一次进入“趋势看板”时，是否默认展示**本月**，并且还未添加曲线，先让用户
选择要观察的内容？例如先选“Go”才显示 Go 的本月趋势；用户可随后切到本周、本季、本年
或全部历史。

推荐：是。本月的信息密度适中；不预置一条“全岗位”线，避免用户误解它是某个维度的结果。

答复：不采纳推荐的“本月”；确定默认范围为**本周**，且初始不预置曲线。

### R3-Q5：尚未完成采集的今天如何显示

问题：预设时间范围是否始终延伸到**今天**？例如今天是周三但每日同步还没完成，图表仍
显示周一到周三，周三留空；同步完成后同一位置再出现真实点，而不是把范围悄悄截到周二。

推荐：是。这与“缺采留空、不能补 0”的既定规则一致，且用户知道今天正在等待数据。

答复：同意推荐方案。范围延伸到今天；今天尚未完成采集时显示为空，完成后补充真实点。

## 节点点击边界（当前有效）

本期只提供图内的轻量点击反馈，例如短暂高亮被点击节点；信息悬浮层暂不实现。
**不跳转**到岗位筛选，不自动填写筛选条件，不保存岗位 ID 集合，不创建快照标识，也不增加
岗位筛选的比较能力或路由参数。

未来是否下钻、下钻是否复用岗位筛选、是否要求历史数量一致，均需在新的决策轮次重新讨论；
不得援引下面已搁置的历史问答作为实现授权。

## 第 4 轮：下钻精度与查询体验

状态：部分搁置（2026-11-04）。R4-Q1 与 R4-Q2 不构成本期范围或未来实现授权；
R4-Q3 至 R4-Q6 的查询与图表交互决定仍有效。

### R4-Q1：下钻是否必须和节点数量精确一致

问题：是否要求未来点击 `2026-11-03` 的“Go = 23”节点后，岗位列表显示的就是该日
快照中那 23 份 Go JD？即使其中一些今天已经下线，或今天的正文／标签已经变更，也不能
用“当前仍有效的 Go 岗位”替代。

推荐：是。图和下钻列表必须可相互验证；这会要求后续岗位筛选增加明确的“观察日快照”
能力，而不是误用“首次发现日期”。

答复：已搁置。曾讨论岗位 ID 集合与详情版本，但当前不开发下钻。

### R4-Q2：本期是否只预留下钻载荷，不做假的跳转

问题：在历史快照筛选尚未具备前，本期是否只让节点有清晰的点击反馈，并在代码中保留
可复用的“曲线条件 + 日期”下钻载荷？例如点击时显示“2026-11-03｜Go｜23 个岗位”，
但不跳到一个结果不一致的列表页面。

推荐：是。先把未来跳转所需信息以统一结构保留下来；等岗位筛选能按观察日查历史后，
再接入真实路由，避免出现“图上 23、列表却是今天 17”的错误体验。

答复：已搁置。本期仅保留图内轻量点击反馈，不保留下钻载荷。

### R4-Q3：配置改动是否需要点击“应用”才查询

问题：是否让用户先添加、删除或调整多条曲线，再点击一次“应用”更新图表？例如先加
“Go”“上海”“后端”三条线，最后一次性查询；而不是每选一个下拉项都立刻发起一次查询。

推荐：是。一次请求能避免配置过程中图表反复闪动，也便于在最多 8 条线时控制查询成本。

答复：同意推荐方案。用户修改配置后点击“应用”才发起图表查询。

### R4-Q4：达到 8 条曲线时如何处理

问题：达到 8 条线后，是否禁用“添加曲线”并明确提示“单张图最多 8 条”；保留现有曲线，
必须先删除一条才能继续添加？例如已有 8 条线时，不能自动挤掉最早添加的“Go”。

推荐：是。用户不会在未察觉时丢失一条正在比较的趋势。

答复：同意推荐方案。达到 8 条线后禁止继续添加，须先由用户删除一条。

### R4-Q5：查询失败时是否保留上一次有效图表

问题：修改条件后查询失败时，是否保留上一次成功的图表，同时在图表顶部显示明确错误并
标注“结果未更新”？例如网络中断时，不能把旧曲线悄悄当作刚应用的新条件结果，也不要
用虚构的 0 替代。

推荐：是。保留已验证数据可让用户继续阅读，同时不会把旧结果伪装成新结果。

答复：同意推荐方案。查询失败保留上一次有效结果，并明确标示结果未更新。

### R4-Q6：Y 轴是否默认自动，并允许用户手动缩放查看

问题：是否让 Y 轴默认根据当前可见数据自动给出合适范围，同时允许用户在图内手动缩放
查看细节？例如“Go”在 5～8 之间，“上海”在 80～100 之间时，先保证两条线都完整可见；
用户再放大低值区域观察 Go 的小波动，而不增加第二条 Y 轴。

推荐：是。所有线的单位都是岗位数，共用一个轴可避免双轴造成的错误比较；自动与手动
切换兼顾第一次阅读和深入查看。

答复：同意推荐方案。Y 轴默认自动范围并支持用户手动查看细节；需与既定预设范围的固定
坐标规则在 R5-Q4 明确适用范围。

## 第 5 轮：下钻入口与图表配置界面

状态：部分搁置（2026-11-04）。R5-Q1 至 R5-Q3 的下钻讨论已搁置；R5-Q4 与 R5-Q5 的
图表交互和配置形式决定仍有效。

### R5-Q1：下钻初始结果是否强制包含已确认下线岗位

问题：为确保节点数量一致，是否让下钻后的岗位列表初始设为“全部状态”（仍有效 + 已确认

## 现有 SCD2 与历史快照事实审计（2026-11-04）

结论：**无需为图表另存一份重复的完整 JD 快照。**对于某次已成功发布的采集运行，现有
