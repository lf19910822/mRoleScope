## 1. 目标与边界

为 mRoleScope 建立可恢复、可审计的数据后台，使每个成功采集周期可以：

1. 由 Go worker 取得唯一运行租约后启动 Python collector；
2. 校验 collector 输出的 manifest、计数、相对路径和 SHA-256；
3. 将完整原始响应压缩并写入不可变归档；
4. 以幂等方式写入 PostgreSQL 的批次、岗位、正文版本和批次映射；
5. 完成解析、聚合和变更计算后，以短事务原子切换公开批次；
6. 在故障时保留诊断证据并继续展示上一个成功发布批次；
7. 在用户个人账号下的第三方云环境安全运行，不使用公司内网、服务器、VPN、云账号或凭据。

本轮工作不包含：访问官网采集、创建付费云资源、启用生产定时器、开放管理后台、实现图表，或将真实密钥提交到仓库。

### 本期收口：远端开发环境

本期的直接目标是让用户购买后的腾讯云 CVM 成为**远端开发与验证环境**：运行私有 PostgreSQL、容器运行时和验证服务，并为 COS、个人 GitHub 与受控运维入口准备好边界。它像先把一间安全的远端工作室装修好，而不是立刻开门营业。

已记录的真实采集、首次基线、旧同步任务交接、每天 02:00 调度和微信告警属于后续数据运营设计；它们约束未来实现，但**不阻断本期环境初始化**，也不会在本期被启用。云产品仍只由用户本人在腾讯云控制台选购。

### 沟通约定

后续 Grill 问题先用通俗语言说明“这个决定会影响什么”，并尽量给出生活化例子；技术术语、端口、服务名和不可变约束仍同步写入本文件，作为实施时的准确依据。

## 3. 目标架构（待决策后的实施基线）

```text
云主机定时器（尚不启用）
          │
          ▼
Go worker ──受控 argv──> Python collector ──> 公开招聘 API
    │                         │
    │                         └──> 临时任务目录 + manifest
    ▼
持久状态机 → 校验 → 原始归档 → 入库 → 解析 → 聚合 → 原子发布
    │              │            │
    │              │            └── PostgreSQL（私有容器/网络）
    │              └─────────── 对象存储（生产）/本地归档（开发）
    ▼
Go Gin 只读 API ─────────────────────────────> 浏览器（HTTPS）
```

关键不变量：

- 状态顺序为 `queued → collecting → validating → archiving → parsing → aggregating → published`；失败记录失败阶段，不改变 `published_run_id`。
- 同一 `schedule_key` 同时只能有一个活跃执行；租约需要可到期、可续租、可恢复。
- 对象存储和 PostgreSQL 没有分布式事务。归档、数据库写入、解析、聚合、发布必须分阶段落库并可幂等重试；发布只发生在全部证据和数据已就绪之后。
- 成功归档只以 `run_id` 寻址，内容包含原始列表、详情和 manifest，不包含 Cookie、Authorization 等敏感头。
- 同筛选范围且相邻的成功批次才可比较；范围或接口口径变动应产生可见断点。

## 4. 拟定开发路径（尚未授权执行）

### 轨道 A：数据后台开发与验证

| 阶段 | 交付物 | 验收重点 |
| --- | --- | --- |
| A1 运行编排 | `collection_runs` 状态机、数据库租约、超时/重试策略、受控 worker CLI | 并发触发不重复执行；进程崩溃后可识别并恢复或失败终止。 |
| A2 校验与归档 | manifest 深度校验、压缩归档格式、本地归档适配器、孤立产物核对 | 篡改/缺失/计数不符不得发布；同一归档可复验。 |
| A3 入库与版本 | jobs/JD versions/run_jobs 幂等写入、内容 hash、完整性对账 | 同内容不重复版本；每个成功 run 的岗位集合可完整还原。 |
| A4 解析与聚合 | 版本化解析批次、规则证据、变更事件、聚合快照 | 规则升级不覆盖旧结果；不可比周期明确标记。 |
| A5 发布与恢复 | 短事务发布切换、失败恢复、管理 CLI、审计日志 | 中途任一失败仍展示上一发布版本；可从既有归档续跑。 |
| A6 生产存储适配 | 目标云对象存储适配器、凭据注入、归档与数据库恢复演练 | 不将密钥给浏览器；成功批次可从对象存储与备份还原。 |

### 轨道 B：云基础设施准备（仅在范围确认后推进）

1. 依据云厂商、地域、域名和运维入口等决策，按届时官方说明核验可用性、实际账单、付款周期和上线前置条件。
2. 建立个人账号下的最小网络边界：HTTPS 对外；SSH 仅限个人受控入口或使用厂商受控运维通道；数据库无公网端口。
3. 以环境变量/个人密钥管理配置数据库与对象存储凭据，绝不进入 Git、镜像或浏览器。
4. 部署 API、worker、反向代理、PostgreSQL 和备份作业；对象存储用于成功批次归档。
5. 完成数据库恢复、归档恢复、回滚到上一发布批次、磁盘/对象存储增长及失败告警演练。
6. 只有 A1–A6 验收、云安全检查和旧同步任务隔离全部完成后，才讨论启用每周一 08:00（Asia/Shanghai）定时器。

## 6. 风险、控制与完成定义

| 风险 | 控制措施 | 通过条件 |
| --- | --- | --- |
| 错误/不完整采集导致误发布 | 计数与哈希校验、阶段状态、只允许完整成功批次发布 | 异常 fixture 无法切换发布批次。 |
| 数据库和归档不一致 | 分阶段提交、幂等恢复、孤立产物扫描和对账 | 从失败中断点重试不丢失也不重复数据。 |
| 云成本超预算 | 采购前按续费价、带宽、流量、对象存储、备份、域名摊销核算 | 用户确认的实际总成本不高于批准预算。 |
| 云端攻击面扩大 | HTTPS-only、最小端口、无 DB 公网暴露、个人凭据隔离 | 安全组和服务监听地址复核通过。 |
| 部署工作流被滥用 | 仅受保护 `main` 可部署；部署必须手动触发并通过 GitHub Environment 门；PR/分叉任务不得使用 CVM runner 或部署权限 | 测试工作流与部署工作流的权限、runner 标签、Environment 规则复核通过。 |
| 服务器版本漂移或无法准确回退 | 仅运行由 GHCR digest 锁定的镜像；记录发布的 Git 提交和 digest；不使用 `latest` | 服务器运行镜像、发布记录与 Git 提交一一对应；可以选择上一 digest 回滚应用。 |
| 真实密钥泄漏至代码或日志 | 密钥仅由用户通过受控运维通道写入 root 可读运行时文件；CI 使用短期 `GITHUB_TOKEN`，不在镜像、仓库、工作流输出或本文档中存放值 | 对仓库、镜像构建上下文和 Actions 日志做密钥扫描后无真实值。 |
| 双任务重复抓取 | 新旧任务切换清单和调度互斥 | 新 worker 启用前，旧 ChatGPT 周任务已停用或明确隔离。 |
| 无法恢复 | 定期数据库/归档恢复演练，记录 RTO、缺失项和修复措施 | 隔离环境恢复一个指定批次并通过只读核对。 |
| 无数据库备份且未演练恢复 | 成功采集必须先完成 COS 归档、重新计算哈希并核对 manifest；恢复时限与重建演练暂后置 | 原始归档不丢失，但数据库故障后的恢复时长和自动重建能力尚未验证；该风险由用户明确接受。 |

“后台初始化完成”不等于“上线”：至少需要已确认范围内的轨道交付物、自动化测试、恢复演练记录和用户对所有决策树分支的确认；生产定时采集仍需额外确认。

#### Q1 澄清记录 — 2026-10-20

### 默认工程规范 — 2026-10-21（用户授权，无需逐项提问）

以下是本项目已冻结的实施基线，不是已经在腾讯云或 GitHub 中执行的操作：

1. **E3：部署执行与镜像权限**：CVM 不为 GitHub Actions 开放 SSH 入站端口。改用仅服务本仓库部署工作的专用 self-hosted GitHub Actions runner，它只经出站 HTTPS 连接 GitHub；普通 CI、Pull Request 和分叉仓库一律使用 GitHub 托管 runner，不能调度到 CVM。部署 job 使用 GitHub Environment `remote-development`，只允许受保护 `main` 的人工触发流程执行。runner 使用独立的非登录 Linux 账户；它不加入 `docker` 组，不能直接读取运行时密钥。
2. **GHCR 临时读取**：构建 job 以最小权限向私有 GHCR 写入镜像；部署 job 使用只具有本仓库 Packages 读取权限、随 job 失效的 `GITHUB_TOKEN` 临时拉取指定 digest。部署助手在独立临时 Docker 配置目录中登录并在拉取后删除该目录；CVM 不保存长期 GHCR 拉取令牌。
3. **E4：配置与密钥边界**：可公开的 Compose 定义、端口绑定、镜像 digest 和非敏感配置可在 Git 中审阅；PostgreSQL 密码、COS 写入身份及其他真实密钥仅由用户通过腾讯云受控运维通道写入 CVM 的 root 可读运行时凭据文件（权限 `0600`）。root 受控部署助手读取这些文件；密钥不得出现于 Git、GHCR 镜像层、Actions 配置、日志、截图或本文档。优先使用腾讯云临时/实例身份访问 COS；若届时产品能力不满足，才创建仅限目标桶和前缀的最小权限 CAM 身份，并记录轮换日期。
4. **最小权限部署助手**：self-hosted runner 只可调用一个 root 拥有的部署入口；该入口只接受已校验格式的 mRoleScope GHCR digest，临时取得镜像、执行受控 Compose 更新、执行本机健康检查并写入发布记录。它不接受任意 shell 命令、不读取或打印运行时密钥；部署 runner 没有交互式 SSH 登录权限。
5. **E5：发布、校验与回滚**：每次人工部署都从指定的受保护 `main` 提交重新运行测试、构建并记录 Git SHA 与镜像 digest；同一时刻只允许一个部署。更新后仅针对私有/本机端点运行健康检查和迁移兼容性检查；本期不会因此开放公网网站。失败时应用容器回到上一份已验证 digest；数据库迁移不自动回滚、不执行破坏性降级，而是按向前兼容和人工修复处理。保留当前与最近 10 个成功部署的镜像及发布记录，其余未引用构建产物可按 GHCR 生命周期策略清理。
6. **范围重申**：本基线不创建腾讯云资源、不安装 runner、不写入真实密钥、不访问招聘官网、不启动采集调度。实际购买、控制台配置、密钥注入与首次部署均需用户在之后明确启动。
