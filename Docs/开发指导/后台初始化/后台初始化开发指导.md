# 腾讯云远端开发环境开发指导

> 状态：可进入实施；未创建腾讯云资源、未写入真实密钥、未发布到 issue tracker。
> 适用范围：mRoleScope 的远端开发与验证环境。本文是实施基线；同目录的《后台初始化开发方案》保留为决策追溯记录，而非操作清单。

## Problem Statement

mRoleScope 需要一处不依赖公司机器、公司网络、公司账号或公司凭据的远端开发环境。维护者需要在个人腾讯云环境中验证 Go 模块化单体、私有 PostgreSQL 和容器化交付，同时保留未来将每个成功**采集批次**的完整**原始归档**写入 COS 的能力。

当前代码已经能验证 Python collector 产生的 `manifest`，并提供 API 存活和数据库就绪检查；但尚未实现持久运行状态机、归档上传、入库、解析、聚合或发布。因此，环境初始化必须先做到“可安全部署和验证”，不能假装已经具备真实采集或公开上线能力。

## Solution

在腾讯云上海地域的个人账号中建立一台成本受控的 CVM，运行 Docker Compose 私有栈：PostgreSQL 16、迁移任务和 Go API。CVM 只通过出站 HTTPS 连到 GitHub、Docker Hub（经腾讯云官方镜像加速器）和必要的腾讯云服务；数据库和 API 不在本期向公网开放。

代码交付使用个人 GitHub 仓库与 GitHub Actions：推送自动测试，受保护 `main` 的人工部署工作流复跑测试、构建项目镜像、推送到维护者的公开 Docker Hub 仓库，并将镜像 digest 交给 CVM 上的专用部署 runner。CVM 只运行被 digest 锁定的镜像，不从 IDE 接收拷贝的业务代码，也不在服务器临时编译源码。

成功采集后才需要的原始归档将存入同地域 COS；在那之前，COS、数据库和调度均不得被用于访问招聘官网或形成真实同步任务。

## User Stories

1. 作为项目维护者，我希望所有远端资源属于我的个人腾讯云账号，从而避免公司基础设施、支付方式和凭据进入项目边界。
2. 作为项目维护者，我希望个人腾讯云账号启用 MFA，从而降低账号被接管后同时影响 CVM、COS 和数据的风险。
3. 作为项目维护者，我希望环境部署在腾讯云上海地域，从而让未来中国大陆访问者、CVM 与 COS 获得同地域的基础条件。
4. 作为项目维护者，我希望先使用一台 2 vCPU、2 GiB 内存、50 GiB 系统盘的月付 CVM，从而以更低成本完成低访问量的远端开发、验证和同步后台早期开发。
5. 作为项目维护者，我希望控制台当天的可用区、库存、带宽和续费价格被复核，从而不把历史报价或优惠当作采购承诺。
6. 作为项目维护者，我希望使用腾讯云当前可选的 Ubuntu 22.04 LTS x86_64 作为默认系统镜像，从而获得稳定、文档齐全的 Docker 与 GitHub Actions runner 运行环境。
7. 作为项目维护者，我希望数据库由自管 PostgreSQL 16 容器提供，从而不在本期引入 TencentDB 的额外成本和运维边界。
8. 作为项目维护者，我希望 PostgreSQL 没有公网 `5432` 端口，从而避免把数据库直接暴露给互联网。
9. 作为项目维护者，我希望 API 在本期仅供 CVM 本机和受控验证使用，从而在域名、HTTPS 与备案均后置时仍能安全验收服务。
10. 作为项目维护者，我希望优先使用腾讯云受控运维通道，从而不必为日常操作开放 SSH。
11. 作为项目维护者，我希望若必须使用 SSH，仅允许我的固定个人 IP 访问 `22` 端口，从而不出现 `0.0.0.0/0` 的管理入口。
12. 作为项目维护者，我希望生产与验证逻辑环境使用独立数据库角色、数据库、COS 前缀和运行配置，从而避免验证操作污染未来正式历史。
13. 作为项目维护者，我希望成功采集批次最终保留完整原始响应、`manifest` 和 SHA-256 证据，从而让岗位、正文版本、批次映射和后续统计可重建。
14. 作为项目维护者，我希望 COS 与 CVM 同地域，且 CVM 磁盘只承载可清理的临时文件，从而不把单机磁盘误当作永久历史仓库。
15. 作为项目维护者，我希望在没有完成 COS 归档及哈希复核时绝不把一次运行标为成功，从而保护不可变原始归档这一数据底线。
16. 作为项目维护者，我希望暂不购买数据库备份、磁盘快照或高可用数据库，从而把首期成本和精力集中在真实数据链路；同时接受数据库故障后的恢复时限尚未承诺。
17. 作为项目维护者，我希望 CVM 可以按文档、镜像和配置重新搭建，从而不依赖某一台机器上未记录的手工状态。
18. 作为项目维护者，我希望每次提交自动运行现有测试，从而在部署前尽早发现 Go、Python collector 或前端回归。
19. 作为项目维护者，我希望远端部署只能由我人工触发，从而避免一次普通推送意外改变 CVM。
20. 作为项目维护者，我希望 CVM 接收不可变容器镜像，而不是从本机复制文件或在服务器编译源码，从而让线上实际版本可追溯到 Git 提交。
21. 作为项目维护者，我希望镜像以维护者公开 Docker Hub 仓库的 digest 部署且不用 `latest`，从而可以准确识别运行版本并回到上一份已验证应用镜像。
22. 作为项目维护者，我希望 Pull Request、分叉仓库和普通 CI 无法使用 CVM 的部署 runner，从而避免不可信代码获得服务器执行权。
23. 作为项目维护者，我希望部署 runner 只需向外访问 GitHub 与 Docker Hub（通过腾讯云官方镜像加速器），从而不因 CI/CD 而新增 GitHub 到 CVM 的入站 SSH 通道。
24. 作为项目维护者，我希望 PostgreSQL 密码、COS 身份和其他真实密钥不进入 Git、镜像层、Actions 日志或本文档，从而避免凭据随着代码传播。
25. 作为项目维护者，我希望每次部署都执行本机健康检查和数据库就绪检查，从而确认容器启动不等于服务真实可用。
26. 作为项目维护者，我希望同一时刻只运行一个部署，从而避免两个 Compose 更新互相覆盖。
27. 作为项目维护者，我希望应用镜像失败时能够回到上一份已验证 digest，而不删除数据库或原始归档，从而把应用回滚和数据恢复分开处理。
28. 作为项目维护者，我希望数据库迁移采用向前兼容和人工修复策略，从而不以自动 down migration 破坏远端数据。
29. 作为项目维护者，我希望在远端环境验收前只使用离线 fixture，不访问招聘官网或启动调度，从而不把环境初始化误变成正式同步。
30. 作为项目维护者，我希望未来的首次真实采集由我手动触发，从而在每日日程、旧任务切换和微信告警尚未实施时仍能保护数据历史。
31. 作为项目维护者，我希望未来自动同步保持禁用，直到首次完整手动基线确认成功，从而保证同一时刻没有两个同步任务访问同一来源。
32. 作为项目维护者，我希望网站、域名、HTTPS、备案、图表、微信告警和灾备演练不阻断本期环境搭建，从而先获得一个安全、可验证的远端工作室。

## Implementation Decisions

### 范围和完成标准

- 本期完成的是远端开发与验证环境，不是公开网站或数据生产系统。环境达到“可实施”后，维护者可以安全地部署现有 API、PostgreSQL 与迁移任务，验证 `/healthz` 和 `/readyz`，并为后续 COS 接入预留最小权限边界。
- 本期不运行 worker 的真实采集，也不启用任何定时器。现有 worker 在 manifest 校验后即停止；持久运行状态机、归档上传、入库、解析、聚合与原子发布属于后续数据后台开发。
- 术语沿用产品与 ADR：**采集批次**是一次完整采集的事实边界；**原始归档**是带 manifest 和 SHA-256 的完整原始响应；**发布批次**只能在全部数据阶段完成后更新。数据库去重不得替代批次归档。

### 腾讯云资源与网络基线

- 资源归属为腾讯云个人账号，个人账号必须启用 MFA；不使用公司账号、企业子账号、VPN、支付方式、网络或密钥。
- 地域固定为上海（`ap-shanghai`）。CVM、COS、未来数据库访问和运行配置必须保持同地域；实际可用区以购买当日控制台库存为准。
- 首期实例为月付 2 vCPU / 2 GiB / 50 GiB 系统盘，Ubuntu 22.04 LTS x86_64。维护者在控制台确认带宽、公共 IPv4、磁盘和 COS 的当期持续成本不超过每月 100 元后自行购买；不采购 TencentDB、负载均衡、CDN、快照或数据库备份服务。购买页当前的 1 Mbps 带宽可用于本期；首次拉取容器镜像会较慢，但不需要为尚未上线的网站提前购买更高带宽。
- 2 GiB 是开发环境的成本优先下限，而非未来数据处理的性能承诺。主机必须配置 2 GiB swap；GitHub 托管 runner 负责镜像构建，CVM 只拉取并运行镜像；一次只允许一个部署或未来同步运行。后续真实采集、解析或聚合出现持续内存压力、swap 持续增长或 OOM 时，先停用调度并将实例升至 4 GiB，再继续数据运行。
- CVM 使用独立 VPC 与子网。它需要受限的出站访问，以完成系统更新、GitHub runner 通讯、Docker Hub 镜像拉取（经腾讯云官方镜像加速器）和未来腾讯云 COS 访问；安全组不开放应用端口或 PostgreSQL `5432` 入站。公共 IPv4 仅为低成本出站连接手段，不能被理解为允许公网服务。
- 优先使用腾讯云受控运维通道。如有 SSH 例外，安全组只允许维护者固定个人 IP 的 `22` 入站，并在无需 SSH 后关闭该规则。绝不允许 `0.0.0.0/0`。

### 远端运行拓扑

- 使用 Docker Engine 与 Compose plugin 管理远端栈。PostgreSQL 16、数据库迁移任务和 Go API 置于私有 Docker 网络；数据库不发布宿主机端口。API 在本期只绑定回环地址，以供 CVM 本机健康检查。
- 生产与验证逻辑环境即使共用一台 CVM，也必须拥有独立的 PostgreSQL 数据库与角色、COS 前缀、运行配置和发布记录。当前部署目标是 `remote-development` 验证环境，不产生或公开正式岗位数据。
- 项目自有镜像和第三方运行镜像均固定到明确版本与 digest。远端 Compose 定义只引用 digest，不允许将可变标签作为部署输入。
- 成功采集的将来归档目的地是同地域 COS。CVM 仅保存可删除的任务临时目录；一份运行只有在完整归档已写入 COS、文件计数与 manifest SHA-256 被重新核对后，才有资格成为成功采集批次。当前环境初始化不会写入真实采集数据。
- 首期不实施数据库逻辑备份、磁盘快照、整机备份或恢复时限承诺。可替换 CVM 的部署图纸、容器镜像、迁移和非秘密配置必须可审阅；真实密钥由维护者重新注入。成功原始归档不得因为数据库、解析或聚合失败而删除。

### GitHub、Docker Hub 和部署执行

- 个人 GitHub 仓库是唯一代码来源。推送和 Pull Request 自动运行测试；部署不是 push 触发器，必须由维护者人工启动。
- 部署只能从受保护 `main` 发起。部署工作流在 GitHub 托管 runner 上再次运行必要测试，构建项目自有镜像并推送到维护者的**公开 Docker Hub** 命名空间；工作流记录 Git SHA 和产物 digest，再把 digest 交给远端部署阶段。
- CVM 不接受从 IDE、本机或 SSH 复制的业务代码，也不在服务器构建 Go、Python 或前端源码。远端只能拉取指定 digest，因此可准确回退到上一份已验证的应用镜像。
- 使用专用 self-hosted GitHub Actions runner 执行远端部署。runner 仅以出站 HTTPS 连到 GitHub；普通 CI、Pull Request 和分叉仓库始终使用 GitHub 托管 runner，不能获得该 runner 标签或部署权限。
- Docker Hub 用户名是公开的 Repository Variable `DOCKERHUB_USERNAME`；仅用于推送的 Docker Hub access token 是 GitHub Actions Secret `DOCKERHUB_TOKEN`。构建 job 只使用该 Token 推送两个项目镜像；CVM 与部署 job 不接收、不保存 Docker Hub Token，也不登录 Docker Hub。
- 部署 job 使用 GitHub Environment `remote-development`，设为单并发，并配置为仅接受受保护 `main`。self-hosted runner 使用独立的非登录 Linux 身份，不加入 `docker` 组。它只能调用一个 root 拥有的受控部署入口；入口从 root 所有的配置读取唯一允许的 Docker Hub 命名空间，校验两个 mRoleScope digest 格式，拉取镜像，执行受控 Compose 更新、本机健康检查并写入发布记录。该入口不接受任意 shell 参数、不打印密钥，也不授予交互式 SSH 登录。

### 已实现的远端部署资产与首次安装

- 仓库中的 `deploy/remote-development/compose.yaml` 是 CVM 的唯一远端栈定义：PostgreSQL 与迁移任务只连接内部 `backend` 网络；API 同时连接 `backend` 与普通 `edge` 网络，以便 Docker 将 API 发布到宿主机回环地址。API 仍只绑定 `127.0.0.1:8080`，PostgreSQL 没有宿主机端口，迁移仅由受控入口以一次性任务运行。
- `deploy/remote-development/mrolescope-deploy` 是 root 拥有的受控入口。它只接受 `/etc/mrolescope/remote-development.conf` 中唯一配置的 Docker Hub 命名空间下的 `mrolescope-api@sha256:<64 位小写十六进制>` 与对应的 `mrolescope-migrate` digest；它不读取标准输入、不保存 Docker Hub 登录信息。它还会确认两个镜像带有相同的 Git revision 标签。
- 入口固定使用 `/etc/mrolescope/secrets/remote-development.env`、`/opt/mrolescope/remote-development.compose.yaml` 与 `/var/lib/mrolescope/releases`，不接受这些路径或 Docker/Compose 参数。新 API 未通过本机 `/healthz` 和 `/readyz` 时，入口会尝试恢复上一份已验证的 API digest；数据库迁移绝不自动回退。
- `deploy/remote-development/bootstrap.sh` 是唯一的首次基础设施例外：它只从**已合入受保护 `main` 的完整 40 位 commit SHA**下载上面两个基础设施文件，安装 root 所有的 Compose、部署入口、Docker Hub 命名空间配置和受限 sudoers 规则。它不下载业务源码、不构建镜像、不启动容器，也不创建密钥。不可使用分支名、`main` 或可变 tag 代替该 SHA。
- 在浏览器确认该 commit 已位于 `main` 后，维护者通过 CVM 终端执行下列命令；`<FULL_MAIN_COMMIT_SHA>` 只替换为页面显示的完整提交 SHA，`<DOCKERHUB_USERNAME>` 只替换为自己的小写 Docker Hub 用户名：

  ```bash
  curl --fail --location --proto '=https' --tlsv1.2 --connect-timeout 10 --max-time 60 \
    "https://raw.githubusercontent.com/lf19910822/mRoleScope/<FULL_MAIN_COMMIT_SHA>/deploy/remote-development/bootstrap.sh" \
    --output /tmp/mrolescope-bootstrap.sh
  sudo bash /tmp/mrolescope-bootstrap.sh <FULL_MAIN_COMMIT_SHA> <DOCKERHUB_USERNAME>
  ```

  如果 CVM 当前不能连接 `raw.githubusercontent.com`，可从 jsDelivr 下载同一个固定提交的 bootstrap；在确认下载脚本的 SHA-256 与该提交审阅后的值一致后，以受限的 `jsdelivr` 备用源获取其余部署资产。每个资产会先在所选源有限重试，再切换到另一受信任源；完整下载与基础校验完成前，任何资产都不会离开暂存目录：

  ```bash
  curl --fail --location --proto '=https' --tlsv1.2 --connect-timeout 10 --max-time 60 \
    "https://cdn.jsdelivr.net/gh/lf19910822/mRoleScope@<FULL_MAIN_COMMIT_SHA>/deploy/remote-development/bootstrap.sh" \
    --output /tmp/mrolescope-bootstrap.sh
  sudo env MROLESCOPE_ASSET_MIRROR=jsdelivr bash /tmp/mrolescope-bootstrap.sh <FULL_MAIN_COMMIT_SHA> <DOCKERHUB_USERNAME>
  ```

- 安装完成后才注册 Actions runner。注册命令必须以 `mrolescope-deploy` 身份运行，并在 GitHub 页面生成的 `./config.sh` 命令末尾追加 `--labels mrolescope-deploy`；再用页面的 `svc.sh` 命令安装并启动 systemd 服务。runner 不加入 `docker` 组。

### 配置、密钥和最小权限

- 可审阅的 Compose 定义、镜像 digest、端口绑定和非敏感配置进入版本控制；真实值永远不进入源代码、镜像层、Actions YAML、工作流日志、截图或本指导。
- Docker Hub 用户名不是秘密：将其同时设为 GitHub Repository Variable `DOCKERHUB_USERNAME`，并作为 bootstrap 的第二个参数写入 CVM 上 `root:root 0644` 的 `/etc/mrolescope/remote-development.conf`。Docker Hub access token 是秘密：只创建具备推送权限的最小 Token，并仅保存为 GitHub Actions Secret `DOCKERHUB_TOKEN`；它不得进入 CVM、Git、镜像、日志或聊天记录。
- PostgreSQL 密码、COS 身份及其他运行时机密仅由维护者通过腾讯云受控运维通道写入 CVM 的 root 可读凭据文件，权限为 `0600`。root 受控部署入口向容器注入所需值，但不回显它们。
- COS 首选腾讯云实例/临时身份。如果届时需要长期 CAM 身份，权限只能限定至目标桶和当前环境前缀，并记录维护者负责的轮换日期；浏览器不得获得 COS 写入权限。
- 不在本期创建供浏览器使用的对象存储、数据库或管理 API 凭据，也不在 GitHub 保存数据库或 COS 的长期高权限密钥。
- 首次离线部署目前只需要 CVM 上的 PostgreSQL 配置；尚未实现归档上传，因此不要在这个文件提前写 COS 访问密钥。维护者以 root 创建 `/etc/mrolescope/secrets/remote-development.env`，所有者为 `root:root`、权限为 `0600`，仅含下面四项。密码使用 `openssl rand -hex 32` 生成的 64 位小写十六进制字符串，这样同一密码既能安全出现在 PostgreSQL 配置中，也无需手工 URL 编码：

  ```dotenv
  POSTGRES_DB=mrolescope_remote_development
  POSTGRES_USER=mrolescope_remote_development
  POSTGRES_PASSWORD=<64 位随机小写十六进制密码>
  DATABASE_URL=postgres://mrolescope_remote_development:<同一密码>@postgres:5432/mrolescope_remote_development?sslmode=disable
  ```

  维护者可使用 `sudoedit` 写入该文件，随后执行 `sudo chown root:root /etc/mrolescope/secrets/remote-development.env` 和 `sudo chmod 600 /etc/mrolescope/secrets/remote-development.env`。密码不得粘贴进聊天、GitHub Secret、Git、终端截图或 Actions 日志。

### 部署验收与回滚

- 一次部署的外部输入是受保护 `main` 的提交及其构建出的镜像 digest；输出是记录了提交、digest、时间和验证结果的发布记录。每次只允许一份部署执行。
- 部署后从 CVM 本机检查 API 存活与数据库就绪，并核验迁移可以在既有 schema 上安全执行。检查失败则该应用部署失败，不改变未来采集调度状态，也不开放公网入口。
- 应用故障时可重新部署上一份成功记录的 digest。应用回滚不删除 PostgreSQL 数据、COS 对象或采集批次。
- 数据库迁移不自动执行 down migration。生产式故障优先前向修复；若将来需要数据恢复，再按已确认的“COS 原始归档不丢失、恢复时限后置”原则单独设计。
- 保留当前及最近 10 份成功部署的镜像和发布记录；Docker Hub 中未被引用的构建产物按维护者设置的保留策略清理。

### 实施顺序和维护者操作边界

1. 维护者在腾讯云控制台自行核验当期价格并购买/创建 CVM、同地域 COS、VPC、子网和最小安全组；不向助手提供账号、密码、访问令牌或密钥内容。
2. 维护者通过受控运维通道完成 Ubuntu 更新、Docker Engine、Compose plugin 和专用部署身份的安装；此阶段不安装业务源码、不开放 API/数据库公网端口。
3. 维护者创建两个公开 Docker Hub 仓库：`<DOCKERHUB_USERNAME>/mrolescope-api` 与 `<DOCKERHUB_USERNAME>/mrolescope-migrate`；然后在 GitHub 配置受保护 `main`、`DOCKERHUB_USERNAME` Repository Variable、`DOCKERHUB_TOKEN` Actions Secret、`remote-development` Environment 和 runner 归属。普通 CI 与部署 workflow 必须使用不同 runner 范围。
4. 在受保护 `main` 合入部署资产后，以完整 commit SHA 和 Docker Hub 用户名运行一次 bootstrap；已注册的专用 runner 不需要重新注册。部署必须使用 Docker Hub digest、root 可读运行时凭据和部署并发锁。
5. 写入仅含 PostgreSQL 四项配置的 root-only 凭据文件，以现有离线 fixture 进行第一次部署验收，验证迁移、`/healthz`、`/readyz`、发布记录、镜像 digest 和网络边界；不访问招聘官网。
6. 只有环境验收通过且数据后台链路另行实现、测试和确认后，才恢复“首次手动真实采集 → 正式历史基线 → 旧任务隔离 → 可配置调度”的后续分支。默认自动同步配置仍为每天 `02:00`（Asia/Shanghai），但本期必须禁用。

## Testing Decisions

- 最高层的验收缝隙是一条人工触发的远端部署工作流：给定受保护 `main` 的提交，外部可观察结果应是固定 digest 的容器启动、数据库迁移完成、`/healthz` 返回存活、`/readyz` 表示数据库可用，并产生可追溯发布记录。测试不依赖 runner 内部脚本实现细节。
- 现有 Go 配置、HTTP 路由和 collector manifest 校验测试继续作为快速反馈层；它们验证外部配置错误、数据库就绪状态、manifest 路径/哈希/计数约束，不要求真实腾讯云或真实招聘接口。
- 现有 CI 保持 Go、Python collector 与已生成前端的类型检查、单元测试和构建；部署 workflow 在发布镜像前再次运行其适用测试，避免只相信历史绿色结果。
- Compose 集成验收应验证 PostgreSQL 没有公网宿主机端口，API 只由回环地址可访问，迁移可在空数据库重复运行，数据库失联时 `/readyz` 返回不可用而 `/healthz` 仍保持存活。
- 镜像验收应验证运行中的项目镜像、发布记录和 Git SHA 的一一对应关系；测试部署不得使用 `latest` 或未记录 digest。应用回滚测试只验证上一 digest 被重新部署，不测试或触发数据库 down migration。
- GitHub 权限验收应验证：Pull Request 不会使用 self-hosted runner；部署只能由受保护 `main` 人工发起；同一时刻的第二个部署会排队或被拒绝；Docker Hub Token 仅存在于 GitHub Actions Secret，CVM 上没有长期 Docker Hub 令牌。
- 密钥验收应扫描源仓库、镜像构建上下文、Compose 可审阅配置和 Actions 日志，确认没有真实数据库密码、COS 密钥或个人访问令牌；运行时凭据文件只允许 root 读取。
- 云网络验收由维护者在控制台和 CVM 上共同检查：无 `5432` 公网规则、无应用端口公网规则、SSH（如存在）只来自固定个人 IP、CVM 能通过腾讯云官方镜像加速器拉取批准的 Docker Hub 镜像，并能通过出站 HTTPS 执行 GitHub runner 通讯。
- 所有环境验收数据使用离线 fixture 或健康检查，绝不访问招聘官网；未来对 manifest、COS 原始归档与 `collection_runs` 状态机的测试将作为数据后台功能规格另行定义。

## Out of Scope

- 购买、开通或支付任何腾讯云资源，以及由助手保管或输入真实凭据。
- 公网网站、域名、HTTPS、备案、反向代理、CDN、负载均衡和任何面向访客的 API。
- 首次真实采集、招聘官网访问、Python collector 的在线运行、自动同步、旧同步任务切换和微信告警。
- 持久 collection run 状态机、数据库租约、COS 归档上传、入库、解析、聚合、变更计算、发布批次切换和图表功能。
- 数据库备份、磁盘快照、整机备份、高可用数据库、明确 RTO/RPO 和周期性灾备演练。
- 将生产与验证环境拆为多台主机、微服务、消息队列、Redis 或 Kubernetes。
- 自动数据库 down migration、基于备份的回滚，或以本地磁盘替代成功批次的 COS 原始归档。
