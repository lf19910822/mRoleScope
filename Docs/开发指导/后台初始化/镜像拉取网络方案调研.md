# CVM 镜像拉取网络方案调研

> 状态：维护者已在 CVM 的 Docker daemon 配置腾讯云官方镜像加速地址，并验证 Docker 已识别配置。重新部署显示：Docker Hub 之外的 GHCR 镜像层下载仍可能超时。维护者已决定不购买 TCR，改由公开 Docker Hub 运行镜像配合该官方加速器交付；详细实施见同目录《GHCR 网络受限的低成本交付方案调研》。
>
> 调研日期：2026-10-21；只采用腾讯云官方资料作为腾讯云产品依据。

## 结论

可以在 CVM 内为 **Docker Hub 镜像拉取**配置腾讯云官方镜像加速器，优先于接入来源不明的第三方公共镜像站。它有望解决本次 `postgres` 官方镜像在 `registry-1.docker.io` 超时的问题；但它不是“让这台 CVM 的所有国际网络都变好”的方案。维护者实际重试时，Docker 已识别该加速器，且 Docker 日志显示 PostgreSQL 镜像已成功拉取；另一个镜像层从 GHCR 内容分发端下载仍超时。即使将 Docker 单层并发下载数降为 1，GHCR 的 TLS 握手仍会超时；两类网络路径需要分别处理。

原因很简单：该配置由 Docker daemon 的 `registry-mirrors` 消费，只影响 Docker 向 Docker Hub 取镜像的路径。它不会代理或加速 GitHub Releases、`api.github.com`、GHCR、`apt`、普通 `curl`，也不会改变 CVM 的 DNS、路由、安全组或一般 HTTPS 出站。因此，之前 GitHub Runner 压缩包下载 EOF 的问题仍需按 GitHub 出站链路单独处理；不能把镜像加速器当作通用 VPN/HTTP 代理。

项目应继续保持“镜像以 digest 固定”的规则。加速器只改变首次取得字节的路径，不能把 `latest` 或未审核镜像变成安全输入。

## 当前可选路径

### A. 腾讯云官方 Docker Hub 镜像加速器（建议先验证）

腾讯云官方《配置镜像加速器》将其配置为 Docker 的 `registry-mirrors`，并给出腾讯云镜像加速地址 `https://mirror.ccs.tencentyun.com`。这是最小的、只针对 Docker Hub 的改动：在 CVM 的 Docker daemon 配置中加入该地址，重启 Docker，然后重新执行**原有的人工部署工作流**；不在服务器手工 `docker pull` 或手工运行 Compose。

这条路径已用于本次第三方运行镜像 `postgres`。在 GHCR 下载持续不稳定、TCR 价格超出预算后，维护者已决定将项目自有运行镜像也迁移至公开 Docker Hub，并继续使用 digest 验证；本段原有 GHCR 直连方案已废弃。

**变更前检查**：维护者应在腾讯云官方文档/控制台确认加速地址仍适用于当前账号与地域；由 root 修改 Docker daemon 的配置前，需要先备份现有配置，确认没有删除 Docker 当前的其它 daemon 选项，并安排一次 Docker 重启窗口。Docker 重启会短暂中断运行中的容器；目前部署失败且没有成功运行的业务栈，这一风险可控，但仍须由维护者确认后操作。

### B. 腾讯云容器镜像服务（TCR）代理缓存（后续可评估）

TCR 的代理缓存/镜像同步思路是把 Docker Hub 上游镜像先纳入腾讯云账号的容器镜像服务，再由 CVM 从该受控仓库拉取。它能减少对 Docker Hub 的运行时依赖，并可为将来多台 CVM 复用缓存。对本项目而言，若要消除这次已经证实的 GHCR 运行时拉取不稳定，API、迁移和 PostgreSQL 三类运行镜像都应从 TCR 拉取；不能只代理 PostgreSQL。它不是当前故障的零配置替代品：至少需要在个人腾讯云账号中开通/创建相应 TCR 实例、配置上游与命名空间/仓库、访问授权，并把 Compose 中的镜像引用改为该仓库的**固定 digest**。

本调研没有把“个人版一定免费”或“没有任何流量/存储费用”写成前提。腾讯云实例类型、配额、地域可用性和计费页会随账号与时间变化；若选择 TCR，维护者必须在创建前于 TCR 控制台的实例选择和计费说明中确认：个人版是否可用、是否需要产品开通、镜像存储/公网或跨地域流量价格、私有拉取权限及保留策略。未确认前，不购买、不启用，也不修改部署资产。

## 不采用任意第三方公共镜像加速器

任意第三方镜像站会成为新的供应链和可用性依赖：它可能替换、记录或无法稳定提供镜像内容，也可能无公告地改变服务策略。对于后续真实数据后台，不应仅因一次 Docker Hub 超时就把所有拉取流量交给未审核第三方。

若未来要采用非腾讯云镜像服务，至少须先明确运营主体、TLS 域名、隐私条款、地域/可用性、故障退出方式，并验证按预期 Docker Hub digest 拉到的内容；此类决策要单独记录，不能隐式写进一条临时运维命令。

## 建议的下一步

1. 将项目自有 API 与迁移运行镜像迁移到维护者的公开 Docker Hub 命名空间，仍固定到 digest。
2. 保留 CVM 上现有的腾讯云官方 Docker Hub 镜像加速器，并通过更新后的受控工作流重新部署。
3. 仅当 Docker Hub 路径也无法满足实际需要时，再评估 TCR 或个人电脑中转归档；不要同时引入未审核第三方镜像站。
