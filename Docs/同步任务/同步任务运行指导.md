# 每日同步任务运行指导

本文用于将已完成部署的远端开发环境升级为“可人工初始化、经核验后每日同步”的运行环境。它不会创建 COS 桶、不会购买云产品，也不应在本地公司机器上保存岗位原始数据。

## 边界与前提

- worker 在 CVM 上以一次性 Docker 容器运行；GitHub Actions runner 只构建、测试和部署镜像，**不**负责生产调度。
- PostgreSQL 仅在 Docker 内部 `backend` 网络中可达；API 仍只绑定 `127.0.0.1:8080`。
- worker 不发布任何端口。它额外连接普通 `edge` 网络仅为向米哈游和 COS 发起 HTTPS 出站请求，不形成公网入站服务。
- CVM 任务目录只在运行期间存在。完整原始响应先经 SHA-256 校验并归档到私有 COS，再在 PostgreSQL 中发布索引、版本和历史期。
- 默认时间是每日 `02:00 Asia/Shanghai`。错过时间不会补跑；失败最多重试两次，等待 15 分钟、45 分钟。

在开始前，远端部署工作流必须已经成功构建并部署 API、migrate、worker 三个来自同一 Git commit 的 Docker Hub digest。

## 1. 创建 COS（在腾讯云控制台手工完成）

1. 在与 CVM 相同地域创建一个**私有** COS 桶；建议名称带上 APPID，例如 `mrolescope-<APPID>`。
2. 创建仅供本同步任务使用的运行身份。它只需对该桶及其对象前缀具备读写/查询对象元数据的最小权限；不要使用主账号密钥。
3. 不配置公开读、公开写、网站托管或自动删除生命周期规则。本期保留成功批次作为原始证据，生命周期成本策略后续再决定。
4. 记下地域、服务端点、桶名、Access Key ID 与 Secret Access Key。后两项只写入 CVM 的 root-only 文件，不能提交 Git、贴到工单或发进聊天。

上海地域的端点形式通常类似 `https://cos.ap-shanghai.myqcloud.com`。实际值以 COS 控制台显示为准；端点不要包含桶名、用户名、查询串或 Token。

## 2. 更新 CVM 的受控部署资产

在合并包含同步资产的受保护 `main` commit 后，以该 commit 的完整 SHA 重新执行 bootstrap。CVM 若不能直连 GitHub，可沿用已验证的 jsDelivr 入口并先核验脚本 SHA-256。

```bash
sudo env MROLESCOPE_ASSET_MIRROR=jsdelivr \
  bash /tmp/mrolescope-bootstrap.sh <40位main提交SHA> <docker-hub-namespace>

sudo stat -c '%n  %U:%G  %a' \
  /opt/mrolescope/remote-development.compose.yaml \
  /usr/local/sbin/mrolescope-deploy \
  /usr/local/sbin/mrolescope-sync \
  /usr/local/sbin/mrolescope-operations \
  /etc/systemd/system/mrolescope-sync.service \
  /etc/systemd/system/mrolescope-sync.timer

sudo systemd-analyze verify \
  /etc/systemd/system/mrolescope-sync.service \
  /etc/systemd/system/mrolescope-sync.timer
```

期望 Compose 与 unit 文件是 `root:root 644`，三个 helper 是 `root:root 750`。bootstrap 只安装资产并执行 `daemon-reload`，不会拉取 worker、不会写密钥、不会启动 timer。

## 3. 写入运行时密钥

仍使用既有 root-owned 文件 `/etc/mrolescope/secrets/remote-development.env`。在已有 PostgreSQL 变量之后增加以下**占位项对应的真实值**；不要在终端回显文件内容：

```dotenv
COS_ENDPOINT=https://cos.ap-shanghai.myqcloud.com
COS_REGION=ap-shanghai
COS_BUCKET=replace-with-private-bucket-appid
COS_PREFIX=mrolescope
COS_ACCESS_KEY_ID=replace-with-least-privilege-id
COS_SECRET_ACCESS_KEY=replace-with-least-privilege-secret
SYNC_TIMEOUT=45m
SYNC_RETRY_DELAYS=15m,45m
```

保存后验证权限，而非文件内容：

```bash
sudo chown root:root /etc/mrolescope/secrets/remote-development.env
sudo chmod 600 /etc/mrolescope/secrets/remote-development.env
sudo stat -c '%U:%G %a' /etc/mrolescope/secrets/remote-development.env
```

期望输出为 `root:root 600`。错误的 COS 值会使 worker 在发起采集前失败，且日志只写脱敏摘要。

## 4. 显式初始化一次

确保 `mrolescope-sync.timer` 尚未启用，再由有 sudo 权限的运维人员执行：

```bash
sudo systemctl disable --now mrolescope-sync.timer
sudo /usr/local/sbin/mrolescope-sync initialize
```

该命令会进行真实外部采集和数据写入。它以 root 创建临时目录，容器内以非 root 用户写入，结束时清理临时目录；成功时 COS 已有 manifest 与原始文件，PostgreSQL 已有首次基线。首次成功只建立基线，不产生“新增/消失/修改”的展示事件。

在 CVM 上核验，不显示原始 JD：

```bash
sudo docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
sudo docker compose \
  --project-name mrolescope-remote-development \
  --file /opt/mrolescope/remote-development.compose.yaml \
  --env-file /etc/mrolescope/secrets/remote-development.env \
  exec -T postgres sh -ceu \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT id, status, data_date, archive_uri, archive_manifest_sha256 FROM collection_runs ORDER BY created_at DESC LIMIT 5;"'
```

同时在 COS 控制台核对对应前缀下存在 `manifest.json`、列表页和详情文件。数据库中的 `archive_manifest_sha256` 应与 COS manifest 的 SHA-256 一致。

### 可选：通过 GitHub Actions 执行固定运维操作

完成本节的 bootstrap 后，仓库中的 **Remote development operations** 工作流可由已获授权的仓库成员在 `main` 上手动触发。它只能调用 root-owned 的固定操作，不能输入任意 shell、Docker 参数、文件路径或密钥：

- `status`：输出 API 健康状态、容器和 timer 状态；
- `initialize-sync`：需要确认文本 `RUN_INITIAL_SYNC`，执行本节的真实初始化；
- `enable-sync-timer`：仅在人工检查过 COS 与数据库成功结果后使用，确认文本为 `ENABLE_DAILY_SYNC`；
- `disable-sync-timer`：停止未来调度但不粗暴中断正在执行的同步，确认文本为 `DISABLE_DAILY_SYNC`；
- `sync-logs`：输出当日同步 service 的脱敏 journal。

该工作流使用既有 CVM self-hosted runner，但它不是调度器：每日调度仍只由 CVM 的本机 `systemd` timer 发起。所有写入 COS 密钥、安全组或系统级 SSH 设置的操作仍需人工在腾讯云/CVM 控制台完成。

## 5. 启用每日 timer

仅在初始化完整成功、COS 对象和数据库审计记录均核验后执行：

```bash
sudo systemctl enable --now mrolescope-sync.timer
sudo systemctl status mrolescope-sync.timer --no-pager
sudo systemctl list-timers mrolescope-sync.timer --all
```

它每日 02:00（`Asia/Shanghai`）启动一次。使用 `Persistent=false`，所以 CVM 在该时间关机或 timer 未运行时不会恢复补跑。失败时由同一 service 最多再试两次；最终失败仅保留脱敏审计和运行摘要，不发布半成品，也不把当天误写为零数据。

## 6. 停止、回滚与排查

暂停后续采集但保留历史：

```bash
sudo systemctl disable --now mrolescope-sync.timer
sudo systemctl status mrolescope-sync.service --no-pager
sudo journalctl -u mrolescope-sync.service --since 'today' --no-pager
```

不要为了回滚而删除 PostgreSQL 历史行或 COS 原始批次。若镜像部署本身需要回滚，只回滚到先前已验证的 API/migrate/worker digest；定时器保持禁用，待人工重新初始化验收。

常见排查顺序：

1. 检查 timer 是否启用、worker 运行时是否没有 published port。
2. 检查 `/etc/mrolescope/secrets/remote-development.env` 的所有权/权限和必填项是否齐全，切勿打印值。
3. 查 `collection_runs` 与 `collection_run_audit_events` 的阶段、稳定错误码和脱敏摘要。
4. 核对 COS 桶私有权限、端点、地域、对象元数据 SHA-256；不要将 COS 设为公开来“修复”访问问题。
