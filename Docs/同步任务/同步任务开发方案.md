# 同步任务开发方案

>
> 本文是同步任务的决策记录。每完成一轮讨论，先将结论和下一轮问题写入本文，再继续讨论，避免会话上下文丢失。本文不代表已启用定时器、真实采集、数据库写入、COS 归档或告警。

## 1. 目标与边界

为 mRoleScope 建立可靠、可追溯且节省磁盘的岗位同步基础：从公开来源取得完整岗位清单和 JD，将可验证的结果增量写入远端 PostgreSQL，并让后续产品可以按周、月、季度、年和任意日期范围进行筛选、排序、同比与环比。

本期设计范围：每日同步调度、采集批次、完整性校验、COS 原始归档、PostgreSQL 入库、岗位版本/可见历史、缺失复核、失败重试与可运维记录。

不在当前探索阶段实施：网页接口、统计图表、周期汇总、同比环比、自定义日期查询、面向访客的筛选排序、微信告警或云资源购买。本期会保留这些未来能力需要的原始时间事实，但不计算或展示任何业务指标。

首期采集范围固定为当前米哈游技术类社会招聘筛选条件；在可预见范围内不扩展至“所有社招”或建设多范围运营后台。

## 3. 已核对的现有基础

### 3.1 采集器

`collector/mihoyo_collector.py` 已沿用既有公开接口、分页完整性校验和四并发详情拉取策略。成功采集时会产生原始列表/详情响应与 SHA-256 manifest；`--probe` 只在内存中验证一页列表及一条详情，不创建任务目录。

旧脚本 `Docs/同步任务/mihoyo_weekly_sync.py` 说明了可用的保守采集策略，但它将整份清洗快照写到文件，并以相邻快照比较变化；新同步设计不应复用“覆盖同一快照文件”的持久化方式。

### 3.2 当前 PostgreSQL 骨架

首个迁移已具备以下基础：

- `collection_runs`：调度键、筛选配置哈希、各阶段状态、起止时间与采集计数；同一调度键只允许一个活跃批次。
- `jobs`：`(source_company, source_job_id)` 唯一，记录首次/末次出现的批次引用。
- `jd_versions`：按 `(job_id, content_sha256)` 去重，保存原始字段与展示字段。
- `run_jobs`：记录每个完整成功批次观察到的岗位和 JD 版本。
- `change_events`：已有的预留变更事件表；本期不扩展也不写入，未来展示任务可由 SCD2 历史按需推导或物化。
- `aggregate_snapshots`：预留按批次与统计口径版本保存聚合结果。

数据契约还规定：**岗位在单次成功批次中未出现，不足以证明它已关闭。** 因此，消失状态不能在一次缺失后草率写死。

现有 `collection_runs` 适合作为“每一次同步尝试的摘要卡片”，但当前没有逐阶段、逐重试的追加式审计明细。为满足排障需要，本期应新增专用审计事件表，而不是把所有报错拼接进一个摘要字段。

### 3.3 岗位身份的首期定义（已确认）

米哈游的岗位身份采用来源 API 返回的岗位 ID。数据库中的稳定业务键为：

```text
(source_company = "mihoyo", source_job_id = 来源岗位 ID)
```

现有 `jobs` 表的 `(source_company, source_job_id)` 唯一约束正好符合此规则。岗位标题、JD 正文、任职要求、地点、项目名称、招聘性质以及其他来源字段都不是身份的一部分；它们会随时间变化，应进入内容版本和事件历史。

这条规则的直接含义是：同一个岗位 ID 消失一段时间后重新出现时，**无论新标题、新 JD 与旧内容相差多大，仍视为原岗位的后续修改，不创建新的岗位身份**。系统将保留旧可见期，打开新的可见期，并为新的内容创建或复用相应 JD 版本。这样访客可以连续查看“同一岗位 ID”的全部出现、缺失、重现和内容修改历史。

首期不尝试根据标题相似度、JD 文本相似度或人工猜测，把两个不同岗位 ID 合并为一个岗位；也不因为相同标题而合并。这些规则容易误将不同岗位混为一谈，若未来确有来源 ID 重用的证据，再单独设计人工关联/拆分机制。

## 4. 已确认的数据演变模型

把一份 JD 想成“岗位的一版说明书”，把一次同步想成“今天点名时看到谁在场”。说明书改变时才产生新版本；即使说明书没改，每次完整点名仍应保留“这一天它存在”的事实。

岗位内容历史和岗位可见历史是两条不同的线，不能混为一个 `is_current` 开关：

- **内容版本**回答“这份 JD 写了什么，以及何时观察到内容改变”。
- **可见期**回答“在我们的完整同步观察中，它从何时开始出现、何时开始缺失、是否后来又出现”。

因此，岗位重新出现时，即使正文 hash 与过去完全相同，也必须新开一个可见期；不能把旧记录重新标记成当前，否则中间消失的一段历史会被抹掉。

```text
完整成功批次
    |
    +--> run_jobs：本批次实际看到哪些岗位（不可变观察事实）
    |       |
    |       +--> jd_versions：内容哈希相同则复用，变化才新增
    |
    +--> 岗位可见期（出现/消失历史）
            出现 --> 缺失待确认 --> 已关闭
              ^                         |
              +----- 再次出现 ----------+
                    |
                    +--> 内容期（SCD2：JD 版本修改历史）
```

建议不为每一次观察重复存储整份原始 JD：

1. `jobs` 是稳定身份，键为来源公司和来源岗位 ID。
2. `jd_versions` 是内容版本，仍按内容 SHA-256 去重；不变内容不重复保存。
3. `run_jobs` 是低成本的“本批次见过它”事实，是日/周/月趋势和审计的基础。
4. 另设“岗位可见期”（名称和具体字段待设计）承载出现、首次缺失、确认关闭和重现。它只因消失/重现而断开；岗位关闭后又重新开放时，即便 JD 文本未变，也应开启新的可见期，而非篡改旧历史。
5. 在可见期内另设“岗位内容期”（SCD2 段，名称待设计），指向一个 `jd_versions` 行。标题或 JD 变化时，只关闭旧内容期、打开新内容期，**不**制造一次虚假的消失/重现。
6. 原始采集归档若后续启用，应与数据库热数据分层；它不是用来替代查询索引的。归档位置、保留周期和是否本期落地仍待另行决定。

### 4.1 建议的岗位时间线语义（待落实为表结构）

一个岗位的历史可呈现为下面的形状；示例时间只是说明结构，不代表真实数据：

```text
10-01 见到岗位 ID 123、JD v1  --> 打开可见期 #1；内容期 #1 = v1
10-05 列表未见，详情明确不可用 --> 关闭可见期 #1 与其活动内容期
10-12 同一岗位 ID 123 又见 JD v1 --> 打开可见期 #2；内容期 #2 = v1
10-18 同一岗位 ID 123 见到 JD v2 --> 可见期 #2 保持；关闭内容期 #2，打开内容期 #3 = v2
```

为支持这条时间线，建议使用两个相互关联的期间层。具体表名、列名、约束和索引留待方案收敛后设计：

| 期间层 | 概念 | 用途 |
| --- | --- | --- |
| 可见期 | `job_id`、`opened_by_run_id`、`first_seen_at` | 该段出现历史归属的稳定岗位，以及第一次被完整批次观察到的证据。 |
| 可见期 | `last_seen_run_id`、`last_seen_at`、`first_missing_run_id`、`first_missing_at` | 最后一次正面观察与首次缺失的证据；它们比推测的“实际下线时刻”更诚实。 |
| 可见期 | `closed_by_run_id`、`closed_at`、`closed_reason`、`is_current` | 详情复核确认关闭的证据和原因，例如 `absence_confirmed`；每个岗位最多一段开放可见期。 |
| 内容期（SCD2） | `presence_period_id`、`jd_version_id`、`valid_from`、`valid_to` | 在某段可见期内，哪个内容版本在何时开始/结束被观察到。相同 `jd_version_id` 可被多个内容期复用。 |

内容变化由 SCD2 内容期表达，而非覆盖旧版或额外维护事件表。若一次成功观察发现 hash 改变，在**当前可见期内**关闭旧内容期，并从该次观察开启新内容期；若之后又改回旧 hash，则复用旧 `jd_versions` 内容行、但新开内容期。若岗位已确认消失后重现，则新开可见期和其首个内容期。这样既满足 SCD2，又不重复存同一份大文本，也不会把内容修改误画成岗位消失。未来变动历史页面可从这些期间和版本推导事件。

### 4.2 内容版本 hash 的首期口径（已确认）

JD 内容版本 hash 只由“会展示给访客或参与后续分析的业务内容”构成，不直接对整个来源响应做 hash。建议先将下列字段规范化为键顺序稳定的 JSON 后，计算 SHA-256：

- 标题、岗位类别/职能、招聘性质、项目名称和招聘对象；
- 工作地点；
- 职位描述/职责、任职要求、补充说明、投递说明、岗位摘要；
- 其他会影响业务筛选、展示或解析结论的来源业务字段。

规范化包括统一空值表示、文本换行与 HTML 表达，确保同一句 JD 仅因空格或标签写法不同不会产生假版本。来源岗位 ID 是身份键，不是版本变化字段。

下列类型不参与内容 hash：请求/响应时间、分页位置、排序号、追踪/请求 ID、传输状态、重试次数，以及其他不改变岗位业务含义的技术字段。完整原始响应仍应按归档策略保存，用于审计和将来调整解析；技术字段变化本身不生成新的 JD 内容期。

### 4.3 “发生时间”与“观察时间”必须分开

每日同步像每天在门口点一次名：我们知道 10 月 4 日仍看见、10 月 5 日没有看见，却不知道它是在两次点名之间的哪一分钟下线。因此数据库和界面不能把推断时间伪装成精确事实。

- `observed_at`：某完整批次实际看到岗位的时间，是确定事实。
- `first_missing_at`：首次完整批次未看到岗位的时间，也是确定事实。
- 实际消失区间只能表述为“最后观察到”和“首次未观察到”之间；若界面必须画时间段，应明确标注为“未观察到区间”。
- 再次出现时，记录新的首次观察时间；此前的缺失区间自然有了右边界，但仍不能倒推出实际恢复的精确时刻。

面向访客的展示建议优先使用“最近一次观察到”“自某批次起未观察到”“再次观察到”等措辞，而非未经证实的“岗位已关闭/已恢复”。达到确认门槛后，可在分析口径中归类为“确认消失”，同时保留上述证据时间。

### 4.4 同批次缺失复核流程（已确认方向）

不必机械地等到明天第二次定时同步。每一轮完整列表采集完成后，可以立即对“上一轮可见、这一轮列表却没有出现”的岗位做一次详情复核。这相当于点名册里少了一个人后，当场再打一次电话确认。

```text
上一轮开放可见期的岗位集合 P
本轮完整列表中的岗位集合 L

M = P - L  （本轮列表缺失的候选岗位）
                |
                v
    对 M 中每个岗位请求一次详情接口（低并发、可重试）
                |
      +---------+----------------------+-------------------+
      v                                v                   v
  详情可正常取得                 来源明确表示不存在      超时/限流/网络错误
      |                                |                   |
记录“列表遗漏但详情可用”       本轮确认消失并关闭       记录“结果不确定”，
可见期保持开放                 可见期                  不关闭可见期
```

复核必须在列表和常规详情均已完成、并已通过完整性校验之后执行；否则这一轮本身不能作为消失判断依据。为了避免对来源造成不必要压力，复核应只针对差集 `M`，使用比常规详情采集更低的并发度，沿用退避重试并设置单轮上限。

“无法查询”不是一个足够精确的关闭条件。实施时必须把复核结果规范为三类：

| 复核结果 | 可作为关闭证据？ | 需要记录的事实 |
| --- | --- | --- |
| `available`：详情响应结构完整、岗位 ID 一致 | 否 | 详情仍可访问；列表本轮未列出。 |
| `definitively_unavailable`：来源返回可识别的“不存在/已下线”业务结果，或明确的 HTTP 不存在语义 | 是 | 复核的来源响应类别、确认时间与批次。 |
| `indeterminate`：超时、DNS/网络错误、5xx、429、响应格式异常或未知业务错误 | 否 | 错误类别、尝试次数和安全摘要；保留现有可见期。 |

不能因服务器超时就把岗位标记为消失；那相当于电话占线便宣布对方离职。只有来源本身给出明确否定，才关闭可见期。若来源接口没有稳定、可识别的“不存在”响应，复核不能单独确认关闭，必须回退为多轮缺失规则或先做一次受控的响应语义验证。

建议为每个缺失候选保留复核审计信息：列表缺失批次、复核请求时间、结果类别、有限且脱敏的响应/错误摘要、尝试次数，以及最终是否关闭可见期。它们可用于排查来源波动，但不需要把每次相同 JD 再存一份。

### 4.5 完整成功批次的 COS 原始归档（已确认）

从首期开始，每次**完整成功**同步均归档 collector 产生的原始列表响应、详情响应和 SHA-256 manifest 到 COS。归档以不可变批次路径组织，数据库的 `collection_runs.archive_uri` 与 `archive_sha256` 指向该归档，而不是复制整份原始响应到 PostgreSQL。

发布顺序应遵循以下原则：归档校验成功与数据库事务成功都是发布前提；任一环节失败，批次不得成为对外可用的新基线，也不得据此改变岗位可见状态。CVM 只保存执行中的临时任务目录；成功归档并完成入库后清理临时文件，不作为长期数据仓库。

原始归档的自动删除/生命周期策略尚未确定；在未明确决定前，不设置自动删除规则，避免采集证据被悄然清除。

## 5. 已确认的时间口径与性能原则

- 所有事实时间使用 `TIMESTAMPTZ`；展示时统一转换到 `Asia/Shanghai`。调度时间不是数据时间本身。
- `data_date` 使用 `Asia/Shanghai` 下成功批次的开始日期。例如可由 `(started_at AT TIME ZONE 'Asia/Shanghai')::date` 得出；它是日历报表的统一归属日期，不替代精确事实时间。
- 每个成功批次至少保留开始、结束、发布（如有）和岗位实际观察时间；业务按“数据日”统计时，应明确采用哪个时间字段。
- 内容期的 SCD2 有效期采用左闭右开区间：`[valid_from, valid_to)`。当前活动内容期的 `valid_to` 为空，避免同一瞬间同时落入两段历史。
- `valid_to` 应保存为可解释的观察边界或确认时间，而不是假装知道岗位实际下线的瞬间；列表和图表同时保留“最后观察到/首次缺失”可避免口径误导。
- 只有筛选范围一致、接口/解析契约可比较、且清单与详情均完整成功的批次，才能参与新增、变更或消失判断。
- 周、月、季度、年等标签优先在查询/聚合层从事实时间推导，而不是逐行重复存储“本周、本月”等会随日期变化的标签。
- 高频筛选字段、时间范围和当前状态需建立针对性索引；完整 JSON/JD 正文仅在需要时读取，不作为默认列表查询载荷。
- 聚合结果可按“统计口径版本 + 截止批次”缓存；源数据与计算规则变化后可以重算，不能把派生统计当作唯一事实来源。

### 5.1 周、月、季度、年的 PostgreSQL 原生口径（已确认）

首期不在记录上写入“本周”“本月”“本季度”等会随查询日期改变的自定义标签，也不自行维护日历序号。所有日历分组和空日期补齐使用 PostgreSQL 内置日期时间能力：

| 目标 | PostgreSQL 查询口径示意 |
| --- | --- |
| 数据日 | `(started_at AT TIME ZONE 'Asia/Shanghai')::date` |
| 周（周一至周日） | `date_trunc('week', started_at AT TIME ZONE 'Asia/Shanghai')::date` |
| 月 | `date_trunc('month', started_at AT TIME ZONE 'Asia/Shanghai')::date` |
| 季度 | `date_trunc('quarter', started_at AT TIME ZONE 'Asia/Shanghai')::date` |
| 年 | `date_trunc('year', started_at AT TIME ZONE 'Asia/Shanghai')::date` |
| 补齐没有事件的日期/周期 | `generate_series(...)` 生成时间序列后再左连接事实数据 |

PostgreSQL 的 `date_trunc('week', ...)` 使用周一作为周起点，符合已确认的周一至周日口径。查询应先以 `TIMESTAMPTZ` 范围过滤并利用索引，再转换时区与分组；避免直接对全表每一行做表达式计算而失去范围索引效果。同比、环比将以这些同一原生周期边界计算，不另造一套应用层日历规则。

## 6. 已确认的失败与一致性原则

- 批次未完整成功（列表分页不一致、详情缺失、校验失败、入库失败等）时，保留失败运行记录和安全错误摘要，但**不得**据此标记岗位消失、覆盖最后一次成功状态或发布半成品。
- 同一时刻只允许一个同步任务运行；已有 `collection_runs` 的活跃调度键唯一约束可作为实施基础。
- 首次成功同步只建立基线，不制造“新增/消失”对比结论；后续仅与最近一轮可比较的完整成功批次比较。
- 每日 02:00 启动首个整轮批次；整轮失败后，在同一数据日内最多再自动尝试两次，建议递增等待 15 分钟、45 分钟。每次尝试都有独立运行记录，不与其他尝试重叠；三次均失败后停止。
- 数据日最终失败时，只记录失败运行，不写入 0 值快照、不生成新增/消失事件，也不让最后成功批次伪装成当天数据。未来分析层应展示数据缺口与覆盖度；本期不实现分析层。
- 首次部署后先由运维人员显式执行一次初始化同步；仅在 COS、数据库和审计记录均核验正常后启用每日 timer。首个成功批次只建基线。
- CVM 若错过计划时间（宕机、timer 未运行等），本轮静默放弃：不在恢复后补跑、不生成补跑审计事件、不伪造错过日期的快照；等待下一次正常计划时间。
- 采集失败告警到微信是低优先级的后续能力；本期先保证失败可记录、可诊断，且不误伤已有数据。

### 6.1 同步任务审计（已确认）

本期新增一张追加式的同步审计事件表（暂定名 `collection_run_audit_events`）。它与 `collection_runs` 的关系如下：

```text
一次同步尝试（collection_runs，一行）
    |
    +--> 0..N 条审计事件（collection_run_audit_events）
            scheduled / collecting / validating / missing-recheck
            archiving / persisting / published / failed / retry-scheduled
```

`collection_runs` 保存本次尝试的最终状态、起止时间、数量汇总、失败阶段和简要失败摘要；审计表保存不可修改的过程事件。每条审计事件至少应包括：关联运行 ID、发生时间、阶段、严重级别、稳定事件代码、尝试序号、可安全展示的简要消息，以及必要的结构化诊断字段（例如上游 HTTP 状态、超时类别、重试等待时间、归档校验结果）。

审计表只保存脱敏、限长的错误摘要，绝不写入密码、Token、DSN、完整请求头、完整原始响应或 JD 正文。原始响应的证据归 COS 归档管理；审计表的职责是说明“在哪一步、因何种类别失败、系统随后做了什么”。建议至少为 `run_id + occurred_at` 和“近期失败事件”建立索引，以便快速查看某次运行或近期异常。

## 7. 已确认的关键决策

### 已确定：首次完整同步未出现，先在同批次二次复核

已确认的方向：岗位可以消失后再次出现；每次出现、内容改变、缺失和再次出现都要保留并可展示。重新出现时新开可见期，绝不覆盖旧期。

已确认规则：上一轮可见、本轮完整列表未见到的岗位，在同一轮立刻调用详情接口复核；详情接口给出明确的不可用语义时，立刻关闭可见期。若详情仍可取得，则不关闭；若结果不确定，则仅记录复核失败，不关闭。

这替代了“必须连续两天缺失才关闭”的默认方案。多轮缺失仍可作为来源无法给出明确不可用语义时的保守回退策略。

### 已确定：列表未出现、但详情复核仍能取得时的口径

这个情况表示“它没有出现在本轮目标列表中”，但并不表示“岗位已不存在”。若把它直接算作正常在岗，会掩盖列表筛选/来源异常；若直接关闭，又违背了二次复核的目的。

推荐规则：保持可见期开放，新增一个时间线事件“列表未列出但详情可访问”；展示层可标为“详情仍可访问，未列入本次目标列表”。同时把“本轮列表中的岗位数”和“通过详情复核仍可访问的岗位数”分开统计，避免将二者混为同一口径。

已确认规则：保持可见期开放，记录“列表未列出但详情可访问”事件；“本轮列表岗位数”与“通过详情复核仍可访问岗位数”使用不同统计口径。

### 已确定：业务内容字段生成版本，技术字段不触发版本

岗位 ID 已经确定身份，但 API 响应可能同时带有真正会影响访客理解的字段，以及请求标识、排序号、接口时间戳等技术字段。若将所有原始字段直接哈希，来源每次改变无意义字段都会制造一版“假修改”；若只哈希 JD 正文，又会漏掉标题或地点变化。

已确认规则：定义一份**规范化的业务内容**并计算内容 hash。它包含会展示或用于分析的来源字段，例如岗位标题、职责/描述、任职要求、补充说明、地点、项目名称、招聘性质、岗位类别等；排除请求时间、分页位置、排序值、追踪 ID 等技术/易变字段。原始响应仍按归档策略保存，便于日后复核。

### 已确定：每次完整成功同步归档 COS 原始响应

PostgreSQL 应保存可查询的岗位身份、内容版本、可见期和逐批次观察；它不适合承担无限增长的完整原始响应仓库。反过来，只保存变更后的 JD 虽然节省空间，却无法在未来重放“某天的列表接口当时究竟返回了什么”。

已确认规则：每次**完整成功**同步都将 collector 产生的原始列表响应、详情响应和 SHA-256 manifest 作为不可变批次归档上传 COS；数据库只保存对应 `archive_uri` 和 `archive_sha256`，并在确认归档成功、数据库事务成功后才发布该批次。CVM 的任务目录只是临时工作区，成功后删除，不作为长期仓库。

这样像把每天的“点名原始单据”放入档案库，而把可检索的目录和统计放在数据库：查图表很快，日后也能复核来源数据。代价是 COS 会按实际原始数据量持续增长，需要后续配置生命周期和成本观察；但它不会挤占 CVM 的 50 GiB 系统盘。

### 已确定：以北京时间批次开始日期作为数据日

日期筛选、周/月/季度/年的统计及同比环比都需要一个稳定的日历口径。例如，同步在北京时间 2026-10-22 02:00 开始、02:12 完成：它可以被标记为“10 月 22 日凌晨观察到的数据”，也可以被业务上归到“10 月 21 日结束时的快照”。两者都可行，但混用会让趋势线出现错位。

已确认规则：以 `Asia/Shanghai` 下的**成功批次开始日期**作为 `data_date`。上述批次的 `data_date` 即为 `2026-10-22`；周按周一至周日、月/季度/年按自然日历划分。精确的 `started_at`、`finished_at`、`observed_at` 仍完整保留，供审计和精确时间范围查询。

日历边界、分组和补齐时间序列均使用 PostgreSQL 内置函数（`date_trunc`、时区转换及 `generate_series`）实现，不维护自定义日历标签或应用层周期序列。

### 已确定：筛选条件变化时建立新观察范围、不跨范围比较

岗位 ID 定义“它是谁”，但筛选条件定义“本次点名册本来应该有哪些人”。例如当前只采集技术社招，日后若改为“所有社招”或只采集某个城市，列表增减主要来自筛选范围变化，不能被误记为岗位新增或消失。

已确认规则：每一种来源公司 + 来源接口 + 规范化筛选条件组成一个**观察范围**，并以现有 `filter_sha256` 识别其版本。筛选条件发生实质变化时，创建新的观察范围和基线；不拿它与旧范围做新增/消失/重现比较。相同岗位 ID 在不同范围仍指向同一个 `jobs` 身份，但各范围分别维护自己的可见期和趋势。

### 已确定：首期固定一个观察范围，不建设多范围运营能力

已确认规则：首期只采集当前米哈游技术类社会招聘筛选条件。现有 `filter_sha256` 继续随批次记录，用于证明批次是否可比较；它在首期是防止错误比较的护栏，而不是需要为用户配置和管理的多范围产品功能。

若未来确实需要修改筛选条件，则创建新观察范围与新基线，不跨范围生成新增、消失或重现事件；该扩展届时再设计管理界面、跨范围展示和迁移策略。本期不为这一假设预先建设通用多范围调度。

### 已确定：整轮失败后最多自动重试两次

请求级重试（例如单个网络请求短暂超时）与整轮同步重试不同。整轮失败可能发生在列表校验、详情完整性、COS 归档或数据库事务任一阶段。由于原始数据无法倒回重采，适度自动重试有助于提高每日数据完整率；但无限重试会持续占用机器、对来源造成压力，也可能掩盖配置故障。

已确认规则：每天 02:00 启动首个批次；若整轮未完整成功，则在同一数据日内最多再自动尝试两次，采用递增等待（例如 15 分钟、45 分钟）。每次均建立独立失败/成功运行记录，不发布半成品，不与正在运行的批次重叠；三次都失败后停止，等待人工排查或次日调度。请求级退避重试仍保留在每一次尝试内部。

这像快递第一次无人签收后按间隔再送两次，但不会整夜反复敲门。后续微信告警可在最终失败时发送，但不是本期阻断项。

### 已确定：最终失败数据日是缺口，不是零值

若当天三次尝试都失败，我们只知道“没有取得可信快照”，不知道“岗位数量为 0”。如果把该日补成 0，趋势线会凭空制造断崖，环比/同比也会被严重扭曲。

已确认规则：该数据日保留为“无成功数据/缺口”，不生成 0 值快照、不生成岗位新增或消失事件，也不以最后一次成功快照冒充当天数据。未来周、月、季度、年统计应携带覆盖信息（预期数据日数、实际成功数据日数、缺失日期）；同比和环比仅在两边覆盖条件满足时给出数值，否则显示“数据不足”。这些分析展示均不属于本期实现范围。

### 已确定：CVM systemd timer 触发一次性同步容器

已确认将 CVM 作为同步任务的执行地点：由 CVM 的 `systemd` timer 在每天 `02:00 Asia/Shanghai` 触发一个一次性 Docker 同步容器。该容器只加入内部 Docker 网络，直接访问私有 PostgreSQL 与腾讯云 COS；不开放新入站端口。GitHub Actions runner 继续只负责构建、测试和部署镜像，不承担生产定时采集。

这样分工像“GitHub 负责把工具送到工作室，CVM 工作室每天按时用工具干活”。即使 GitHub Actions 调度延迟或不可用，已经部署在 CVM 的定时器仍可独立运行；数据库也无需暴露到公网。

备选是 GitHub Actions 的 `schedule` 触发采集，但其定时精度、网络出口和密钥路径都不如 CVM 可控，且与现有私有数据库边界不匹配。

已确认规则：CVM 的 `systemd` timer 每日 `02:00 Asia/Shanghai` 触发一次性 Docker 同步容器；容器仅使用内部 Docker 网络访问 PostgreSQL 和 COS，不开放新入站端口。GitHub Actions/runner 仅构建、测试和部署镜像，不承担生产调度。

### 已确定：人工显式初始化后再启用 timer

定时器只会在下一个凌晨 02:00 执行。若部署在白天，直接等待会延迟数据历史的起点；但自动在部署完成后立即采集，也会让“发布代码”隐式触发真实外部请求和数据写入，不便于人工核验。

已确认规则：部署完成后，由运维人员执行一次受控的、显式的“初始化同步”命令，建立第一份完整基线；核验 COS 归档、PostgreSQL 记录和审计事件后，再启用每日 timer。首个成功批次只建立基线，不生成新增/消失/变更结论。

这像先由人陪同试运行一趟，再交给每天凌晨的自动班次。初始化命令与定时任务使用同一镜像和同一同步入口，避免产生两套逻辑。

### 已确定：错过计划时间静默放弃，不补跑

已确认规则：`systemd` timer 不启用持久补跑。若 CVM 在计划时间不可用，或 timer 未执行，本轮静默放弃；系统不在恢复后自动启动同步，也不为错过日期写入人工补跑数据。下一次同步仍按正常每日 `02:00` 计划执行，未来数据展示应将该日识别为缺口。

### 已确定：本期不维护字段级变更事件表

未来需要展示“岗位在何时修改了什么”。JD 完整前后版本已经由 `jd_versions` 保存；如果每次打开页面才比较两大段文本，查询慢且比较规则可能随代码变化，导致历史展示不稳定。

已确认规则：岗位内容变动由 SCD2 内容期的前后版本和有效时间表达；可见变动由可见期表达。本期不新增字段级变更事件表，也不扩展/写入已有 `change_events`。未来展示“改了什么”时，再从前后版本按当时确认的业务字段口径计算或物化，不让这项展示优化增加本期同步复杂度。

### 已确定：PostgreSQL 保留每个唯一 JD 版本的原始字段

每次完整成功同步的完整原始响应都会归档到 COS。仍有一个容量与便利性的选择：`jd_versions` 现有 `raw_fields` 可保存每一个**内容发生变化时**的详情原始字段副本；也可以只在 PG 保存规范化业务字段和 COS 引用，需要解析时再从 COS 取回。

已确认规则：保留每个唯一 JD 内容版本的 `raw_fields` 和规范化展示字段在 PostgreSQL；不变内容因 hash 去重不会重复写入，完整逐批次原始响应仍只在 COS。这样后续解析某个版本时无需下载归档，且重复量仅随真实内容修改增长，不随每日同步次数增长。

可把它理解为：COS 保存每天的完整原始档案箱，PG 为每种不同的“说明书版本”保留一份便于查阅的副本。若未来实际测得版本字段很大、增长超预期，再迁移为只保留 COS 引用，而不是现在预先牺牲可用性。

## 8. 实施前需要验证的技术事实

以下是实现和验收时需要验证的事实，不是新的产品决策，也不授权在当前探索阶段执行真实同步：

1. **来源“明确不可用”的响应语义**：当前 collector 将详情请求失败统一视为错误。实施前需用受控、内存内的测试验证来源对无效/已下线岗位 ID 的 HTTP 状态和业务响应字段；只有可稳定识别的明确否定才映射为 `definitively_unavailable`。若无法证明该语义，则缺失复核一律为 `indeterminate`，不关闭可见期。
2. **COS 安全边界**：部署前由用户创建腾讯云 COS 私有桶（建议与 CVM 同地域）；同步运行身份仅获该桶所需的最小读写权限。凭据只存在 CVM root 管理的运行时密钥文件，不进入 Git、镜像、审计表或终端输出。
3. **幂等与发布顺序**：实现必须验证“同一运行重试不产生重复版本/可见期”，并确认 COS 归档校验和 PostgreSQL 单事务状态写入均成功后，才把批次标记为可用。
4. **运行边界**：实现必须验证 `systemd` 的每日时区、非持久补跑设置、单实例锁和整轮重试次数；不存在真实成功批次的日期不得生成岗位状态变化。

完成这些验证后，才进入实现任务：数据库迁移、同步 worker/容器、COS 上传、审计表、部署资产、初始化命令与 `systemd` timer。它们应通过后续 OpenSpec 变更收敛为可执行规格与任务清单。
