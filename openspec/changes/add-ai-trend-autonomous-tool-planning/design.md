# Design

## Context

当前趋势运行器在调用模型前读取一次 Serving 筛选目录，然后由固定规划器从一次性 Intent 中构造工具调用。Qwen 适配器没有声明工具或解析工具调用；类别工具虽已注册，但没有进入生产规划路径。类别目录中的正式值、显示名称和技术值已经由 Serving 提供，可以作为本次请求的一致快照。

本设计延续现有边界：模型只处理用户问题、正式目录和有限趋势摘要；Serving 仍负责查询和每日曲线；前端仍消费结构化 NDJSON 事件；最终草稿仍由服务端确定性构造和校验。

## Goals / Non-Goals

**Goals:**

- 让 Qwen 在安全白名单内自主决定何时发现类别、读取类别值、读取明确值和请求趋势摘要。
- 让类别限制成为候选解析的硬范围，避免未知类别或模型通配符扩大为整个 technology 维度。
- 让模型工具调用结果能继续驱动最终 Intent，同时保持最终草稿和排名的服务端确定性。
- 执行每个子查询的数量限制，并保持 20 次工具、8 条批量候选和现有超时边界。
- 让工具错误职责和现有流式操作记录保持一致。

**Non-Goals:**

- 不让模型生成每日点位、SQL、JD 正文、图表或自定义指标。
- 不改变 Serving 趋势接口、草稿应用协议、数据库结构或前端图表渲染。
- 不把完整技术词典或完整趋势序列一次性塞入模型上下文。
- 不为每个新增技术类别增加专用 Go 代码或专用 prompt 分支。

## Decisions

### 1. 使用受限的模型—工具循环，最终仍采用 Intent 合同

扩展 Qwen 适配器，使一次模型会话可以返回两类结果：受约束的工具调用，或最终 `ai-trend-draft-v1` JSON。编排器收到工具调用后执行白名单工具，把经过大小限制和字段过滤的结果追加回模型，再继续会话；收到最终 JSON 后执行现有严格 Intent 校验。

模型工具循环与现有 Intent 修正循环分开计数：工具调用总数最多 20 次，结构化 Intent 非法时最多 3 次修正。每次模型回合和工具执行仍受整个请求超时约束。

备选方案是把类别目录静态拼入 system prompt。它能减少协议改动，但无法让模型按需选择工具，也会随类别目录增长而增加每次请求的输入 token，因此不采用。

### 2. 用单次 Serving 快照支持类别工具

请求开始时读取当前公开筛选目录一次，构建技术类别索引：正式类别值、显示名称和该类别下的正式技术值。`list_available_categories` 和 `list_category_values` 使用这个快照，避免模型每次发现类别都重复访问数据库；工具调用仍产生正常的操作事件并计入工具预算。

类别值工具同时接受正式类别值和显示名称，先在快照中规范化为正式类别值，再返回有限的 `{value, label}` 列表。找不到类别时返回安全的不可用值错误，绝不返回整个 technology 列表。

### 3. 按范围优先级解析 Intent

候选解析遵循具体正式值、已登记类别、整个维度的优先级。类别表达式解析为该类别的候选集合，并携带扩展匹配状态；`*` 只解析为该维度的全部正式值。未知表达式保持不可解析，不进入通配符分支。

删除按“编程语言/数据库/前端框架”枚举的查询兜底。若模型错误地产生空表达式或通配符，编排器只允许在工具结果明确证明用户没有类别或值限制时继续；否则将范围校验错误反馈给模型，或交付无结果提示。

### 4. 工具选择和最终草稿分工

模型负责决定类别、正式值、子问题、排名口径和数量。服务端负责验证正式值、读取趋势摘要、按排名指标排序、落实 `ranking.limit`、合并重复曲线，并把候选压到最多 8 条。模型不直接决定每日点位，也不绕过草稿校验。

对于“使用最多的编程语言”这类问题，模型可以选择编程语言类别并设置 `limit=1`；服务端读取该类别候选的摘要后只生成第一名。对于多个子问题，服务端继续采用每个有效子问题先保留一条、再按排名和输入顺序补齐的分配规则。

### 5. 错误和流式事件沿用既有职责边界

工具参数不符合合同、枚举或类别范围时，工具返回安全校验错误并继续模型回合，让模型在上限内修正。参数合法但 Serving、数据库或单个批量元素失败时，不触发模型重试；编排器标记操作失败、保留其他成功结果并生成部分草稿。

模型工具调用的开始、完成和失败事件沿用现有 NDJSON `operation` 事件，参数通过 HTTP 层过滤。模型逐字推理、原始工具返回、SQL、凭据和 JD 内容不进入事件或审计记录。

## Risks / Trade-offs

- **[模型工具循环增加一次或多次模型回合]** → 类别目录和类别值结果保持小而有界；明确值问题跳过类别发现；持续统计实际 token 和耗时。
- **[模型反复调用工具耗尽预算]** → 服务端强制 20 次调用和请求超时，达到上限即用已有结果生成部分草稿。
- **[模型把显示名称当成内部类别值]** → 工具边界同时接受两者并立即规范化，错误类别不会回退为通配符。
- **[工具结果包含过多候选]** → 每个目录结果最多 100 条、每个趋势批次最多 8 条，并禁止完整每日点位进入模型。
- **[旧的测试 Provider 不支持工具回合]** → 保留 IntentProvider 的测试替身适配层；生产 Qwen 路径和新增端到端测试使用工具会话接口，最终合同校验保持一致。

## Migration Plan

1. 先增加工具会话、工具描述和类别索引的单元测试，再改 Qwen 适配器和编排器。
2. 在本地运行 Go 测试、前端类型检查、OpenSpec 严格校验和真实趋势请求回归，重点覆盖编程语言、数据库、明确值和无类别宽泛问题。
3. 发布 API 后用真实流式请求确认工具顺序、20 次上限、中文解释、部分失败和最终草稿应用。
4. 若模型工具协议异常，回滚 API 镜像到上一版本；旧的确定性 Serving 趋势接口和已应用曲线不受影响。
