# Design

## Context

现有趋势 AI 链路由 `internal/aitrend` 的 `TrendRunner`、工具编排器、Qwen provider、Serving reader 和草稿校验组成，并已有生产请求的聚合审计。评测需要复用这条链路，但固定 Serving 数据、逐题结构化轨迹和评测报告不能写入生产审计或日常数据任务。详见 `proposal.md` 的 Why 和 `ai-evaluation-benchmark` spec。

## Goals / Non-Goals

**Goals:**

- 用人工审阅的 Markdown 题目生成可执行的、版本化的 30 题 benchmark。
- 在固定 Serving 快照上运行真实趋势 AI 链路，并隔离每次请求的状态。
- 用确定性约束判分工具调用、范围、正式值、排名、容量和草稿校验，保留可排错的结构化轨迹。
- 单独报告质量、基础设施完整性、token、成本和延迟，支持后续模型或提示词对比。

**Non-Goals:**

- 不接入 BFCL 或 GAIA 官方数据集和排行榜。
- 不把 benchmark 变成线上请求路径、日常 Serving 读取或发布门禁。
- 不保存逐字思维链、凭据、无关 JD 正文或真实用户看板状态。
- 不在本变更中实现实际曲线应用、前端展示或并发压测。

## Decisions

### 1. 评测边界和执行入口

新增独立的评测运行包和命令入口，调用现有趋势 AI 链路的公开构造 seam；固定数据通过已有 Serving reader 接口注入。主评测在草稿通过应用前校验后结束，应用和看板展示另行测试。这样可以复用生产行为，同时避免把测试状态写入真实看板。

候选方案：复制一套简化的测试编排器会更容易控制，但会漏掉真实模型工具循环、错误职责边界和 token 统计，因此不采用。

工具调用判定借鉴 BFCL 的结构化参数匹配思想，但使用项目自己的语义约束；不接入 BFCL 或 GAIA 官方数据集、排行榜或通用任务裁判。

### 2. 题目和快照的双层产物

在 `Docs/开发指导/AI评测/` 保存人工审阅的 Markdown 题目、正式值约束和判分规则；审阅通过后生成机器可读案例文件。固定 Serving 快照采用版本化的、去除敏感内容的评测 fixture，服务于评测运行器而不被日常拉取或生产查询发现。

候选方案：每次直接读取 CVM 线上数据会更接近实时环境，但数据变化会污染回归比较；只写代码中的题目又不便于审阅，因此采用“Markdown 源 + 机器产物 + 固定快照”。

### 3. 结构化案例约束

每个案例包含稳定 ID、中文问题、类别、允许维度和正式值、时间范围、排名语义、期望候选集合或排序、最多 8 条容量规则、异常预期、解释检查项和通过条件。类别范围可以额外声明必选正式值，例如“哪些数据库正在使用？尤其是 MySQL？”允许返回其他数据库，但最终草稿必须包含 `mysql`。正式值用维度 ID 比较，别名先归一化；普通比较按集合比较，排名题比较顺序。

需要验证模型错误修正的案例可声明受控故障注入，例如第一次工具参数替换为非法 JSON；注入只发生在隔离评测 Runner 中，不改变生产工具或真实用户请求。

这使判分器能够检查“比较 Go 和 Python”是否越界，也能接受不同但合理的工具调用顺序，而不依赖模型生成的自然语言。

### 4. 运行、重试和结果分类

运行器按受控串行执行每题三次，每次建立独立请求和隔离状态，沿用 20 次工具调用上限。工具或基础设施错误与 AI/语义错误使用不同状态；基础设施错误最多补跑两次，仍无完整结果则标记评测未完成，不伪造通过或计入 AI 失败率。

候选超过 8 条时，判分器依据固定排序检查前 8 条、总候选数和未展示数量，即使候选值为零也遵循同一固定顺序。局部工具失败、未知值和不支持条件遵循最大努力规则：可用结果必须保留，且不能静默扩大为 `*`。非法 AI 工具参数回传模型修正；合法请求的后台失败只记录失败并继续可用结果，不要求模型重试。

全局 `*` 查询使用一次服务端趋势排名工具跨全部正式值计算 Top N，再交给 Draft 构建；不能先把候选截断到内存上限后再排名，否则技术关键词数量超过候选上限时会漏掉真正的第一名。排名工具的局部读取失败仍返回成功候选并将 Draft 标为 partial。

当前 Serving 条件是单维度的；当用户同时指定项目和技术关键词时，评测保留全局技术最大努力结果，Draft 标为 partial，并明确说明尚未按项目过滤，不伪装成项目内精确统计。

多个互相独立的子问题仍可在一个 Intent 中并列规划；它们分别生成候选组，Draft 在总共 8 条曲线容量内为每个有结果的子问题保留至少一条。该能力不等同于跨维度交集过滤。

对占比/变化率和柱状图等当前不支持的用户要求，运行链路保留岗位数量折线草稿，追加限制说明并标记 partial；明确冲突的多个时间范围则在调用模型和 Serving 前返回安全的时间条件错误。

### 5. 确定性判分和解释检查

判分器读取案例约束、Intent、工具调用记录、工具结果摘要和最终 Draft，依次执行 Schema、正式值归一化、范围、依赖、排名、候选容量和 Draft 校验。端到端通过要求关键条件全部满足；工具、范围、排名和草稿另有分项结果。

解释只做轻量规则检查（中文、长度、与实际曲线一致、明显限制是否说明），保存审计供开发者按需查看，不展示给普通用户，也不影响端到端通过。显示名称只用于报告，判分使用正式 ID。首期不引入 LLM Judge，避免评测结果再依赖一个不稳定的模型裁判。

### 6. 轨迹、版本和报告

每次运行写入独立的结构化评测产物，包含案例和运行 ID、模型/提供商、提示词版本、工具 Schema 版本、快照版本、代码 revision、事件时间、工具名和参数、结果摘要、验证结果、Draft、token、首个事件延迟、总耗时和估算成本。工具参数和结果在写入前使用安全摘要，不保存思维链、凭据或不必要 JD 原文。

报告按每题 0/3 至 3/3、工具调用/查询范围/草稿三个分项分数、六类通过率和整体等权通过率汇总，并分别报告基础设施未完成、工具调用次数、成本以及平均/P50/P95 延迟。成本和延迟不改变功能通过结果。详细轨迹留在独立评测产物目录且不进入普通用户响应，Markdown 题目与汇总报告可版本化。

### 7. 版本和回归比较

评测运行开始时生成一个 immutable evaluation version，绑定模型与 provider、提示词和工具 Schema 摘要、Serving snapshot、代码 revision 与题目/判分器版本。任何绑定项变化都产生新版本；首轮只建立基线，是否在发布前运行由后续流程决定。

## Risks / Trade-offs

- **[固定快照与线上差异]** → 保留独立的 CVM 真实链路冒烟测试，但不把它混入固定 benchmark 分数。
- **[模型随机性导致结果波动]** → 每题独立运行三次，报告稳定通过率而不是单次结果。
- **[评测器过度拟合题目]** → 六类题目由人工编写多种口语化问法，并把可读约束与机器案例分开审阅。
- **[轨迹泄露敏感数据]** → 只保存结构化结果和安全摘要，禁止凭据、思维链和无关 JD 正文进入评测产物。
- **[工具或网络瞬时失败污染质量分数]** → 单独分类、最多补跑两次，并把仍未完成的样本从 AI 失败率中排除。
- **[评测运行拖慢或干扰业务]** → 主评测受控串行、只读固定快照，应用测试使用隔离状态。

## Migration Plan

1. 创建并审阅 30 题 Markdown 与固定快照，生成首个机器案例版本。
2. 在本地或隔离评测环境运行三次重复 benchmark，检查轨迹脱敏、判分和报告统计。
3. 运行独立的 CVM 真实链路冒烟测试和应用集成冒烟测试，确认两者都不会修改真实看板或日常数据任务，且结果不进入固定 benchmark 分数。
4. 保存首轮基线报告；后续模型、提示词、工具或快照变化均以新 evaluation version 运行比较。

不需要生产数据库迁移或线上 API 兼容迁移。若评测实现出现问题，可删除或停用评测入口和产物，不影响线上趋势 AI 链路。
