# Design

## Context

参见 `proposal.md`。现有 `jdserving.ListJobs` 对同一字段的多个值做 OR、不同字段做 AND，但总数使用会员记录计数，不能直接证明跨观察范围的岗位身份已去重；单维度趋势汇总也不能推算岗位交集。当前会员视图按观察范围选择已发布批次，正式维度结果按当前正文优先、同岗位旧结果回退的既有规则选择。

现有趋势 Intent、工具循环和草稿以单维度曲线为中心；`rank_trend_values` 是全维度排名。`AssistantReplyContext` 不包含交叉结果，现有回复将模型增量直接发给页面，事后仅检查长度和语言。`applyTrendRankResults` 可以将原候选外的全局排名值加入子问题；`emitValidatedDraft` 在校验失败且失败事件发送成功时可能返回 nil。两者都必须在本变更覆盖的范围校验路径中解决。

现有 `agentContextV1` 和规划提示词只描述趋势与折线；其默认月份、平均数和最多 8 条曲线属于图表规划口径，不能自动套用于当前交叉数量或文字排名。

本设计以工作树中已审核的 `refine-ai-trend-dimension-planning-prompt` 为前提；实施时保留并衔接该变更，不能覆盖它的提示词或测试。用户决策记录见 `Docs/开发指导/AI作图_01/AI作图开发决策.md` 的 2026-11-27 节。

## Goals / Non-Goals

**Goals:**

- 用现有 Serving 的正式岗位事实计算可复核的当前交叉统计，让 AI 能看到相应聚合结果，同时以受控方式交付数字和排名。
- 将每个子问题的用户范围、统计事实和图表候选关联，保障失败时不输出不合格结果，统计与图表可以分别成功。
- 保持调用有界、数据只读、原有草稿与图表合同兼容，并可通过离线测试验证关键路径。

**Non-Goals:**

- 不增加交并集趋势曲线、历史交叉统计、跨维度并集、自由 SQL、JD 原文外传或新的岗位事实来源。
- 不宣称程序能够完全理解所有自然语言，也不把模型查询类别视为用户确认。
- 不因单个岗位缺少技术分析结果提示或告警，不更改既有岗位列表和趋势图的默认筛选口径。

## Decisions

### 1. 交叉条件使用独立的受限结构

增加与现有单曲线 Intent 并行的交叉统计意图：每个子问题保存正向条件组、排除条件、分组维度、排名数量及时间含义。正向组内允许同维度 `any` 或 `all`，各组以 AND 连接，排除组以 AND NOT 应用；例如 `(Unity OR Unreal) AND 后端 AND NOT 上海`。同一维度可有多个 AND 连接的值组，避免丢失“(Unity 或 Unreal) 且 C++”这样的组合。结构不能表达跨维度 OR；收到此类请求时返回能力限制，不得将其降级为 AND 或忽略某条件。

显式正式值、类别、别名和排除条件由用户原话、可用的明确选择与正式目录共同解析；类别是一个值集合，不是合成曲线。纯查询时前端目前只发送 `query`，不得假定带有当前图表选项。未知值、目录不可用或不确定映射保持未确认；空值集绝不调用现有 `ListJobs` 的“空数组即不限制”语义。含糊的同维度“和”生成分别、去重并集及交集三组关联统计；其他无法可靠确认的范围返回限制、澄清或独立已验证部分。

同步调整实际发送给模型的 Agent 上下文、规划提示词、工具说明及相应合同，保留已审核的四维定义和范围规则，同时分别说明“当前交叉统计”和“单维度趋势图”的时间、排序、数量和能力边界。同步更新人工审阅稿及契约测试；不得把保留已审核内容理解为冻结旧的“只能规划折线”措辞。

备选：仅给模型新增自然语言工具描述，继续用单维度 Intent。该方式无法承载 AND、OR、排除和分组，也无法阻止不同子问题或图表候选相互污染。

### 2. Serving 同一记录筛选后按岗位身份聚合

新增只读的当前岗位聚合入口，复用 `serving_jd_current_inventory_memberships`、`serving_jd_current_dimension_resolutions`、已发布技术结果和现有正式项目、岗位族及地点事实。正向条件必须由同一条有效会员记录同时满足；对于用户指定的排除项，同一岗位若有当前有效正式记录明确命中该排除项，不得用另一条不命中记录绕过排除。最终总数按 `job_id` 去重；分组须保留通过筛选的会员记录来源，在这些记录上按 `(job_id, 分组正式值)` 去重，不能用去重后的岗位 ID 重新关联未通过筛选的记录。默认岗位族包含主、副；用户明确只看主岗位族时限定主岗位族。不要将不同观察范围的两条记录分别满足的正向条件拼成同一次命中。

现有会员约束只保证同一发布批次内 `(published_run_id, job_id)` 唯一，故不直接复用列表查询的 `COUNT(*) OVER` 当唯一岗位总数。测试同一岗位多个范围均匹配、仅一个范围匹配和条件分散在不同记录等情况；同时核对回退结果、有效/待复查状态与正式发布规则。需要技术判断的岗位若没有可用技术结果则静默跳过；不涉及技术的查询不因其缺失而丢弃该岗位。

沿用现有已发布观察范围，不新增多范围产品能力或擅自挑选一个未被证实的权威范围；此前同步方案的首期采集范围为一个观察范围。若同一岗位的当前有效记录冲突且正式事实不足以判断，应保守地不将无法确认满足排除条件的岗位作为确定匹配，并保留其余可验证结果。不得向用户暴露内部观察范围或版本；实际是否存在此类冲突在实施时用受控数据验证，不能预先声称线上存在。

对排除项区分“正式结果明确命中”“正式结果可用但未命中”和“结果不可判断”：最后一种不能因为 `NOT EXISTS`、空地点数组或缺少标签就自动当作明确不匹配。技术结果不可用继续按既定决定静默跳过；其他维度遵循现有正式数据与筛选口径，无法确认的条件不纳入确定匹配。`unrecognized` 是既有岗位筛选专用项目伪值，不能当作正式项目曲线或默认项目排名值；不得将缺少结果误写成用户明确要求该伪值。

类别在服务端以正式目录的全部可用值展开，统计先于排序和显示截断。默认前 8 项；显式更多或全部使用确定排序和分批交付，不能由图表上限、模型候选上限或单次工具输出上限截断统计全集。可用结果为零、未能解析范围和整个查询失败使用不同状态。

为避免类别、会员和正式结果跨版本拼接，聚合计算在一个只读一致性快照内完成。若模型先前读取的目录与执行时正式目录不一致，重新解析并在预算内验证，仍无法确认则阻断相关统计；不把数据库事务跨模型交互长期保持。分批结果必须来自同一已确定的统计快照，取消或预算耗尽时只交付已验证部分并标明显示范围。

备选：分别调用每条单维度趋势摘要后加减，或先读取全局前 N 再过滤。前者没有岗位重合关系，后者会漏掉范围内应上榜的值。另一个备选是直接使用列表 `Page.Total`，但当前它统计会员行而非已证明去重的岗位。

### 3. 范围约束与草稿校验分别落在确定性层

为每个子问题构造范围记录，保存用户明确表达、正式类别展开、可确认正式值、排除条件以及是否仍有歧义；类别查询结果本身只提供目录证据。校验模型 Intent、交叉工具参数、聚合结果来源和候选草稿。基于用户条件检查图表各自的维度与值：上海与 Java 的两条独立曲线可以作为交集问题的辅助图，但不可标为交集，也不能添加未经支持的其他候选。

范围证据须独立于模型 Intent：优先记录用户明确选择，其次由程序依据原话中可直接识别的正式名称、类别名和已确认别名记录文本片段、维度、正向/排除及所属子问题；模型提出的映射仅是待核实候选。只有能确定条件归属和否定关系时才形成硬约束；包含否定、多个子问题或别名歧义而无法可靠归属时保持未确认，不能以模型自己的结果作确认。校验时分别比较筛选范围与用户要求的分组维度：游戏引擎技术排名不能变成全局岗位族排名，而“游戏引擎岗位中的岗位族排名”可以保留岗位族分组。

修正排名合并：范围内排名只可更新原候选或来自完整正式范围且属于该子问题的候选，拒绝维度、类别或正式值越界。筛选维度和分组维度分别验证：例如游戏引擎是技术筛选范围、岗位族是用户要求的分组目标时，后端可以是合法分组值，但数量必须来自游戏引擎范围，不能拿全局岗位族排名替代。修正草稿校验：即使失败事件成功发送，也要向调用方传播校验失败并终止不合格草稿分支；上层需隔离该分支错误，继续交付已验证的交叉统计。如支持部分草稿，应先剔除未通过的条目并重新验证剩余草稿。每个子问题独立校验；未知或复杂语义不得被假定为已确认。针对真实自然语言仍可能发生语义误判，系统只对可独立确定的条件作硬校验，其他情况通过三口径回答、澄清或已验证部分处理。

备选：只在续轮提示中说“已确认范围”。类别目录不等于用户范围，模型可能仍调用全局排名，且当前失败事件不能阻止错误草稿发送。

### 4. 结构化聚合结果贯穿模型、服务端回答和页面

在现有受限工具注册表中新增交叉统计能力，参数只接受正式维度、正式值、受支持的关系、分组和有界分页，不允许任意 SQL。模型获取当前条件、聚合数量和排名的安全结构化结果；需要多页时按预算分页，未读页不能被模型描述为已知结论。服务端保存同一结果的事实引用，为用户直接渲染数量、排名、时间和必要的范围说明，模型只使用这些事实组织解释。

AI 所作的每条总体统计或排名结论必须有覆盖该结论范围的完整聚合证据；对较长结果可分页读取，或提供从完整结果计算出的有界汇总，不必把所有明细装进单次模型请求。程序按用户要求呈现全部可交付排名；若 AI 只拿到部分页面且没有覆盖总体的可信汇总，它只能解释已有证据，不能声称分析了完整排名。

交叉问题的模型回复采用受限的结构化事实引用或预定义解释片段；服务端核验引用与关系后填入事实文本。不能只靠数字正则校验自由文本，因为“第一名”“更多”等无数字表述也可能错误；不接受无法验证的统计结论。若解释失败或不满足合同，仍交付程序生成的已验证统计。程序可以先流式发送操作进度及已验证的事实，但不能在校验前转发模型生成的统计内容。

如现有 NDJSON 文本事件无法表达独立的事实块或分页，则扩展为向后兼容的公开安全聚合事件，并更新页面消费；不得把原始工具结果、岗位 ID、JD 正文、SQL、内部发布/解析版本或凭据写入模型输入和用户事件。扩展 `safeAITrendTool` 及参数过滤，保留既有 20 次工具调用等预算，避免每个候选分别耗尽调用；确保服务模式分类及现有“摘要后关闭工具”的控制不会让纯统计请求跳过交叉查询。指南类请求和普通曲线请求保持原行为。

备选：直接把数据交给模型并原样流式复述。模型可能写错数字或排序，输出之后无法由后验校验真正阻断。

### 5. 统计与图表分开终结

当前统计与原有单维度草稿分别记录成功、部分成功和失败；无论图表是否生成，已验证的统计都可呈现。整体交叉查询故障不等于零，图表成功时仍可交付并说明交叉数量不可用；单条岗位缺技术结果则按静默跳过处理。维持用户停止、新请求失败时保留旧草稿等现有生命周期，不发送不合格的新草稿。

历史交叉问题标明历史交叉不可用，并在当前统计成功时补充当前参考；如已有历史单维度曲线可生成，继续显示并说明它们不是交集或并集。说明不同时间与主/副岗位族等口径，避免将当前统计与图表节点直接等同。

## Risks / Trade-offs

- [模型误解问题] → 用原话、明确选择和正式目录构建可校验约束；含糊关系列三种结果，其余不确定范围不冒称已确认。
- [多观察范围、结果回退或发布切换导致误计] → 同一会员记录内匹配、按 `job_id` 去重，使用一致性快照并覆盖版本与多范围场景；真实数据口径需在实施验证中核对。
- [全部排名过长或查询过慢] → 服务端聚合后有界分批、支持取消并测量实际查询计划；预算不足时明确部分范围，不伪称全部或放宽过滤。
- [严格事实模板限制语言灵活性] → AI 仍读取聚合数据并选择受验证的事实和解释；无法验证时保留程序结果，优先保证数字和排名可信。
- [新增事件或模式破坏现有客户端] → 优先兼容现有 NDJSON 消费；若新增事件，提供旧客户端可忽略的扩展和回归测试，不改变单维度趋势 API。

## Migration Plan

1. 在已审核提示词改动的基础上实现并验证受限查询、范围校验、回答及兼容性；视实际查询计划决定是否需要索引或迁移，不预设新持久化事实表。
2. 用离线 fixture、确定性 provider 和必要的数据库集成测试验证；没有测试数据库时明确跳过，不能称为真实数据库验证。
3. 按项目现有发布流程由后续明确的发布请求执行；回退应用版本即可恢复原单维度路径。任何新增可选事件需在回退时保持旧客户端兼容。
