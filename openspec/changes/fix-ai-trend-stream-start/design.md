# Design

## Context

模型调用发生在编排器进入 Serving 工具计划之前。现有编排器只在工具循环开始时发出操作事件，因此模型调用期间 HTTP 流没有事件。参见 proposal.md 和 `ai-trend-stream-progress` 规格。

## Goals / Non-Goals

**Goals:**

- 在模型 HTTP 请求开始前立即刷新一个可识别的操作事件。
- 为模型返回成功、结构化校验失败重试和提供方错误提供成对的终态事件。
- 保持现有 NDJSON 消费方式、工具调用配额、token 审计和停止语义不变。

**Non-Goals:**

- 不传输模型逐字输出、思维链、请求正文或凭据。
- 不把 Qwen 请求改造成 token 级流式生成，也不更换模型或 HTTP 客户端。
- 不延长模型超时或改变现有重试次数。

## Decisions

### 1. 复用操作事件表示模型阶段

新增受控操作名称 `analyze_intent`，沿用现有 `operation` 事件的 `running`、`completed`、`failed` 状态。这样前端无需引入第二套时间线，服务端仍能使用同一套 NDJSON 校验和参数过滤；模型阶段没有 `params`，不会暴露模型输入或原始响应。

备选方案是新增事件类型或单独建立 SSE 通道，会扩大协议和前端状态面，不能解决本次首事件延迟问题，因此不采用。

### 2. 在编排器包围每次分析调用

编排器在调用分析器前发送 `analyze_intent/running`，分析器返回后发送 `completed`；发生提供方、上下文或其他错误时发送 `failed`。结构化意图校验仍在 `completed` 后执行，校验失败事件和下一次重试保持原有顺序。

### 3. 将模型操作排除出工具审计

模型操作只用于用户可见进度，不进入 `audit_tools`、`tool_call_count` 或 20 次 Serving 工具上限。模型 token 和 AI 尝试次数继续由现有审计字段记录。

### 4. 保持前端通用操作渲染

前端继续按已有操作事件列表渲染 `tool`、参数和状态；`analyze_intent` 会自然显示在 AI 对话窗口顶部。只补充传输层和状态测试，不增加模型原文或摘要展示。

## Risks / Trade-offs

- [模型调用在开始后仍可能长时间无新事件] → 首个 `running` 事件立即刷新，至少明确请求已启动；不伪造周期性进度百分比。
- [同一请求可能出现多次 `analyze_intent`] → 每次重试都发送独立的开始/终态事件，前端按现有同名运行项闭合。
- [客户端中途断开] → 终态事件写入失败时沿用现有取消路径，审计把未闭合操作标记为跳过，不把它记成成功工具调用。

## Migration Plan

1. 更新事件常量、编排器发射逻辑、HTTP 白名单和审计过滤。
2. 添加 Go 与前端事件状态测试，运行质量门。
3. 通过受保护 `main` 发布并用真实问题验证首事件与工具事件的时间顺序。
4. 如需回滚，回退应用镜像；旧前端忽略新增操作名称也能继续消费原有工具、草稿和终止事件。
