# 备份、恢复与回滚

> 当前远端开发环境的已确认边界是不购买数据库备份、磁盘快照或高可用服务。成功采集批次的 COS 原始归档是后续数据链路的永久证据，但不能把它误称为当前数据库备份。本文件中的恢复演练是后续阶段要求，尚未执行。

## 备份对象

- PostgreSQL：本期不建立每日逻辑备份或物理备份。数据库故障后的恢复时限尚未承诺。
- 成功批次归档：后续成功批次需要位于同地域私有 COS，并核对 manifest/文件 SHA-256；它不是数据库备份的替代品。
- 配置：仅备份非秘密配置。密钥由个人账号下的密钥管理保存。

## 恢复演练

1. 后续若引入 PostgreSQL 备份，在隔离环境恢复指定时间点的备份。
2. 按 `collection_runs.archive_uri` 下载一个成功批次，核对 archive/manifest SHA-256。
3. 重建该批次的 `run_jobs` 映射并核对计数。
4. 运行只读 API 核对当前发布批次与历史批次可访问性。
5. 记录耗时、缺失项和修复措施。

## 回滚

应用回滚不删除批次。若当前发布批次被发现不可靠，在审阅后以短事务将 `publication_state.published_run_id` 指回上一个已验证成功批次，并保留故障批次、日志和归档用于诊断。数据库迁移不自动执行 down 操作；故障优先采用前向修复。当前受控部署入口只会恢复上一份已验证的应用镜像，不会删除数据或执行数据库回退。
